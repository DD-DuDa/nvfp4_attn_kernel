# FP4 Decode 相对 FA4 的 2x 性能目标

本文是任务计划，不是设计定稿。它要做的四件事：把目标翻译成可证伪的验收条件、
用实测数据判断目标是否可达、**规定每一轮迭代靠什么证据推进**（§6.3：IKET 主、
ncu 备）、以及规定这个循环在无人值守下怎么跑而不失控（§6.6）。

**写这份计划时没有修改任何 kernel。** 下文所有代码引用都是当前 `HEAD` 的事实。

**本计划由 §12 的九项决策定稿，全部已拍板，无待决项。** 后台 agent 直接按此执行，
不需要也不允许自行改动其中任何一项。

## 1. 目标

在 `q_fp4 / k_fp4 / v_fp4` 三者**都已是量化输入**的前提下，decode kernel 相对
原版 FA4 快 **2x**，且**每个 seq_len 都要达到**，不是全表平均达到。

> **执行顺序覆盖（2026-07-29，用户明确要求）**：性能主线先假定**没有 BF16
> residual**，且输入有效长度按页对齐（`len % 128 == 0`）。Phase 1–5 先在纯
> FP4 Q/K/V 合同下达到 §8.1；只有达到预期 speedup 后，才新增一个独立的
> FP4-Q + BF16 residual 兼容阶段。现有 BF16-Q residual 测试和零长度 residual
> 语义仍必须保持，不得为了这个顺序覆盖而回归。该覆盖不修改 D0–D8、D3 门槛或
> 数值 gate，只调整 residual 新合同的实施时点。

三处已钉死的定义如下。

### 1.1 输入合同变了（已定：单入口双路径）

当前合同（`CLAUDE.md`）是「Q 是 BF16，每次 decode 调用内部量化」。目标合同是 Q
已经是 FP4。这不是优化，是**接口变更**。

> **决策 D2（已定）**：`fp4_decode` 保持单入口，新增可选参数——传 BF16 走旧路，
> 传 `query_fp4 + query_scales` 走新路。

选它而不选「直接改签名」，是因为 `tests/kernel/` 的 46 个测试与全部数值 oracle 都以
BF16 Q 为输入。单入口双路径下两条路共用同一个 core kernel，**现有测试仍然覆盖真正
被优化的那部分**；改签名则会一次性废掉全部数值门槛，在无人值守的几十轮里等于没有
回归保护。

绑定要求：**Phase 1 必须同步给 `tests/kernel/` 加 FP4-Q 入口的数值测试。** 否则新
入口本身没有任何 gate，而它恰恰是性能目标所在的那条路径。

### 1.2 门槛是「每个 seq_len 的几何平均」

比值的算术平均会被单个极端 case 主导，全文一律用**几何平均**。

> **决策 D3（已定）**：对每个 `seqlen ∈ {16384, 32768, 65536, 131072}`，其在所有
> `batch` 上的几何平均比值 ≤ 0.5（即快 2x）。四个都要满足。计时用
> **CUDA graph replay**（D9）。`s1024` 与 `s4096` 继续测量并报告，但**不设门槛**。

门槛只覆盖长上下文，是因为目标场景是 16k 以上的文本（D13）。短序列的瓶颈与长序列
不是同一个：`s1024` 的困难来自低 batch 下 CTA 铺不满和每次 launch 的固定开销，把它
当硬门槛会把预算吸到一个与目标无关的区间。它仍然要报，作为回归看门狗。

取「每 seqlen 聚合」而不是「每格」，是因为每格 ≥2x 会被 `batch=1, seqlen=65536`
单格绑架——那一格需要 42.6x，与 roofline 几乎持平，会让 agent 在一个格子上耗尽
全部预算。取全表单一平均则相反，会让长序列的失败被短序列的成功掩盖，而长序列
恰恰是这件事的意义所在。

### 1.3 性能在哪条路径上测（已定）

> **决策 D4（已定）**：gate 用 **FP4-Q 路径** vs **FA4 较优者**。同时 Phase 0a
> 必须**另外记录 BF16-Q 路径的数字**。

gate 走 FP4-Q 路径是为了对应「q/k/v 都已量化」这个前提。另记一份 BF16-Q 的账是为了
防自欺：§5.4 指出 Q 量化开销目前**完全没有数**，不分开记的话，Phase 1 换合同白送的
收益会和后面真正的 kernel 改进混在一起，最后可能出现「gate 过了，但大部分是接口变更
送的」而无人值守的 agent 不会自己发现。

这个比较本身是**跨输入合同的比较**——FA4 拿 BF16 K/V，我们拿 FP4 K/V，这正是整件事
的意义。写清楚即可，但不写清楚，这个 2x 将来会被质疑。

### 1.4 「原版 FA4」是哪一个

见 §3，已定为 FA4 较优者。

## 3. 基线定义：这一步决定任务难度

`fa4_bf16` 是 `num_splits=1`；`fa4_split` 是按 FA4 自带的 `num_splits_heuristic`
选 split 数。两者在低 batch 上差距极大：`batch=1, seqlen=65536` 是 0.634 ms
对 0.051 ms，**12.3x**。

FA4 在真实 serving 里默认就会走启发式，所以「原版 FA4」的诚实定义是**带 split-K
的那一个**。按这个定义：

- 低 batch 长序列是主战场，FP4 现在慢 6–21x
- **FP4 必须实现 split-K**。即便 D3 是按 seqlen 聚合、不单独考核 `batch=1`，
  `seqlen=65536` 的几何平均仍被 `batch=1` 的 21.28x 主导，不做 split-K 那一行
  的 10.5x 拿不到

按 `fa4_bf16` 定义则回避了 split-K，但那是在跟一个真实场景下没人会用的配置比，
数字好看而无意义。

> **决策 D0（已定）**：基线取 FA4 较优者（`num_splits=1` 与启发式两者取小）。
> 这是最严格也最诚实的定义。**agent 不得自行改用 `fa4_bf16`**；确需弱化基线是
> 人的决定，不是它的（见 §6.6）。

顺带记录一个 FA4 自身的坑，benchmark 已经绕过：`flash_attn/cute/internal/interface.py:546-548`
在 `num_splits != 1 且 cu_seqlens_q is None` 时会静默把 `pack_gqa` 关掉，导致
split-K 在 GQA 下性能塌掉 4x。`tests/kernel_profile/bench_decode.py` 通过走 varlen
路径（提供 `cu_seqlens_q`）规避。**任何重测都必须保持走 varlen，否则基线会被低估。**

## 4. Roofline：2x 是否可达

FP4 的 KV 字节数是 BF16 的 `1/3.556`（`128/2 + 128/16 = 72` 字节/token/头
对 `128 × 2 = 256`，见 `1.vllm_v1_design.md` §2.2）。

高 batch 下 FA4 已经把带宽吃满：`batch=16, seqlen=65536` 达 6660 GB/s。同一格
FP4 只有 529 GB/s，全表 FP4 最好也只有 646 GB/s。

**结论：FP4 现在不是带宽受限，是每 CTA 吞吐受限。** 它只用到 FA4 所达带宽的
8–10%。

如果 FP4 变成带宽受限并达到 FA4 同等的带宽效率，它会比 FA4 快 **3.56x**——因为
搬的字节少 3.556 倍。所以 2x 这个目标**在高 batch 下位于 roofline 以内**，需要
达到 FA4 所达带宽的 **56%**。余量存在但不宽裕：3.556x 是天花板，2x 用掉其中
56%，这也是为什么目标不能再往上定——**4x 会直接超出 roofline，在带宽受限区间
物理上不可能。**

最难的一格值得单独算一遍，因为它决定 `seqlen=65536` 那条 gate 能否成立。
`batch=1, seqlen=65536`：FA4 带 split-K 是 0.0514 ms，FP4 现在 1.0941 ms。KV 字节
75.5 MB，按 FA4 在该格达到的 5.22 TB/s 计，roofline 底板是 **0.0145 ms**。所以
即便这一格要单独做到 2x（0.0257 ms），也仍在底板之上 1.78 倍——**不是物理不可能，
但要求 split-K（约 12x）与字节收益（3.556x）两条都近乎满额兑现。** 这正是 D3 取
「每 seqlen 聚合」而非「每格」的原因。

低 batch 是另一回事：那里 FA4 自己也没吃满带宽（`batch=1, seqlen=1024` 只有
287 GB/s），瓶颈是 SM 占用率而不是带宽，split-K 才是杠杆。所以：

| 区间 | 瓶颈 | 主要手段 |
|---|---|---|
| 高 batch（≥16） | 每 CTA 吞吐 | 消除冗余 CTA 与冗余 KV 流量（§5.1）；warp 布局重划分（§5.5） |
| 低 batch（1–4） | SM 占用率 | split-K + combine（§5.2） |

两个区间的手段不同，**必须分开度量**，否则一个区间的改善会掩盖另一个区间的退化。

「每 CTA 吞吐受限」这个实测结论，BitDecoding 给了对应的理论说法：**low-bit 把
kernel 从带宽受限推成计算受限，roofline 整个挪了位置，于是照搬旧 roofline 下调优
出来的 warp 布局与 tile 划分就不再成立。** 我们这里 8–10% 的带宽利用率正是这个
现象的表征。这条推论落在 §5.5。

## 5. 已知的五个结构性瓶颈

以下每条都有代码位置，不是猜测。但「有代码依据」不等于「是当前的主要瓶颈」——
**五条的优先级必须由 Phase 0b 的第一份 IKET trace 决定**（涉及流量的那条补 ncu），
不能照单全收。静态代码分析能列出嫌疑，不能排序。

### 5.1 Q 被补到 128 行，只用 1 行

```39:46:src/nvfp4_decode_kernel/_kernel.py
    query_padded_bf16 = torch.zeros(
        rows,
        128,
        query.shape[1],
        query.shape[2],
```

decode 的 query 长度是 1，却按 128 个 slot 排布。叠加 GQA 后每个 KV 头要起
`ceil(qhead_per_kvhead × 128 / 256)` 个 CTA，GQA-8 下是 4 个，意味着**同一份 KV
被读 4 遍**。这与 §4 里「带宽只用到 8–10%」是同一个现象的两面。

**关键更正：`pack_gqa` 已经是开着的。** `_decode.py:319` 无条件传 `pack_gqa=True`，
kernel 内部也确实在用（`qhead_per_kvhead_packgqa`，见 `fp4_decode_kernel.py:1218,
1902, 1921`）。所以浪费的来源**不是「没启用 pack_gqa」**——恰恰相反，pack_gqa 按
`seqlen_q × qhead_per_kvhead` 填 M 维，而这里的 `seqlen_q` 是补出来的 128 而不是
真实的 1，于是打包非但没省下什么，反而把 128 倍的空行乘进了 M 维。

要动的是 **padding 本身**，不是开关。这一条改变了 Phase 2 的着手点：不要去「加
pack_gqa」，要去掉 `_kernel.py` 的 128 行补齐，让 M 维只装真实的
`1 × qhead_per_kvhead` 行。

这个修法有已发表的形式：BitDecoding 的 **Query Transformation**，把 query 从
`[1, (g_q, h_kv)]` 重排为 `[g_q, h_kv]`，在不改变 attention 语义与 KV 共享模式的
前提下拼出一个填满 Tensor Core fragment 的 Q tile。它的出发点和我们这里一字不差：
`Q_len = 1` 会让 fragment 填不满、warp occupancy 低下。区别只在于它取 `seqlen_q = 1`
而我们取了补齐后的 128。见 `.claude/skills/bitdecoding/reference/03-porting-to-sm100.md`。

### 5.2 Split-K 关着，且不能直接打开

```318:322:src/nvfp4_decode_kernel/_decode.py
        is_split_kv=False,
        ...
        is_persistent=not has_residual,
```

kernel 里继承自 FA4 的 split-KV 骨架是在的（`_fa4/block_info.py` 的
`get_n_block_min_max` 会按 `split_idx` 切 n_block 区间），但**把 `False` 改成 `True`
不会工作**，缺四样东西：

1. **没有 combine kernel。** 各 split 的部分输出和 LSE 没有归并者。
2. **没有 partial 缓冲。** `_decode.py` 传 `mLSE=None`，partial O/LSE 无处可写。
3. **调度器不兼容。** 默认走 `StaticPersistentTileScheduler`，它把 split_idx 写死：

```220:221:src/nvfp4_decode_kernel/_fa4/tile_scheduler.py
            (Int32(block_idx), Int32(head_idx), Int32(batch_idx), Int32(0)), is_valid
        )
```

   支持 split 的是 `SingleTileScheduler` 系（`:133-139` 用 `num_splits_divmod`
   拆出 split_idx，grid 在 `:129` 乘上 `num_splits`）。换调度器会丢掉 persistent
   的收益，这个取舍要实测。

4. **residual 会被重复计入。** BF16 尾巴的融合只在
   `fp4_decode_kernel.py` 里用 `split_idx == 0` 做保护，split 路径下的正确性没有
   测试覆盖——`tests/kernel/` 里没有任何 split-K 测试，因为这条路径一直是关的。

另有一处已存在的限制：split-K + FP4 时 `kv_stage` 被压到 4
（`fp4_decode_kernel.py:352-353`），会削弱流水线深度。

### 5.3 每次调用有 host 同步

```144:145:src/nvfp4_decode_kernel/_decode.py
def _check_device_values(condition: torch.Tensor, message: str) -> None:
    if bool(torch.any(condition).item()):
```

五处调用点（`:611, 692, 697, 712, 748`）。每个 `.item()` 都是一次设备同步。这解释了
`results.json` 里 `wall_ms` 远大于 `gpu_ms` 的现象——`batch=1, seqlen=1024` 是
0.39 ms 对 0.055 ms，**7 倍**。

注意：这一项**不改善 `gpu_ms`**，只改善 wall time。如果验收只看 `gpu_ms`，它不该
排在前面；但它决定了 kernel 在真实服务里的可用性，`1.vllm_v1_design.md` §6.4 已经
把「零 host sync」列为集成前的硬合同。

### 5.4 Q 量化在调用内

`_kernel.py:47-51` 每次调用都做一次 Q 量化并分配 scratch。新合同（§1.1）直接消掉
这一项。**但它到底占多少，现在没有数**——`results.json` 的 `kernels` 字段全是空的，
per-kernel 拆分没抓到。Phase 0 必须先把这个数测出来，否则无法判断新合同本身贡献了
多少加速。

### 5.5 warp 布局是照搬 FA4 的，而 low-bit 已经把 roofline 挪了

这一条来自 BitDecoding（HPCA 2026，`.claude/skills/bitdecoding`），是本轮新增的
瓶颈，也是四条旧瓶颈里没有覆盖的维度。

核心论证：**low-bit KV 搬的字节少得多，kernel 从带宽受限变成计算受限。针对旧
roofline 调出来的 warp 布局，在新 roofline 下不再是对的。** 这与 §4 的实测结论
（FP4 只用到 FA4 所达带宽的 8–10%，是每 CTA 吞吐受限）完全同向——同一个现象，
一个是实测，一个是论文给的解释。

BitDecoding 的做法是**固定 `W_m = 1`，把 warp 全部投到 N 维**，因为 decode 的
query 长度是 1，沿 M 分 warp 等于分给空气。代码里就是
`Layout<Shape<Int<1>,_4,_1>>`，而 FA2 在同一位置写的是
`Layout<Shape<Int<kNWarps>,_1,_1>>`。

我们的 kernel 站在错误的那一边：`softmax0`/`softmax1` 各 4 个 warp，由
`stage = Int32(0 if warp_idx < self.softmax1_warp_ids[0] else 1)`（`:2094`）选择，
而 stage 轴是撑开 M 的——`cta_tiler = (q_stage × m_block_size, ...)`（`:151`）。
也就是说 **16 个 warp 里有 8 个分在了 BitDecoding 主张只该放 1 个 warp 的轴上**，
而那个轴按 §5.1 还有 127/128 是 padding。另有 1 个 warp（15 号）默认完全空转。

两点必须诚实说明，否则会把它当成显然的 bug：

- FA4 的 `q_stage = 2` 同时也是软件流水手段（ping-pong 让 softmax 与 MMA 重叠），
  它的价值不全来自 M 的长度。
- SM100 的 `tcgen05` 由单个 warp 向 TMEM 发射 MMA，不像 `mma.m16n8k16` 那样把
  MMA 平铺到多个 warp 上。所以「warp 投到 N」在这里不是一一对应的搬运，对应物是
  softmax 与 correction 的工作如何在 N tile 上分布。

因此本条可迁移的是**诊断而非补丁**：warp 预算继承自一个为不同 roofline 调优的
kernel，且有一个 warp 完全闲置。是否重分配，由 Phase 0b 的 IKET 关键路径决定。

BitDecoding 的消融给了这条路的量级和陷阱（Table III，4-bit）：

| `W_n` | 协作 softmax | 延迟 | TC 利用率 | 数值正确 |
|---:|---|---:|---:|---|
| 1 | 否 | 3.746 ms | 10.91% | 是 |
| 4 | 否 | 0.610 ms | 19.71% | **否** |
| 4 | 是 | 0.613 ms | 19.66% | 是 |

三点读法，重要性递减：拓宽 N 值 **6.1x**，是该论文里最大的单项结构收益；**中间那行
是陷阱**——只看计时是干净的大胜，结果却是错的；协作 softmax 只花 **0.5%** 就把正确性
买回来，几乎没有取舍余地。

即便修好，TC 利用率也只有 19.66%——拓宽 N 是必要而远不充分的。

还有一条 Blackwell 特有的、论文点名的停顿源：native NVFP4 消掉了反量化，但 PV
那一步要求 P 重新量化，`O = Quant(softmax(QK)) · V`。我们的 kernel 在 `quant_pv`
下正是这个形状，所以**softmax 与 PV MMA 之间应当存在一个序列化点**。这是可以
预先登记、由第一份 IKET trace 直接证伪的假设。

### 6.3 分析工具的分工：IKET 主、ncu 备

这是本次计划相对上一版最大的改动。

**为什么 IKET 是主。** §4 的结论是「FP4 不是带宽受限，是每 CTA 吞吐受限，只用到
FA4 所达带宽的 8–10%」。这句话本身就说明 ncu 的聚合计数器已经把能说的说完了——它
能告诉我们「不是带宽问题」，但说不出「那一个 CTA 内部的时间到底耗在哪」。而
decode kernel 恰好是 16 warp 的 warp-specialized persistent kernel
（`fp4_decode_kernel.py:201-209`）：

| warp | 角色 |
|---|---|
| 0–3 | softmax stage 0 |
| 4–7 | softmax stage 1 |
| 8–11 | correction |
| 12 | MMA |
| 13 | epilogue |
| 14 | TMA load |
| 15 | empty（默认配置下整个 warp 空转） |

IKET 给的正是这一层：每个 warp 角色的生命周期、各阶段耗时、**等待占比**，以及
CTA 在 SM 上的分布。CUTLASS 4.6 的 release note 对 IKET 的定位原话就是
"makes it easier to understand persistent, warp-specialized kernels' performance"。

**分工表。**

| 问题 | 工具 |
|---|---|
| 哪个 warp 角色是关键路径 | IKET |
| 生产者与消费者 warp 是重叠还是串行 | IKET |
| 某个角色多大比例的时间花在等待上 | IKET |
| CTA / SM 之间负载是否不均、grid 是否铺开 | IKET |
| 实际搬了多少 DRAM 字节（§5.1 的 4x 冗余假设） | ncu |
| occupancy 被什么限制（寄存器 / smem / warp slot） | ncu |
| L2 命中率、sector 效率、指令构成 | ncu |

一句话：**IKET 回答「时序与结构」，ncu 回答「数量与资源」。** 假设一旦涉及
「谁在等谁」「顺序对不对」，先上 IKET；只有当问题本质是「多少」时才转 ncu。

**两者不能同时跑**（都要抢 CUPTI 驱动资源），每次取证都是一趟独立的 run。这既是
约束，也是「IKET 优先」的效率理由：选错工具就白费一整轮。

**三条纪律**，违反任何一条都会让证据失效：

1. **kernel 必须在 profiling 那趟 run 里真正 JIT 编译。** 已缓存复用的 kernel 拿不到
   插桩，产出静默为空。`_decode.py` 里有编译缓存（`CLAUDE.md` Code Map 明列），
   profiling 前必须清掉或绕过。这是最常见的失败方式。
2. **插桩过的 run 绝不能用来出性能数字。** IKET 有每 kernel 的固定进出开销，还可能
   抑制展开后的指令交织。性能门槛只认干净 run 的数据。
3. **range 的两端必须在同一个 warp guard 内**，且布点保持 warp-uniform。发散的
   push/pop 会让 profiling 失败或产出错误时间线。

细节见 `.claude/skills/iket-trace/`，其中 `reference/04-pitfalls.md` 逐条列出失败
形态，`helpers/analyze_trace.py` 把 trace JSON 直接变成「角色关键路径 + 等待占比」
的结论表，不必肉眼读 Perfetto。

### 6.4 为什么这个任务适合用 RLCR

按 HAN Lab 自己的消融，Humanize 是三个组件里贡献最大的，因为它把「一堆零散尝试」
变成「plan → 实现 → 验证 → 独立 review」的纪律性循环。这个任务恰好有它擅长的两个
特征：搜索空间大（split-K 配置、调度器选择、stage 数、GQA 打包方式互相耦合），

反过来说，如果没有客观 gate，RLCR 会退化成自说自话。所以 Phase 0 必须先把度量建

### 6.5 具体怎么用

**每轮迭代的 loop 内容**固定为：

1. 从 KernelWiki 取先例，而不是凭空设计。已验证可用的查询：

```bash
cd .claude/skills/KernelWiki
python3 scripts/query.py "split-k decode attention combine kernel lse merge blackwell"
python3 scripts/query.py "pack_gqa decode attention query padding sm100"
python3 scripts/query.py --tag nvfp4 --type kernel
python3 scripts/query.py --symptom low-sm-utilization --compact
```

   实测该库对本仓库对口——检索 NVFP4 paged decode 会返回 flashinfer 的
   "Add NVFP4 KV cache quantization support for SM100"、"Support NVFP4 KV for
   prefill and batch attention kernels" 以及 flash-attention 的
   "[Cute,Fwd,Sm100] Support paged attention"。

2. 改一处，在**干净 run**（无插桩、无 profiler）上跑 `tests/kernel/`（数值 gate）
   + benchmark（性能 gate）。

3. **先取 IKET 证据**，而不是只看总时间：

```bash
V=/apdcephfs_wzc1/share_303541817/hunyuan/dayoudu/dev/BitKV_nvfp4/_local/envs/vllm-nvfp4
"$V"/bin/run-iket -o ./iket_out --clobber profile --postprocess all -- \
  "$V"/bin/python tests/kernel_profile/bench_decode.py --single-case ...

"$V"/bin/python .claude/skills/iket-trace/helpers/analyze_trace.py \
  ./iket_out/*.trace.json \
  --roles "0-3=softmax0,4-7=softmax1,8-11=corr,12=mma,13=epi,14=load,15=empty"
```

   要回答的是：**关键路径的 warp 角色变了吗？该角色的等待占比降了吗？**

4. **只有当 IKET 答不了时才转 ncu**——也就是问题落在「多少字节 / 多少占用率 / 缓存
   命中」这类量的维度上。metric 名以
   `.claude/skills/ncu-report-skill/reference/08-b200-metric-names.md` 为准，
   诊断路径见同目录 `06-diagnosis-playbook.md`。转 ncu 时要在轮次记录里写明
   「IKET 无法回答的原因」，避免循环退化成两个 profiler 都跑一遍。

   **每一轮都要能回答「瓶颈从 A 变成 B 了吗」，只报 wall time 变化的轮次视为无效
   轮次。**

5. 记录候选、结果、失败分支。失败分支必须留下，否则循环会反复走回头路。

**每个 Phase 开始时**用 `humanize-gen-plan` 把该 Phase 的目标转成带验收条件的
可执行 plan；Phase 内每轮仍按 RLCR 的工件和门控推进。独立 review 使用 §6.2
规定的内部 sub-agent reviewer，禁止触发外部 `codex exec` / `codex review`。

### 6.6 无人值守执行纪律

本计划由后台 agent 长时间无人值守执行，以下六条是硬性约束。它们解决的不是「怎么
优化得更好」，而是「跑砸了怎么不把事情搞坏、卡住了怎么不空转到天亮」。

**1. 专用分支。** 在 `perf/fp4-decode-2x` 上跑，不直接动 `main`。起步前工作区必须
干净——`.claude/`、`docs/tasks/`、`tests/kernel_profile/` 这些当前未提交的文件要先
落盘成 commit。否则 agent 一旦用 `git checkout` / `git stash` 做回滚恢复，**可能把
它自己要读的计划文档和 skills 一起清掉。**

**2. 每个 Phase 以一个「`tests/kernel` 绿的 commit」结束。** 某一轮把测试跑红且当轮
修不好，revert 那一轮，不带着红继续。

这是「最终代码必须过 `tests/kernel`」唯一可靠的落地方式。只在收口时跑一次是不够
的：无人值守几十轮之后，若中间某轮引入了静默数值错误，排查等于要在几十个 commit
里做二分——而 §5.2 已经点名 split-K 的 residual 双计正是「静默数值错误，最难查」
那一类。每轮都绿，等于把二分范围永远压在一轮之内。全量 46 个测试 54 秒，每轮跑得起。

**3. 轮次预算：每个 Phase 上限 10 轮或 2 小时，先到为准。**

**4. 打不过 gate 时：不放宽，提交最后一个绿的状态，把失败原因与已排除的分支写进
日志，继续下一个 Phase。** 这些 Phase 大体正交——去 padding、split-K、host sync
清理互不依赖，一个卡住不该连坐其余。最差结局也是「部分收益 + 一份说明哪条路走不通
的记录」，而不是「什么都没有」。

**唯一例外是 Phase 1**：它是新合同的落地，后面所有测量都在它上面做。Phase 1 失败
就整体停下等人，继续下去测出来的数没有意义。

**5. agent 不得自行放宽任何 gate**，性能的和数值的都不行，也不得更换 D0 基线。
§8.2 原本只约束了数值门槛，但卡住时最自然的「解法」恰恰是放宽性能门槛。放宽是人的
决定。

**6. 两层 gate，不要混淆。**

| 层级 | 检查什么 | 何时 |
|---|---|---|
| Phase 级 | 不退化，且改善可归因到本 Phase 的改动 | 每个 Phase 收尾 |
| 最终级 | §8.1 的每 seqlen 2x | 只在 Phase 5 |

每个 Phase **开工前先写下预期倍数和推导依据**（例：Phase 2 去掉 padding，GQA-8 下
冗余 CTA 是 4 倍，故预期 2–4x），收工时拿实测对照。实测远低于预期**不直接判失败**，
但必须触发一次原因分析——那通常意味着瓶颈判断错了。

预期由 agent 自己推而不是本文给死数，是因为预期本身就是可证伪的假设，写下来才能在
事后暴露判断错误；预先拍死的数字反而会变成凑指标的目标。

混淆两层的后果是双向的：把 §8.1 的 2x 当成 Phase 级门槛，Phase 2 拿到 4x 也会被判
失败，按第 4 条触发「记录并跳过」，**白白丢掉一个本来成功的 Phase**；反过来只要
「有提升」就算过，则 0.5% 的改善也会被带进下一个 Phase。

## 7. 分阶段计划

排序原则：**先把度量建牢，再动 kernel；最高不确定性的东西排最前。**

### Phase 0 — 度量基建（不改 kernel 算法）

没有可信的度量，后面所有轮次都是盲跑。本 Phase 分两半：benchmark 侧和 IKET 侧。

#### 0a. Benchmark 侧

- **补齐 `batch=64/128 × seqlen=65536` 两格**：把 `--max-kv-tokens` 从默认
  2,200,000 提到 ≥8,400,000。这两格不是跑不下（BF16 KV 32 GiB，卡上 191.5 GB），
  是被这个旋钮挡掉的。前提要实测确认：若 bench 同时给四个 variant 分配输入，峰值
  可能到 60–70 GiB，仍在容量内但不要假定。**这一步必须先于任何门槛判定**，它把
  `seqlen=65536` 的 gate 从 15.7x 降到约 10.5x
- 修好 per-kernel 拆分：`results.json` 的 `kernels` 字段目前全空，
  拿不到 Q 量化 / attention / epilogue 的分项耗时
- 把 §5.4 的 Q 量化占比测出来
- **同时记录 FP4-Q 路径与 BF16-Q 路径两个数字**（D4）。gate 认前者，后者用来随时
  拆开「接口变更白送的」与「kernel 真改出来的」两笔账
- 扩展 grid：至少加 `batch ∈ {2, 8, 32}`，以及 GQA 之外的 MHA/MQA 各一组
  （目标说的是「任意 batch, seq_len」，只测 GQA-8 覆盖不了）
- 输出：几何平均 + 最差单点，两个数一起报
- 固化基线定义（D0），把 FA4 的 `num_splits` 记进结果
- **给结果加 provenance**：env 路径、python / cutlass / flash-attn 版本、GPU 型号、
  commit。现在 `results.json` 是个裸 list，什么都没记；这次靠「torch-base 没装
  flash-attn」才反推出它是哪个环境跑的，纯属侥幸。RLCR 会产出几十轮数据，没有
  provenance 就无法回溯。

#### 0b. IKET 侧

> **先做 go/no-go，预算 2 轮。** IKET 目前只在一个 64 线程、2 block 的玩具 kernel
> 上验证过（`/tmp/iket_smoke/smoke.py`），**从未跑过 `fp4_decode_kernel.py`**——
> 一个 4700 行、16 warp 特化、带 TMA/UMMA/TMEM 三级流水的持久化 kernel。两者之间
> 隔着几类已知会出问题的东西：16 warp × 长序列的事件量可能撑爆 buffer、marker 必须
> 落在 warp-uniform 位置（本 kernel 满屏 `if warp_idx == ...` 分支）、以及与 mbarrier
> 流水同步的相互干扰。
>
> **过了**，按下文 IKET 主、ncu 备执行。**没过**，主备顺序对调：ncu 转正，§8.3
> 的证据要求改成「IKET 或 ncu」。
>
> 这一步存在的理由是 §8.3 写了「无核内证据的轮次视为无效」。若 IKET 在真实 kernel
> 上跑不通而不设退路，**这条规则会把整个循环锁死**——每轮都无效，agent 空转到预算
> 耗尽。方法论不该有单点故障，尤其是无人值守。

- 给 `fp4_decode_kernel.py` 的 `@cute.kernel`（`:1495`）按 §6.3 的角色表加**粗粒度**
  插桩：每个角色一个 lifetime range，加 3–5 个阶段 range，**重点包住等待点**
  （pipeline acquire / mbarrier wait），因为等待占比才是判断「谁饿着谁」的依据
- 唯一名字数控制在 30 以内，单名 ≤ 32 字符
- 解决编译缓存：确认 profiling 时 kernel 确实重新 JIT，否则 trace 静默为空
- 采一条基线 trace 存档，作为后续所有轮次的对照

插桩本身**不改变 kernel 语义、也不改变干净 run 的产物**：IKET 调用在未开启 lowering
时被编译器完全剥离，不往最终 kernel 里加任何代码。这是 D1 成立的前提。

> **决策 D1（已定）**：marker 永久留在 kernel 源码里。
>
> 零成本由上述剥离机制保证，而每轮重新插桩既费时又容易插错位置，导致轮次之间的
> trace 不可比。
>
> **绑定条件：插桩后的 kernel 必须仍然过 `tests/kernel`。** 编译不过或数值变了，
> revert 插桩本身，而不是改测试。这样 D1 不会和 §6.6 第 2 条打架。
>
> 与 `CLAUDE.md` 规则 7（「不加实验性环境开关、诊断硬编码、调试 dump 路径」）的
> 张力是已知的：IKET marker 形式上属于诊断插桩。豁免理由是它更接近 NVTX 那类永久
> 标注而非临时 dump，且零开销、零语义影响。合入时在 `CLAUDE.md` 补一句显式豁免。

**验收**：
- 同一配置重跑三次，几何平均波动 < 3%。达不到就先解决计时噪声，否则后面分不清
  「改善了」和「抖动」
- `analyze_trace.py` 能在真实 decode kernel 上产出非空的角色表，且 `malformed_ranges`
  为 0
- 基线 trace 给出**当前关键路径的 warp 角色**——这是 Phase 2 的起点假设，也是第一次
  用证据而非推测来定位瓶颈

### Phase 1 — 新输入合同（q_fp4 直通）

按 D2 实现单入口双路径。这是目标的前提，也是最便宜的一笔收益。

本 Phase 的新 FP4-Q 路径先覆盖纯 FP4、页对齐输入；不要求同时支持 BF16 residual。
BF16-Q 旧路径的 residual 行为仍由现有测试保护。FP4-Q + residual 在 Phase 5 性能
达标后单独实现。

**本 Phase 是唯一「失败即整体停下」的 Phase**（§6.6 第 4 条）：后面所有测量都在
新合同上做，它不成立则后续数字没有意义。

**验收**：
- 与现有 BF16-Q 路径在同一份输入上数值一致（先用现有 quantizer 产生 `q_fp4`，
  再喂新入口，结果应与旧路径逐字节相等）
- **`tests/kernel/` 新增 FP4-Q 入口的数值测试**（D2 的绑定要求）。不加的话新入口
  没有任何 gate，而它正是性能目标所在的路径
- FP4-Q 新测试本 Phase 覆盖 `len % 128 == 0` 的纯 FP4 路径；residual 组合暂不作为
  Phase 1 成败条件
- `tests/kernel/` 全绿（含新增用例）
- 记录加速幅度，FP4-Q 与 BF16-Q 两条路径分别记——这是后续所有 Phase 的新起点

### Phase 2 — 高 batch：消除冗余 CTA 与冗余 KV 流量

对应 §5.1。目标区间 `batch ≥ 16`，那里瓶颈是每 CTA 吞吐。

取证分两层，**先 IKET 后 ncu**：

1. **IKET 先答结构问题**，且不需要计数器。trace 的 launch 记录直接给出 `gridDim`，
   `locationTable` 给出实际跑起来的 CTA 与 SM 分布。「每个 KV 头起 4 个 CTA」这个
   断言看 grid 就能证实或证伪。同时看 load warp（14）是不是关键路径、它的等待占比
   多少——如果 load 角色饱和而 MMA 角色大量空等，冗余流量假设就成立。
2. **ncu 只用来定量**：把冗余量化成字节。预期表现为 L2/DRAM 流量约为理论 KV 字节数
   的 4x。这一步 IKET 答不了，因为它没有任何流量计数器。

假设不成立就回到 IKET 的角色表重新定位，而不是硬推原方案。

按 §5.1 的更正，本 Phase 的着手点是**去掉 Q 的 128 行 padding**，不是启用
`pack_gqa`（它本来就开着）。改动会波及 `_kernel.py` 的缓冲分配、`_decode.py` 的
布局适配、以及 kernel 内 `seqlen_q_static` 的取法
（`fp4_decode_kernel.py:1906`）——比「翻一个开关」大得多，排期要按这个体量估。

**验收**：`batch ≥ 16` 区间几何平均相对 Phase 1 提升；IKET 上关键路径角色的等待
占比下降；ncu 实测 DRAM 流量接近理论 KV 字节数。数值门槛不变。

### Phase 2b — warp 布局重划分

对应 §5.5。**前置条件：Phase 0b 的 IKET trace 显示 softmax 或 correction 角色确实
占据关键路径。** 如果关键路径在 load 或 MMA 上，本 Phase 直接跳过——不要因为论文
说得有道理就动手，那正是 §6.3 要杜绝的无证据轮次。

本 Phase 受 BitDecoding 启发最深，因此重申 §6.2 的定性：**那是知识库不是规范。**
`W_m=1 / W_n=4` 是 SM80/SM90 上 `mma.m16n8k16` 的结论，SM100 的 `tcgen05` 由单
warp 发射 MMA，不存在同构的搬运。可借用的是「decode 场景下 M 轴不值得分 warp」
这个判断和 6.1x 的量级预期，具体改法必须自己按 IKET 证据推。

排在 Phase 2 之后有个实际理由：Phase 2 去掉 Q padding 之后，M 轴才真的只剩
`g_q` 行，此时「8 个 warp 分在 M 上」的浪费才完全暴露，重划分的收益也才好度量。
顺序反过来会把两件事的效果搅在一起。

分两步，中间可验证：

1. **先只回收空转的 warp 15**，这是最小改动、无正确性风险的一步，用来校准「多一个
   warp 值多少」。
2. **再动 softmax 的 stage 划分**。一旦 softmax 的行被拆到多个 warp 上，就必须同时
   引入跨 warp 归约（BitDecoding 的 `sTMP`）和 P 的 smem 中转（`sAcc`），否则
   rowmax 不完整、P 的分布也对不上 PV MMA 的 operand 布局。

**验收**：
- IKET 上关键路径角色的等待占比下降，且 16 个 warp 的 lifetime 离散度收窄
- **数值 gate 必须与性能 gate 同轮跑**——这是本 Phase 的硬性要求，理由见下
- 全表不退化，包括低 batch

> **本 Phase 最大的风险是「快而错」。** BitDecoding Table III 的中间行记录了这个
> 陷阱：拓宽 N 但不加协作 softmax，延迟从 3.746 ms 降到 0.610 ms（6.1x），TC 利用率
> 从 10.91% 升到 19.71%，**结果是错的**。任何只看性能的门槛都会把它判为大胜并合入。
> 所以本 Phase 不接受「先记下来后面修数值」的轮次。

### Phase 3 — 低 batch：split-K + combine

对应 §5.2，四个缺失件都要补齐。这是全计划风险最高的一步，因为它同时涉及调度器
更换、新 kernel、以及 residual 语义。

分两步走，中间可验证：

1. **先不带 residual 的纯 FP4 split-K**：partial 缓冲 + combine kernel + 调度器
   切换。此时 residual 双计问题不存在。
2. **再融合 residual**：`split_idx == 0` 的保护需要在 split 路径下重新论证并测试。

调度器取舍（§5.2 第 3 点）正好是 IKET 的强项：换掉 persistent 之后，CTA 在 SM 上
的分布、每个 CTA 的 lifetime、以及尾部效应都能从 trace 的 `locationTable` 与
`warpLifetimes` 直接读出来，不必靠总时间反推。低 batch 下「split-K 是否真的把 SM
铺开了」也是同一份数据回答的。

**验收**：
- 新增 split-K 的数值测试（目前 `tests/kernel/` 完全没有）
- **零长度 residual 语义必须保持**：`seqused_residual == 0` 的行贡献恰好为零，
  包括在混合 batch 里（`CLAUDE.md` 明确要求）
- `batch ∈ {1, 4}` 区间相对 FA4 较优者的比值显著下降
- IKET 上低 batch 的 `sms_used` 显著上升，且 CTA lifetime 的离散度没有恶化
  （split 之间负载不均会吃掉 split-K 的收益）
- persistent 调度器换掉之后，高 batch 区间**不得退化**——这是本 Phase 最容易踩的
  坑，必须每轮都跑全表而不只跑低 batch

### Phase 4 — Host sync 清理

对应 §5.3。提供 trusted-metadata fast path，与 `1.vllm_v1_design.md` §10.3 里
S7 规划的 `trusted_metadata: bool = False` 接口对齐，避免两处各做一套。

**验收**：steady-state 下 `aten::_local_scalar_dense` 计数为 0；
`wall_ms / gpu_ms` 比值接近 1。

### Phase 5 — 收口

全表重测（**干净 run**，不带插桩），按 D3 出**每个 seqlen 的几何平均**，对照 D0
基线判定是否达标。这是全流程唯一一次检查最终门槛（§6.6 第 6 条）。

未达标的 seqlen 逐个给出证据与结论——优先 IKET 的角色表，量的问题补 ncu，不做
「全表平均达标就算过」的模糊处理。

**没到 2x 怎么办**：用 Phase 0a 实测的带宽重算一次 roofline，给出「还差多少、剩余
余量在哪、下一步该动什么」，然后**停下等人**。不继续循环，不放宽门槛。这与 §10 里
D0 那条风险的处理方式一致，也是 §6.6 第 5 条的必然结果。

### Phase 6 — 达标后补 FP4-Q + BF16 residual

residual tail，补齐混合 batch、零长度 residual、非满 residual 长度与 direct scatter

### Phase 7 — 上限探针之后的两条并行调查

Phase 5b 判 FAIL 之后，`tests/kernel_profile/probe_softmax_ceiling.py`
量出了「softmax 算术为零」时的 kernel-only 上限（`docs/perf/phase7/`）。结论把剩余
工作切成了三块，其中两块与 softmax 无关：

| seqlen | production vs FA4 | 上限 vs FA4 |
|---:|---:|---:|
| 1024 | 2.603x 慢 | 1.930x 慢 |
| 4096 | 1.436x 慢 | 1.41x 快 |
| 16384 | 1.321x 慢 | 2.19x 快 |
| 65536 | 1.353x 慢 | 2.37x 快 |

转置 S（把 KV 位置搬到 lane 轴）在 16384 与 65536 上足以过 D3，在 1024 与 4096 上
**无论实现得多好都不够**。所以在动手写转置之前，先把两条独立的路查清楚。

**Track A — 短序列的 GPU 侧地板（已完成，见 `docs/perf/phase7/track-a-short-seqlen-floor.md`）。**
地板是**输出存储，不是流水线**。`b1 s1024` 的 40.5 us 拆成：epilogue 19.7 us（49%）、
主循环 16.0 us、launch 与 drain 4.8 us、combine 0。`epilogue_s2g` 在
`seqlen_q_static_one` 下走非 TMA 分支，跑在**单个只有 24 个寄存器的 warp**上，却把
整块 128×128 输出物化成每线程 512 值的 fragment，为写 8 KB 输出产生 2.16 MB 的
寄存器溢出。把存储限制到 decode 真能产出的那几行后，`b1 s1024` 从 40.5 降到
20.8 us，**输出逐位相同**，且在 split 路径上每次 launch 稳定省 3.1–3.3 us。
「persistent scheduler 有独立开销」和「`q_stage=2` 是 2x 浪费」两个假设都被证伪——
它们是同一个 epilogue 缺陷的杠杆，不是独立问题。

**Track B — softmax 免费之后的带宽余量（已完成，见 `docs/perf/phase7/track-b-bandwidth-headroom.md`）。**
真实 HBM 读取上限是 7.58 TB/s。`q_stage=1`（decode 下 `seqlen_q=1`，第二个 Q stage
全是死工作）把最优形状推到 6.90 TB/s，此后 kernel 不再受带宽约束，绑定项变成每
n_block 378 ns 的流水线代价。`n_block` 增大等结构参数在此之后收益有限。另记一笔：
按单个 KV 头访问时有 3.7x 的 layout 惩罚，源于跨步访存。

**Track C — host 派发开销（已完成，见 `docs/perf/phase7/track-c-host-dispatch.md`）。**
结论超出了原本的范围，因此单列：**§8.1 的 gate 一直用 CUDA event 计 eager 模式时间，
而那个时间里有很大一部分是 Python 派发。** eager 下 FP4 每次调用约 90 us 的 host
开销，FA4 约 43 到 55 us，两边不对称且随 split 路径的选择而变。把两边都放进 CUDA
graph（decode 在真实服务里本来就跑 graph）重测，每个 seqlen 的几何平均变成：

| seqlen | event 比值（旧读数） | graph 比值（真实） |
|---:|---:|---:|
| 1024 | 1.426 | **2.618** |
| 4096 | 1.851 | **1.352** |
| 16384 | 1.451 | **1.192** |
| 65536 | 1.293 | **1.290** |

**这条修正把 Track A 顶到第一优先级**：按旧读数 s1024 最接近达标，按真实读数它是唯一
差出 2 倍以上的。另外 `b1 s16384` 的真实比值是 0.931，已经比 FA4 快。

**D9 已拍板：gate 改用 graph replay**（见 §8.1）。event 读数不再作为验收依据。

**Track C 的旁支：split 护栏标定错误**（`docs/perf/phase7/split-guard-miscalibration.md`）。
`_decode.py:59` 的 `min_pages_per_split = 8` 是按「1K 上下文因 combine launch 慢
1.7x」标定的，而那 1.7x 是 combine 路径约 34 us 的 **Python 派发**，GPU 上的 combine
只有 3.7 us。护栏挡住的是 host 开销，代价是 GPU 占用率：

| 形状 | 启发式选 | 耗时 | 实测最优 | 耗时 | 提升 |
|:--|---:|---:|---:|---:|---:|
| b1 s1024 | 1 | 42.1 us | 8 | **10.4 us** | 4.05x |
| b4 s1024 | 1 | 43.3 us | 4 | **12.5 us** | 3.46x |
| b16 s1024 | 1 | 43.8 us | 2 | **28.8 us** | 1.52x |
| b1 s4096 | 4 | 22.7 us | 16 | **12.6 us** | 1.80x |

Track A 交叉验证了这一点，但对成因的解读不同，且 Track A 的证据更强：seqlen 128 时
占用率同样是 8 个 CTA、主循环只有八分之一长，production 仍要 26.5 us，而 epilogue
修好后同形状只要 6.8 us。**所以护栏挡住的收益里，有很大一部分其实是「分了 split 就
走上一条 epilogue 不溢出的代码路径」，而不是占用率本身。** 两个修法叠加后护栏仍值得
放松，但只在低 batch：epilogue 修好后 `b16 s1024` 上任何 split 数都比不分更差。

`_kernel.py:113` 那次「结果被丢弃」的校验经复核**不是缺陷**——它是 `validate_only=True`
的故意调用，用来在派发到 split 实现前保住单一公共入口的完整契约检查。它只是把整套
shape/dtype 校验在 host 上跑了两遍。gate 改 graph 之后这笔开销不再计入（见 D11）。

**共享资源纪律**：只有 GPU 1 锁了频（`nvidia-smi -lgc 1965`，负载下 1845 MHz），
其余卡未锁，不得擅自更改。任何计时测量必须持 `flock /tmp/nvfp4_gpu1.lock`
串行执行，否则两条 Track 会互相污染。编译一律带 `CUTE_DSL_CACHE_ENABLED=0`。

### Phase 8 — 四个杠杆，按依赖顺序落地

三个 Track 汇总后，剩余工作是四个杠杆。**顺序不是工程洁癖：其余三个杠杆的实测值
全部是在 epilogue 缺陷仍在的前提下量的，epilogue 一修，它们的边际价值都要重算。**

**D13（长上下文优先）改变了杠杆之间的排序。** 门槛只覆盖 16k 以上之后：

- **split 护栏（8.3）几乎失去意义**，全部收益在 `b1–b8 s1024`——低 batch 短序列时
  CTA 铺不满。16k 以上本来就走 split 路径。降为可选。
- **`q_stage=1`（8.4）与方案 2（8.5）是主线。** Track B 的 1.30–1.36x 是在 65536 上
  量的，方案 2 的 2.07–2.14x 是在 16384 上量的，两者在 `b32 s16384` 叠到 3.02x。
- **epilogue（8.1，已落地）在长上下文里贡献很小**，每次 launch 固定省 3.1–3.3 us，
  `b8 s16384` 只有 1.03x。它值得做是因为逐位安全，不是长上下文的答案。

因此实际执行顺序是 8.1 → 8.2 → **8.4 → 8.5** → 8.3（可选）。

**8.1 Epilogue（独立 commit，只碰 `src/`）。** 两个旋钮都装：

- *逐行分段搬运*（`fp4_decode_kernel.py:4391-4392`）。这一行在 `pack_gqa` 分支
  **之外**，所以它同时压在 BF16 residual 和 direct-scatter 两条 Track A 没测的
  路径上。单开它 `b1 s1024` 到 23.18 us，溢出流量降 53 倍。
- *行数上界*（同一调用点 + `_fa4/pack_gqa.py:126-166` 加一个可选 constexpr 行界）。
  `seqlen_q_static_one` + PackGQA 下可达行数就是编译期常量 `qhead_per_kvhead`，
  行循环上界与死 Q stage 的跳过都是 constexpr，不引入任何动态分支。单开它到
  20.81 us。

两者合计 20.84 us，与单开行数上界同速。**仍然两个都装**，因为单开行数上界之所以够
快是靠编译器把那块死 fragment 消掉——那是运气不是结构性保证，且不覆盖 residual 与
scatter。

验收：`tests/kernel` 全绿，**外加在纯 FP4 / BF16 residual / direct scatter /
indexed rows 四条形态上逐位对比修改前后，`max_abs_diff` 必须为 0**。不把逐位对比
固化成常驻回归测试——那需要在 production 里留一个能实例化旧 epilogue 的开关，违反
`CLAUDE.md` 规则 7。

**8.2 全网格 graph 重测。** 后续所有判断以这份读数为准。

**8.3 Split 启发式（D13 之后降为可选）。** 换成占用率公式，形式向 FA4 的
`min(num_SMs // total_mblocks, max_splits, num_n_blocks)` 看齐。这个公式在我们自己
的实测表上逐点命中最优（b1→8、b4→4、b8→2、b16→1），不是拿实测拟合出来的。保留一个
远小于现在的页数下限，因为我们的 combine 要 2.3–3.9 us 而 FA4 更便宜；现有的
`splits * 8 <= max_pages_per_row` 太严，s1024 只有 8 页时只允许 `splits == 1`。

**8.4 `q_stage=1`。** 按占用率条件开启，判据与 8.3 共用同一个量。机器跑满时值
1.30–1.36x，低占用率时是负收益。**先查清 `b128 s1024` 上 cosine 从 0.9875 到 0.9868
的偏移再合入**——疑似 `fp4_decode_kernel.py:3198` 那条 `q_stage==1` 专属的 SFQ TMEM
路径，不是噪声。

Track A 曾担心 `q_stage=1` 会让 softmax warp 4–7 空闲、应与 warp 重划分一起决定。
这个顾虑不成立：`warp_id % 4` 同时决定 TMEM lane 组和 SMSP，w0/w4 落在同一个 SMSP
上共用那 4 ops/clk 的 MUFU，让 warp 4–7 也做 softmax 拿不到任何 `exp2` 吞吐。

**8.5 方案 2（Q 复制）go/no-go。** 判据：8.2 重测后仍有 seqlen 距 0.5 差过 1.3x
则动手。两个必须先知道的事实：

- **收益与 GQA 比例强相关。** 浪费倍数是 `128 / qhead_per_kvhead`，所以 MHA 8:8
  收益最大、GQA 32:8（实测 2.07–2.14x）居中、**MQA 32:1 只浪费 4 倍，几乎拿不到**。
- **它会二次改动 epilogue。** 真实输出行变成 32 个拷贝行之和，要重写 8.1 刚定下的
  行边界。

探针（`tests/kernel_profile/probe_qreplicate.py`）未建模 Q 复制进 SMEM 与 O 的
32→1 归约，两者都是 per-CTA，所以 2.07x 偏乐观但估计偏得不多。

### Phase 8 的余量评估：刚好压线，没有富余

把四个杠杆的实测值乘起来，s16384 落在 **0.503**——擦着过。而且这个数字是把 b32 测到
的 3.02x 外推到所有 batch 得出的，Track B 已显示 `q_stage=1` 在 b4 上是负收益。
**如果 3.02x 只在机器跑满时成立，s16384 就过不了线。**

有一格几乎物理上过不去：`b1 s16384` 现在 22.7 us，其中约 4.8 us 是 launch/prologue/
drain，要到 0.5 得压到 12.2 us，意味着除 launch 外的全部工作只剩 7.4 us，而 Track A
实测 FA4 自己在单 n_block 时的地板就是 6.33 us。

s1024 那 5.24x 靠的是低 batch 吃 split（2.3x）、高 batch 吃方案 2（约 1.6x），两者
不在同一格里，只能靠几何均值把它们混起来才够。

**未达标时的处置（D12）**：四个杠杆全部落地后若仍未达标，交逐格表加剩余差距的归因，
**停下等人拍板，不自行继续磨新杠杆，也不自行放松门槛**。

## 8. 验收门槛

### 8.1 性能

| 门槛 | 值 |
|---|---|
| **每个 seqlen 的几何平均**（在 batch 上聚合，vs D0 基线） | ≤ 0.5（即快 2x） |
| 设门槛的 seqlen | **{16384, 32768, 65536, 131072}** |
| 只报告不设门槛的 seqlen | {1024, 4096} |
| 计时方式 | **CUDA graph replay**，两边同法（D9） |
| 覆盖 | batch ∈ {1,2,4,8,16,32,64,128}，含 MHA/GQA/MQA |
| 报告项 | 每 seqlen 的几何平均、全表几何平均、最差单点（后两者只报告不设门槛） |

计时方式是 graph replay 而非 eager CUDA event，理由见 Phase 7 Track C：eager 读数
里 FP4 每次调用约 90 us、FA4 约 43–55 us 是 Python 派发，两边不对称，比值因此既非
kernel 性能也非端到端性能。decode 在真实服务里本来就跑在 graph 里。

graph replay 下的 Phase 7 基线（`docs/perf/phase7/graph-gate.json`，epilogue 修复
之前）与到 0.5 的缺口。修复之后的读数见 `docs/perf/phase8/`：

| seqlen | 几何平均 | 需要的加速 | 是否设门槛 |
|---:|---:|---:|:--|
| 1024 | 2.618 | 5.24x | 否 |
| 4096 | 1.352 | 2.70x | 否 |
| 16384 | 1.192 | 2.38x | 是 |
| 65536 | 1.290 | 2.58x | 是 |

**按 seqlen 分别设门槛，是这张表的要害。** 只设一个全表几何平均，就可以靠短序列的
大幅改善掩盖长序列的失败，而长序列低 batch 恰恰是 §3 认定的主战场。反过来若逐格
设 2x，`batch=1, seqlen=65536` 单格需要 42.6x（§4），与 roofline 几乎持平，会让
agent 在一个格子上耗尽全部预算。

最差单点仍然要报，但**不设门槛**——它是诊断信息，不是验收条件。

`CLAUDE.md` 已明确：「Current numerical gates are defined in the test file;
do not relax them to hide a kernel regression.」

- `tests/kernel/` 全部通过

- 零长度 residual 语义不变
- `query_row_indices` 行为不变

**性能轮次里如果数值门槛红了，那一轮作废，不是「先记下来后面修」。**

| 风险 | 影响 | 缓解 |

### Phase 10 — 转置落地，D3 达标

D10 当时判「转置不做、由方案 2 取代」。方案 2 走到第二步被 PTX §9.7.17.2.3.1 挡住：
`tcgen05.ld` 交给一个线程的是一整行，列的选择是 warp 一致的，所以复制 Q 最多把每
线程的 `exp2` 减半，拿不到需要的 32 倍。转置随即恢复执行，落地后 D10 作废。

转置把 S 存成 (kv 位置, 查询行)：线程持有 kv 位置，只跑 `qhead_per_kvhead` 次
`exp2` 而不是一整行 key。s16384 的 graph 几何平均从 1.097 到 0.620。代价是行最大值
变成跨线程归约，P 因 `OperandSource` 只选 A 的来源而从 TMEM 挪到 SMEM。

落地过程中最贵的一课与数值无关：`self.transpose_s` 一度写成 16 项 `and` 链。DSL 的
预处理把每个短路算符改写成携带后续代码副本的嵌套条件，于是这个函数的 AST 从 1.4 万
节点涨到 400 万以上，预处理从 0.01 秒变成十分钟以上。改成 `all([...])` 即恢复。短路
同时掩盖了一处 `self.use_block_sparsity` 的提前读取——那个属性要到一千行之后才赋值，
也就是说这个判定从来没有真正成立过。**在 traced 函数里不要用长 `and` 链。**

0.620 到 0.5 的路径由探针定夺，不靠推断。把 softmax 的算术整段删掉、保留全部 barrier
与流水线握手，量出这一版的上限是 **0.331**；再逐项关掉，得到归因：

| 关掉的部分 | s16384 几何平均 | 该项代价 |
|:--|---:|---:|
| 无（完整转置） | 0.620 | — |
| 跨 warp barrier 与 SMEM 往返 | 0.586 | 0.034 |
| P 的量化打包整段 | 0.447 | 0.173 |
| softmax 全部算术 | 0.331 | 0.289 |

P 那一项里真正贵的不是 shuffle 而是两条指令选择：组最大值本可从行最大值蝶形的中间级
取出（`exp2` 单调，组内最大的指数就是最大分数的指数），以及归一化用的是精确除法而非
近似倒数——P 只有三位尾数，除数还是被除数取不到的上界。三项微调把 0.620 推到 0.503。

最后一段来自结构而非指令：decode 只有一个 Q tile，第二个 softmax warpgroup 整个
kernel 空转。转置之后每线程代价正比于它持有的查询行数，于是把行对半分给两个
warpgroup。两组本就互不干涉——列、P 的行、scale 的条目都不相交——只有归约暂存区和
具名 barrier 需要各自一份，暂存区按「warp 数 × 每组行数」定尺寸后总量不变。

**D3 达标**（graph 几何平均，`docs/perf/phase10/graph-gate-long.json`）：

| seqlen | Phase 8 | 转置 | +指令 | +行拆分 | vs FA4 |
|---:|---:|---:|---:|---:|---:|
| 16384 | 1.083 | 0.620 | 0.515 | **0.479** | 2.09x |
| 32768 | — | — | 0.503 | **0.475** | 2.11x |
| 65536 | — | — | 0.516 | **0.464** | 2.16x |
| 131072 | — | — | 0.493 | **0.470** | 2.13x |

`tests/kernel` 58 项全绿；七个形状与非转置路径 `cos=1.000000`，对 BF16 参考的距离一致。

剩余余量在 0.470 与 0.331 之间，仍是 softmax：每 KV 块一次的跨 warp barrier（0.034）、
5 步蝶形、以及 P 走 SMEM 后 PV 无法中途流水（`gemm_ptx_partial_fp4` 的 SMEM-A 路径
断言 `mbar_ptr is None`）。b16 在四个 seqlen 里有三个是最差的一档，指向波次量化而非
softmax，是与本条正交的下一个杠杆。

#### 门槛之外的覆盖面（同一日实测，graph 几何平均）

D3 只约束「纯 FP4 + 预量化 Q + GQA 32:8 + 四个长 seqlen」。其余形状一并测了：

| 配置 | 比值 | 说明 |
|:--|---:|:--|
| s1024 / s4096（D13 已放弃的短序列） | 0.504 / 0.488 | 意外一并达标 |
| MHA 32:32 @16k | 0.418 | `R=1`，每线程最省，最快 |
| **MQA 32:1 @16k** | **0.858** | `R=32`，转置最不占便宜的形状 |
| BF16-Q 入口（调用内量化 Q）@16k | 0.600 | 多一次独立的量化 launch |
| **混合路径（fused residual）@16k / @65536** | **3.524 / 3.447** | 转置判定显式排除 |

后两项不是本轮引入。混合路径在转置之前的 `b11dfa8` 上逐格相同（s16384 同为 3.524），
是既有缺陷；其额外开销随 seqlen 线性增长（s16384 +229 us，s65536 +838 us），形状不像
一页 residual 应有的代价，值得单独查。MQA 则是转置本身的结构后果：每线程持有
`qhead_per_kvhead` 个查询行，`R=32` 时行拆分只减到 16，仍远多于 GQA 的 2。
