# NVFP4 Block Scale 的 4/6 自适应选择

## 1. 目标

把 block scale 的取法从固定的 `amax / 6` 改成按每 16 元素一组、以 MSE 为准在
`amax / 6` 和 `amax / 4` 之间自适应选择，作用于 K、V、Q 三处量化点。解码路径
和 MMA 完全不动。

配套的校准侧工作在
`BitKV_nvfp4/docs/tasks/6.kv_smoothing_calibration.md`，两份计划互为前后依赖，
见第 7 节。

## 2. 原理

### 2.1 E2M1 网格与两个候选 scale

E2M1 可表示的幅值是 `{0, 0.5, 1, 1.5, 2, 3, 4, 6}`。给定 scale `s`，一个值
被编码成 `round_e2m1(x / s) · s`，可表示上界是 `6s`。

现状 `s = amax / 6`：组内最大值恰好落在格点 6，用满整个网格，包括顶端
4→6 那个宽度为 `2s` 的空档。

候选 `s = amax / 4`：组内最大值落在格点 4，完全不使用 4→6 区间。上界变成
`6s = 1.5 · amax`，所以不会裁剪。

### 2.2 收益来自哪里

两者的最坏舍入误差分布不同：

| 区域 | `s = amax/6` | `s = amax/4` |
|---|---|---|
| 低端（相邻格点间距 0.5s） | `amax/24` | `amax/16` |
| 顶端（`amax/6` 是 4→6，`amax/4` 是 3→4） | `amax/6` | `amax/8` |

`amax/4` 在顶端好 1.33 倍，在低端差 1.5 倍。两者在 `x = amax` 处都是精确的，
差别出现在**紧邻 amax 下方**：`s = amax/6` 时落在 `(0.667·amax, amax)` 的值只
能舍入到 `0.667·amax` 或 `amax`，而 `s = amax/4` 时该区间被 3、4 两个格点切得
更细。

所以 `amax/4` 适合「组内有多个值贴近 amax」的分布，`amax/6` 适合「一个大值加
一片小值」的分布。逐组按 MSE 选择正是为了同时吃到两边。

选择规则：两个候选 scale 都**先舍入到 E4M3**再算 MSE——比较一个存不下的 scale
没有意义。误差相等时取 `amax/6`，让这次改动相对现状是严格改进。

### 2.3 为什么解码路径完全不动

无论 scale 怎么选，落盘的都是每 16 元素一个 E4M3，`tcgen05.mma` 那边只负责相
乘。4/6 只改变**写入时怎么挑这个数**，不改变它的类型、布局、数量或消费方式。

因此 K/V 上的 4/6 是零解码开销：写路径的流量约是解码读流量的 0.01%，把该组的
量化算术翻一倍在那里不可测。

## 3. 作用范围

### 3.1 纳入 K、V、Q

- K 页、V 页：`quantize_kv_kernel.py::_quantize_vector`，K 与 V 共用，改一处。
- Q：`quantize_q_kernel.py::_quantize_query_kernel`，每步一次、张量很小。

三处的代价都可忽略。

Q 这一处还有一层与 Task 6 的联系：per-channel smoothing 会把 Q 的组内动态范围
拉宽、让更多值贴近 amax，那恰好是 4/6 擅长的分布。两个改动在 Q 上是互补的。

### 3.2 不纳入 P

P（softmax 之后的概率）的量化在 `fp4_decode_kernel.py` 的热循环里，每个 KV
tile 走一遍。4/6 要对两个候选各量化一次、算两次误差再比较，在那里是实打实的
翻倍。

而且 P 未必受益。它的典型形态是少数几个大值加一大片极小值——正是低端分辨率
更重要的那种分布，也就是 `amax/6` 占优的那一侧。花热循环的代价去换一个方向存
疑的收益不合算。

P 保持 `amax/6`，作为单独的待测项记录在此，不在本计划内实施。

## 4. 与仓库规则的张力

### 4.1 规则 7 与开关形式

开发规则 7 禁止实验性环境开关。4/6 需要 A/B，所以开关必须是别的形式。

先例是 `num_splits`：CLAUDE.md 明确说它「是让 split-K 路径能从公开入口被测试
到的东西」，生产从不使用。同样地，在三个量化入口上加一个类型化的
`scale_mode` 参数是合规的，生产取一个定值，测试两边都能到达。

服务侧怎么选是一个未决点。`nvfp4_vllm` 需要从某处拿到这个值，而唯一干净的来
源是 vLLM 的 config，不能是环境变量。若不愿引入 config 字段，退路是让 4/6 无
条件生效、评测 A/B 通过两个 build 完成——操作上笨重，但完全合规。这个选择在
Phase 1 开始前定下来。

### 4.2 数值边界

`s = amax/4` 比 `s = amax/6` 大 1.5 倍，E4M3 的上界 448 因此对应更紧的 amax 上
限：`amax ≤ 1792`，而 `amax/6` 是 `amax ≤ 2688`。BF16 的 post-RoPE K 实际上远
达不到，但选择逻辑必须在 scale 超出 E4M3 范围时回落到 `amax/6`，而不是溢出。

下溢方向相反且更宽松：`amax/4` 比 `amax/6` 晚下溢，不需要额外处理。

## 5. 分阶段计划

### Phase 0 — Torch 参考实现先行

在 `src/nvfp4_decode_kernel/reference.py`（由 Task 6 Phase 0 建立）里实现 4/6
的选择逻辑，加一个 `scale_mode` 参数。

这一阶段不碰 CuTeDSL，因此不需要 SM100，也不需要任何开关设计。它的产出是一个
纯离线的答案：在真实抓取的 K/V/Q 张量上，4/6 相对 `amax/6` 把量化误差降低了多
少。如果这个数字接近零，后面几个阶段就不必做。

### Phase 1 — CuTeDSL 落地

改 `_quantize_vector` 和 `_quantize_query_kernel`：算出 amax 后，构造两个
E4M3 scale 候选，各做一次 E2M1 舍入并累加平方误差，取小者，其余流程不变。

保持规则 4：不引入 per-call 转置，不物化额外的 scale 拷贝。两个候选的比较在寄
存器里完成，落盘的仍然是一个 E4M3。

### Phase 2 — 验证

在 SM100 上（规则 9，import 检查不算数）：

- `tests/kernel` 新增用例，断言 kernel 的 4/6 输出与 `reference.py` 的
  `scale_mode="four_over_six"` 逐字节一致，这是把两份实现钉在一起的唯一手段。
- 断言 `scale_mode="amax6"` 下的输出与改动前逐字节一致，证明这次改动对现状是
  纯增量。
- 断言在人造的「组内多值贴近 amax」输入上 4/6 的 MSE 严格更低，在「单个大值加
  一片小值」输入上退化为 `amax/6`。

### Phase 3 — 评测联动

交给 `BitKV_nvfp4/docs/tasks/6.kv_smoothing_calibration.md` Phase 6。

## 6. 验证纪律

`scripts/run_tests.sh kernel` 的干净基线是 **1 failed, 85 passed**；
`test_prequantized_query_matches_bf16_query_exactly[32-1]` 是已知的、故意未修的
kernel bug。判据是这次改动**有没有新增失败**，不是套件是否全绿。

任何逐字节比较两次运行的用例都要避开 `(heads_q, heads_kv) = (32, 1)`——那个几
何本身解码就不可复现——并且必须带 `-p no:randomly`，否则 `pytest-randomly` 让
一次碰巧变绿的运行看起来像修好了。

## 7. 与 BitKV Task 6 的耦合

顺序已定：Task 6 的 smoothing 先做、先评测，4/6 在其后。

这带来一个必须记录在案的后果。Task 6 的 α 是针对 `amax/6` 量化器搜出来的，而
4/6 **改变了量化器本身**，所以 4/6 上线后那份 α 就过期了，必须重搜。重搜只需
重跑 Task 6 的 Phase 2（统计量和 token 子样本与量化器无关，可复用），代价是又
一次亚分钟的搜索，不是又一次前向。

对应地，Task 6 第一轮的评测结论只对 `amax/6` 量化器成立，报告里要写明。

Task 6 的 sidecar 元数据里带有 `quantizer variant` 字段，就是为了让这次重搭有
据可查。

## 8. 范围外

- P 的 4/6（第 3.2 节，单独待测）。
- 除 `amax/6` 与 `amax/4` 之外的候选 scale。
- 第二级 global scale。
- 任何改变 scale 存储类型、布局或数量的方案。
