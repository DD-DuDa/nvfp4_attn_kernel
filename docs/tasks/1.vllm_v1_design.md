# NVFP4 KV Cache 的 vLLM 集成：v1 设计

本文取代 `1.vllm_tag_redesign.md` 作为实现依据。那份文档描述的是旧仓库
（`nvfp4_attn`）双池架构下的优化路线；v1 换了内存模型，它的大部分结论不再适用。
第 8 节说明哪些还有效。

## 1. 决策摘要

| # | 决策 | 依据 |
|---|---|---|
| D1 | Out-of-tree 包，注册 `CUSTOM` backend；非必要不改 fork | vLLM 官方扩展机制 |
| D2 | **vLLM 的 paged cache 就是 FP4 池**；BF16 尾巴在我们自己的 per-slot buffer | §2 |
| D3 | **不使用 dtype tag**，页状态由 `seq_lens` 推导 | §3 |

## 2. 反转：vLLM 的 block 就是 FP4 页

### 2.1 旧仓库为什么会更费内存

旧架构里 vLLM 拥有 BF16 blocks，FP4 池是另开的、在 vLLM 记账之外的一块内存。
vLLM 仍然按 `gpu_memory_utilization` 把显存填满 BF16 blocks，FP4 池是净增量。
结果是用了 FP4 反而比纯 BF16 更费内存。

### 2.2 v1 的做法

反过来：**vLLM 的 paged cache 直接存 FP4**，并且如实告诉 vLLM 页有多大。
BF16 尾巴不进 vLLM 的 block，住在我们自己的固定 buffer 里。

以 Llama-3.1-8B（`L=32, H_kv=8, D=128, P=128`）为例：

```text
nvfp4_kv_cache_full_dim(128) = 128/2 + 128/16 = 72 字节/token/头

FP4  页 = 2 × 128 × 8 × 72  × 1 = 147,456 字节/层   (144 KiB)
BF16 页 = 2 × 128 × 8 × 128 × 2 = 524,288 字节/层   (512 KiB)
比值 = 3.556×
```

同样的显存预算下 vLLM 会分配约 3.56 倍的 block，调度器自动接纳更长的上下文。
不需要 `kv_cache_memory_bytes` 之类的手工干预——vLLM 的页大小记账是唯一真相来源。

BF16 尾巴 buffer：

```text
每 slot = P × H_kv × D × 2字节 × 2(K,V) × L
        = 128 × 8 × 128 × 2 × 2 × 32 = 16 MiB
总量 = max_num_seqs × 16 MiB
```

**注意 `max_num_seqs` 因此变成一个显存旋钮**：vLLM 默认 256，那就是 4 GiB 的隐形开销。

**v1 定为 8**（128 MiB）。选 8 而不是 1，是因为多行 decode 路径
（批量 metadata、slot 分配与复用）正是集成 bug 最容易藏的地方，
而 kernel 测试虽然覆盖了 multi-batch，集成层没有。
e2e 测试要相应地批量跑（`NVFP4_GSM8K_MAX_NUM_SEQS=8`，
默认值 1 会让这条路径完全测不到）。以后要放大只是改个 buffer 尺寸。

### 2.3 单缓冲就够

promotion 时先读尾巴、qpack 写出 FP4，再把新 token 写回同一块缓冲。
读写有先后，不需要双缓冲。

### 2.4 实际量化的是 Q/K/P/V，不只是 Q/K

准确的数据路径是：

```text
FP4 prefix:
    FP4 Q × FP4 K
    → softmax
    → P 量化为 FP4
    → FP4 P × FP4 V

recent tail:
    BF16 Q × BF16 K
    → BF16 softmax/P
    → BF16 P × BF16 V

最后在线合并两部分的输出与 LSE。
```

- Q/K 沿 `head_dim` 每 16 个元素一组做 block-scaled NVFP4；
- V 沿 **token 轴**每 16 个 token 一组；
- P 也在 FP4 prefix 分支里量化。

对应代码证据：`fp4_decode_kernel.py` 的 `quant_qk` / `quant_pv` 两条路径，
以及 `quantize_kv_kernel.py` 中 V 的 K-major（token-contiguous）布局。

因此 bookkeeping 的根因不是 Q 量化，也不是 P 量化，而是 **V 沿 token
轴量化不能处理半页**：recent token 必须先留在 BF16 staging page，填满后再
promotion。Q/P 量化没有跨 step 状态，只带来当前 wrapper 的 scratch/repack
执行开销。

## 3. 不需要 dtype tag

### 3.1 判据

> 当且仅当一页的精度取决于**无法从 `(页索引, seqused)` 推导出来的运行时历史**时，
> 才需要存储 per-page tag。

tag 是一个物化的事实；只有当这个事实推不出来时，它才值得存。

### 3.2 v1 的推导

```python
n_fp4    = (seqused - 1) // P     # 页 [0, n_fp4) 是 FP4，在 vLLM 的 block 里
residual = ((seqused - 1) % P) + 1  # 尾巴，在 per-slot buffer 里
```

页 `n_fp4` 是唯一的 BF16 页，且它永远不在 vLLM 的 block 里。
于是 tag 存的信息量为零。

这不是新发明的方案：`tests/kernel/test_fp4_decode_correctness.py:260-261`
里的 fixture 用的就是逐字相同的两行。**kernel 从设计之初就假定调用方这么算**，
`seqused_fp4` / `seqused_residual` 本来就是它的输入合同。
这是对「不需要 tag」的一个独立佐证。

旧架构需要 tag，是因为 FP4 池和 vLLM blocks 是两套独立的 id 空间，
一个逻辑页可能落在任意一边。反转之后不存在这种二义性。

### 3.3 连带消失的东西

`PreGroupedViews`、FP4 池分配器、pending/release ownership ledger、
`sp_id // 4` oracle 分叉、自定义 GC 与 vLLM teardown 之间的 double-free 风险，
以及 `1.vllm_tag_redesign.md` 的 Phase 1–3。

§4.1 的 tag-aware metadata kernel 退化成三个 elementwise op：

```python
fp4_page_ids     = block_table                      # 直接透传，无 gather
seqused_fp4      = ((seq_lens - 1) // P) * P
seqused_residual = ((seq_lens - 1) % P) + 1
has_bf16         = 可省略                           # v1 每行必有尾巴
residual_page_ids = row_to_slot                     # GPU control kernel 输出
```

### 3.4 多轮也推得出来

多轮的关键在于：**推导不需要知道 prefix cache 命中在哪里断开，
因为断开点两边都是 FP4**——命中的部分是上一轮写的，新算的部分是这一轮写的。

例：第一轮 prompt 900 + 生成 300 = 1200 token，页 7、8 在 decode 中 promote，
页 9（48 token）随请求结束丢弃。vLLM 缓存了 block 0-8（1152 token）。
第二轮 prompt = 1300，命中 1152，重算 148 个 token：

```text
n_fp4 = (1300-1) // 128 = 10
页 0-8  ← 缓存来的 FP4          ✓
页 9    ← 本次 prefill 填满，qpack 成 FP4  ✓
页 10   ← 20 个 token，进尾巴    ✓
```

丢掉的尾巴每轮最多 `W` 个 token，8B 模型上约 2 ms 的重算，可忽略。

这依赖 vLLM 只 hash 填满的 block（`kv_cache_utils.py` 的
`request_block_hasher`，注释 "We only hash full blocks"），
且单 KV cache group 时 `hash_block_size == block_size`，
所以命中一定落在页边界上，和 promotion 的粒度天然对齐。

### 3.5 什么情况下 tag 才该回来

- **位置性策略不需要**：例如「前 N 个 token 保持 BF16」（attention sink），
  仍然是 `(页索引, seqused)` 的函数，加个特例即可。
- **真正需要 tag 的**：FP4 页和 BF16 页可以**任意交错**。
  典型触发场景是「按运行时测量的误差/重要性决定每页精度」，
  或者「每轮结束保留一个 BF16 岛」（见 §7.3）。

即使到了那一步，也要先问：状态是不是仍然是一个**二分**（低精度前缀 + 高精度窗口）？
如果是，最多只需要**每序列一个 int32**（边界在第几页），而不是每页一个 tag。
只有真正任意交错才需要 per-page tag。

## 4. W = P

BF16 窗口长度和页大小之间没有自由度，被两个方向夹死。

### 4.1 `W ≥ P`：FP4 必须整页写

V 沿 token 轴打包（`[pages, heads, head_dim, page_size/2]`），
且 kernel 接口要求 `seqused_fp4` 是页大小的整数倍。
所以必须先在 BF16 里攒够一整页才能量化写出去。
**BF16 窗口是暂存区（staging），不是保护区（protection）。**

### 4.2 `W ≤ P`：promotion 的触发条件必须是 block 内在属性

`W > P` 时，BF16 窗口会占据 `W/P` 个 block，其中除最后一个外都是**填满的**。
此时出现两个互相关联的问题：

**（a）promotion 时机没有唯一答案。**
`W = P` 时触发条件是「这个 block 填满了」，是 block 内容的属性，谁看都一样。
`W > P` 时触发条件是「序列已走过这个 block 之后 W 个 token」，是**读者位置**的属性。
而 prefix caching 下同一个 block 被多个序列共享，各自走的距离不同。

**（b）格式变成读者的函数。**
同一个物理 block，`seqused` 较小的请求认为它在窗口内（BF16），
`seqused` 较大的请求认为它已滑出（FP4）。两边推导都对，但字节只有一份。

即便把 BF16 放在自己的 buffer 里（block 只写 FP4，不存在格式变更），
`W > P` 仍然会把 promotion 竞态从 1 步拉宽到 `W - P` 个 token：
vLLM 按 token 数判定 block 满了就对外缓存，而我们要等它滑出窗口才写 FP4。

**结论**：`W = P` 是唯一让「离开 BF16 窗口」和「block 填满」重合的取法，
而「填满」是唯一 block 内在的、共享安全的触发条件。

### 4.3 P 的取值

`P = W = 128` 是当前 kernel 的写法（`quantize_kv_kernel.py` 的 `PAGE_SIZE = 128`）。

`P = W = 16` 在维度上也成立（V 变成 `[pages, heads, 128, 8]`，
恰好一个 scale 组，因为 `SF_VEC_SIZE = 16`），**且量化质量完全相同**——
NVFP4 的 scale 组本来就是 16 个 token，`P` 只决定一页装几个 scale 组。
它的收益是尾巴 buffer 从 16 MiB/slot 降到 2 MiB/slot、prefix cache 粒度细 8 倍；
代价是 block table 大 8 倍、kernel 多迭代 8 倍页数、高精度近期窗口短 8 倍。

v1 用 128，`P` 不做成运行时参数（kernel 里是编译期常量）。

## 5. Promotion 时机：本步最后一层之后

### 5.1 三个候选位置

| 位置 | 数据是否安全 | 竞态窗口 | 是否需要改 fork |
|---|---|---|---|
| 第 N 步 layer 0 | ✗ layer 1..L-1 还没写 boundary token | — | 否 |
| 第 N+1 步 layer 0（旧仓库做法） | ✓ | 1 步 | 否 |
| **第 N 步 layer L-1 的 attention 之后** | ✓ | 0 | 否 |

旧仓库用的是第二种（`vllm_hook.py` 里 `_unified_step_promotion_done`
在每步第一层复位，promotion 只在该步跑一次，内部对所有层循环）。

### 5.2 为什么最后一层可行

- 此时 32 层都已写完本步的 boundary token → 数据安全
- 本层自己的 attention 已经跑完 → 它这一步仍需把该页当 BF16 读
- vLLM 的 block caching 发生在整个 model forward 之后 → 我们赶在它之前写完 FP4，
  竞态归零
- backend 知道自己是第几层，不需要 patch fork

### 5.3 步内顺序

```text
第 N 步 build()：
    seq_lens = 1024 → n_fp4 = 1023//128 = 7
    页 0-6 FP4，页 7 是尾巴（128 token）      ← 全部 32 层共用这份 metadata

layer 0 .. L-2：写 KV 到尾巴 → attention
layer L-1     ：写 KV 到尾巴 → attention → **promotion**
                  条件 seq_lens % P == 0
                  对全部 L 层：qpack 尾巴 → vLLM block (seq_lens/P - 1)
                  重置尾巴 buffer

第 N+1 步 build()：
    seq_lens = 1025 → n_fp4 = 1024//128 = 8
    页 0-7 FP4（页 7 刚 promote），页 8 是尾巴（1 token）  ✓
```

### 5.4 限制

`PP > 1` 时最后一层不一定在本 rank 上，需要另行处理。v1 强制 `PP == 1`。

### 5.5 promotion 不允许 host-side 分支

promotion 条件 `seq_lens % P == 0` 必须在 GPU 上计算。最后一层后**每步固定**
发射 promotion kernel，由 device mask 决定哪些 row 真正 qpack：

```text
promotion_mask[row] = (seq_lens[row] % P == 0)
固定 launch → kernel 内 mask → 0 或多行 promotion
```

禁止下面这种写法：

```python
rows = (seq_lens % P == 0).nonzero()
if rows.numel() == 0:       # 动态 nonzero / host 控制流
    return
```

这会把 promotion 变成每步一次固定 launch，其中约 127/128 的 step 只做 mask
检查，但换来：

- promotion 路径没有 DtoH 或 Python 分支；
- launch 数与 batch 内容无关；
- 将来可以进入 CUDA graph。

v1 仍强制 `enforce_eager=True`，因为完整 graph 兼容还取决于其他 kernel 和 buffer
地址稳定性，不能仅凭 promotion 谓词化就宣称已经支持。S10 同时测
BF16 graph、BF16 eager、NVFP4 eager，把 graph 代价与量化代价分开。

## 6. 实现约定

### 6.1 护栏（一律 fail closed）

| 检查 | 原因 |
|---|---|
| `block_size == 128` | V 量化组跨页会读不了；见 §4 |
| `enable_prefix_caching == False` | v1 不支持 continuation prefill；见 §7 |
| `prefix_match_unit == block_size` | 细粒度命中会落在页中间，半页无法 V 量化 |
| 拒绝 `num_computed_tokens > 0 且 query_len > 1` | continuation 需要在 FP4 上做 prefill |
| decode 行 `query_len == 1` | 投机解码会带来回滚，v1 不支持 |
| `pipeline_parallel_size == 1` | promotion 挂在最后一层；见 §5.4 |
| `enforce_eager == True` | v1 尚未验证完整 CUDA graph；promotion 本身已 host-branch-free |
| `max_num_seqs == 8` | 尾巴 buffer 固定 128 MiB；不接受 vLLM 默认 256 |
| `kv_transfer_config is None` | connector 会按 block 搬字节，与 region-major 候选布局不兼容 |
| `cache_config.kv_offloading_size is None` | KV offload 同样按 block 地址/大小搬字节 |

**关于 TP**：`TP > 1` 不设护栏。KV 头分片后每个 rank 的尾巴 buffer 按比例变小，
而每个 rank 都持有全部层，promotion 挂最后一层照常成立，所以设计上应当直接可用。
但 v1 **不测它**，算未验证状态。

### 6.2 GPU-resident slot control plane

BF16 尾巴需要跨步跟着**请求**走，而 vLLM 的 batch 行号跨步不稳定
（`InputBatch` 在请求结束时会压缩行）。所以需要一个稳定的 key。

**不能用 request id。** 这一点是查证过的，不是猜测：`CommonAttentionMetadata`
（`v1/attention/backend.py:411-488`）里**完全没有字符串 request id**，只有 batch
索引；`finished_req_ids` 只存在于 `SchedulerOutput`
（`v1/core/sched/output.py:219-222`），`ForwardContext`、
`AttentionMetadataBuilder.build()`、`AttentionImpl.forward()` 三处都拿不到。

**改用 `block_table_tensor[row, 0]` 作为 key**，也就是逻辑页 0 的物理 block id。
理由：

- 它在请求的整个生命周期内不变（prefix caching 关闭，没有 CoW）
- 它在所有存活请求之间唯一（block 被独占持有）
- 它每步都在 `CommonAttentionMetadata` 里，不需要任何额外管道

slot 表必须常驻 GPU，不使用 Python `dict` / `set`。由于 v1 只有 8 个 slot，
一个 CTA 就能完成所有工作。persistent state：

```text
slot_keys          int32 [8]   # -1 表示 free
slot_last_seq_lens int32 [8]
```

once-per-step control kernel 输入：

```text
block_table[:, 0]  int32 [num_reqs]
seq_lens           int32 [num_reqs]
query_start_loc    int32 [num_reqs + 1]
```

输出到 persistent scratch：

```text
row_to_slot        int32 [num_reqs]
token_to_slot      int32 [num_actual_tokens]
seqused_fp4        int32 [num_reqs]
seqused_residual   int32 [num_reqs]
promotion_mask     bool/int32 [num_reqs]
error_code         int32 [1]   # debug/fail-stop
```

同一 kernel 内完成：

1. 用 `block_table[row, 0]` 查找/分配 slot；
2. 比较当前 key 集合，释放缺席 key；
3. 用 `seq_len == last_seq_len + query_len` 检测 key 复用；
4. 推导 `seqused_fp4` / `seqused_residual`；
5. 展开 `token_to_slot`；
6. 生成 `promotion_mask`。

这样回收靠「缺席」而不是通知，同时不需要 `finished_req_ids`、DtoH、Python
逐请求循环，也不需要把 Python slot list 再 HtoD。

三个必须处理的边界：

1. **block 复用**：请求结束后 block 0 可能立刻被新请求拿去用，于是新请求
   撞上同一个 key。用 `seq_lens` 连续性校验；对不上时在 device 上把该 slot
   当成新 generation，覆盖有效 tail 范围，不做 host round-trip。
2. **抢占**：V1 的抢占是「释放 block 重算」，所以被抢占的请求下次出现时
   `block_table[:, 0]` 已经变了，天然走「新请求」分支。上面那条校验也会兜住。
3. **缺席即死亡**：这条依赖「running batch 每步都包含全部运行中的请求」。
   V1 除抢占外确实如此。若将来这个前提变了，会表现为尾巴被误释放，
   所以 debug 路径必须 poison + fail loud。

### 6.3 必须钉死的实现细节

`seq_lens` 在我们读取时**是否已包含本步要写入的 token**。
差一个 token，§3.2 的整套推导就错位一页。
错了的表现是「精度偶尔掉一点」，极难定位，所以要在写代码前先验证并写成断言。

### 6.4 零 host-sync 合同

steady-state decode 中，我们新增的代码必须满足：

```text
0 × Tensor.cpu()
0 × Tensor.item()
0 × Tensor.tolist()
0 × 动态 nonzero 后的 Python 分支
0 × Python request/slot 循环
```

允许 Python 做的事情只有启动时配置、分配 persistent buffer、缓存 tensor views
和发射固定 kernel。每步的 request 生命周期、row→slot、长度拆分和 promotion
选择全部在 GPU 上。

当前 standalone wrapper 的 `_check_device_values()` 使用
`torch.any(...).item()`；带 residual + direct scatter 时每层最多 5 次，
32 层静态上限为 **160 次 host scalar read/step**。集成前必须提供 trusted
metadata fast path：

- shape / dtype / stride 继续在 host 校验（不读 device value）；
- value-range 检查只在 debug/test 模式启用；
- production metadata 完全由 §6.2 的 GPU control kernel 产生，不再逐层
  `.item()` 检查；
- debug 的错误必须 fail-stop，不能写一个无人读取的 flag 后继续 attention。

这个合同只约束我们相对 stock vLLM 新增的路径；vLLM 自身已有的 scheduler
CPU metadata 不计入增量，但也不得为了我们的 backend 新增一次往返。

## 7. v1 不做的事

### 7.1 Continuation prefill（多轮 + chunked prefill）

两者是同一个问题的两种外衣：**prefill 的 query 需要在已经量化成 FP4 的上下文上做 attention**。
stock FlashAttention 读不了 FP4。

解锁方式：**FP4 → BF16 dequant kernel**（现有 qpack 的逆），配一个单层 scratch buffer。
按层反量化后走 cache-free 的 `flash_attn_varlen_func`。

成本估算（8k 历史，Llama-3.1-8B）：

```text
反量化流量 ≈ 1.4 GB / 32 层  →  B200 上约 0.5 ms
从头重算 8k ≈ 131 TFLOP      →  约 120 ms
```

即反量化能拿到 prefix caching 几乎全部的收益，代价约 0.4%。
scratch 峰值内存约 4 MiB / 1k token（单层复用）。

一个 kernel 同时解锁多轮和长上下文。

### 7.2 长上下文

v1 的 prompt 上限由 `max_num_batched_tokens` 决定（必须单次 prefill 完）。
测试里设 16384，GSM8K 的 prompt 约 900 token，余量充足。
128k 需要 §7.1。

### 7.3 中间的 BF16 岛

「每轮结束不 promote，把尾巴留作 BF16 供下一轮复用」这个想法**不采纳**：

- 会在序列中间留下位置任意的 BF16 岛 → 这正是唯一真需要 per-page tag 的情形
- vLLM 一个 KV cache group 只有一个 page size，BF16 岛（524,288 字节）
  装不进按 FP4 尺寸分配的 block（147,456 字节）
- 放进自己的 buffer 则进不了 vLLM 的 prefix cache（cache 只能指向 vLLM 的物理 block），
  要复用就得自己再实现一套 hash → buffer 的缓存 + 引用计数 + 淘汰
  ——那等于把旧仓库的双池架构镜像着搬回来
- 每个岛 16 MiB，每轮一个，随对话轮数无上限增长
- 收益只有每轮省下约 2 ms 的重算

如果将来发现**质量上**必须在序列中间保留高精度页，这套成本才值得重新评估。

### 7.4 投机解码

回滚可能把 `seqused` 退到已 promote 的边界以下，需要反量化回 BF16
（依赖 §7.1 的 kernel），或者把 promotion 延后到投机窗口之外
（仍是位置性规则，不需要 tag）。

## 9. 实施计划

### 9.0 排序原则

1. **每一步做完系统都能跑、能测**，不存在「写了三天还没法验证」的阶段。
2. **最高风险的未知项排在最前**：如果页大小声明这条路走不通，整个内存模型要重来，
   宁可第一天就知道。
3. **先把管道跑通，再引入 FP4**。S2 结束时全链路已经通了但一个 FP4 字节都没写，
   这样后面出问题时可以确定是量化逻辑而不是集成管道。

目标模型：**Llama-3.1-8B-Instruct**（`L=32, H_kv=8, D=128`）。硬件：单卡 SM100。

选它是因为旧仓库的 GSM8K 基线就是在它上面测的，测试里的准确率常量可以直接沿用。
代价是它**还没下载**（`models/` 下目前只有 Qwen3-8B），S0 要先解决。
本文所有内存数字都按这个配置计算；换成 Qwen3-8B（`L=36`）的话，
尾巴 buffer 会从每 slot 16 MiB 变成 18 MiB，页大小不变。

### 9.0.1 kernel 侧已有的覆盖

计划里不包含「补 kernel 测试」这一步，因为 `tests/kernel/` 已经有了：

| 文件 | 覆盖 |
|---|---|
| `test_fp4_decode_correctness.py` | 独立 PyTorch oracle（`_torch_fp4_decode`）、边界集 `(1,127,128,129,255,256,257)`、8192 长上下文、GQA/MHA/MQA、多 batch 混合长度、`has_bf16=0` 逐字节相等、poisoned page-table 尾部、`query_row_indices` 等价、`out`/`out_indices` scatter |
| `test_quantize_query.py` | query 量化路径 |

split-K 没有测试，但也不需要：新仓库的 decode 路径把它硬关掉了
（`_decode.py:279` 的 `is_split_kv=False`），v1 不走这条分支。

因此 S6/S7 的数值门槛应当**复用**这些 oracle，而不是另写一份。

### 9.1 cache dtype 切换时机

这条贯穿多步，单独说清楚免得踩坑：

| 步骤 | `kv_cache_dtype` | cache 里装什么 |
|---|---|---|
| S0–S5 | 默认（bf16） | vLLM 自己写的 BF16，我们不碰 |
| S6 起 | `nvfp4` | 我们写的 FP4；BF16 只在 per-slot 尾巴 buffer |

S1 只负责**验证** `nvfp4` 这条路能走通并选定 layout，不真的切过去。
真正切换在 S6——写路径就绪之前把 cache 换成 FP4 形状，
stock FlashAttention 就读不了了，S2 的直通验证也就做不成。

### S0 — 环境与 BF16 基线

**做什么**

- 下载 `NousResearch/Meta-Llama-3.1-8B-Instruct`（`models/` 下还没有）
- `pip install -e third_party/vllm`，确认 `import vllm` 解析到 fork 而不是 site-packages
- 确认 SM100（`torch.cuda.get_device_capability()[0] == 10`）
- 跑 `tests/e2e/test_vllm_integration.py` 的 BF16 一半

**验收**

- GSM8K N=32、5-shot、greedy，BF16 准确率 ≥ 0.60（测试的 `GSM8K_MIN_ACCURACY`），
  预期落在 0.78 附近
- `_require_vllm_fork()` 通过

**注意**

现有测试里 `NVFP4_ATTENTION_CONFIG = {"backend": "FLASH_ATTN", "nvfp4_kv_mode": "tagged"}`
（`tests/e2e/test_vllm_integration.py:43-46`）引用了一个 **`AttentionConfig` 里不存在的字段**。
S0 阶段先只跑 BF16 那半，这个 dict 留到 S2 一起改。

### S1 — 页大小声明（最高风险未知项）

上一轮设计讨论结束时唯一悬而未决的问题，先解决它。

**要回答的三个问题**

1. `kv_cache_dtype="nvfp4"` 能不能拿到我们要的页大小？
   `FullAttentionSpec.real_page_size_bytes`（`v1/kv_cache_interface.py:203-218`）
   在 `is_nvfp4` 时用 `nvfp4_kv_cache_full_dim(head_size)`，
   `head_size=128` 时是 72，算出 `2 × 128 × 8 × 72 = 147,456` 字节/层。

2. 这个 dtype 还会连带触发什么？fork 里 FlashInfer 那条 NVFP4 路径要求
   trtllm-gen backend、FP8 query、FP8 输出缓冲
   （`v1/attention/backends/flashinfer.py:1977-1986` 等）。
   我们用自己的 backend，理论上不受影响，但需要逐一确认
   `config/cache.py`、`config/model.py`、`platforms/interface.py`、
   `model_executor/layers/attention/attention.py` 里对 `nvfp4` 的分支
   不会在引擎启动阶段拦下我们。

3. `get_kv_cache_shape` 返回什么形状？字节预算对得上（K_fp4 + K_sf + V_fp4 + V_sf
   合计也是 147,456），但内部排布和 upstream 不同。两个候选：
   - **block-major**：每个 block 内部依次放四个区域。符合 vLLM 的直觉，
     但四个区域各自跨 block 不连续，kernel 要处理 stride。
   - **region-major (SoA)**：整个张量先放所有 block 的 K_fp4，再 K_sf，再 V_fp4，再 V_sf。
     四个区域各自连续，kernel 拿到的就是四个正常张量。
     前提是 vLLM 不会把 block 当成连续字节去搬——关闭 prefix caching
     和 KV connector 之后应该成立，需要验证。

**做什么**

写一个独立脚本（不进 pytest），构造 `LLM(...)`，打印
`kv_cache_config` 里的 `page_size_bytes`、`num_blocks`、每层张量的 shape 与 dtype。

**验收**

- 引擎能启动，不因 `nvfp4` dtype 报错
- `page_size_bytes == 147456`
- 同样 `gpu_memory_utilization` 下，`num_blocks` 约为 BF16 情况的 3.5 倍
- 明确选定一种 layout，并记录选择理由

**如果走不通**

退路是自定义 `KVCacheSpec` 子类，但那需要改 `Attention.get_kv_cache_spec`
（fork 里它按 `kv_cache_dtype` 字符串硬编码分支），违反 D1。真到这一步要重新评估 D1。

### S2 — 直通 CUSTOM backend

**做什么**

- 新建 out-of-tree 包（暂定 `src/nvfp4_vllm/`），通过 vLLM 的 plugin entry point 注册
- backend 继承 FlashAttention，**行为完全不改**
- 把测试里的 `NVFP4_ATTENTION_CONFIG` 改成真实存在的配置，删掉 `nvfp4_kv_mode`
- **仍然用默认的 BF16 cache dtype**（见 §9.1）

**验收**

GSM8K 准确率与 `FLASH_ATTN` **逐 token 一致**（greedy 且没有引入任何量化，
所以应当完全相同，不是「接近」）。

**为什么单列一步**

这一步把「插件 entry point 加载、backend 被正确选中、metadata 能构建、
forward 能被接管」全部验证完，而 FP4 风险为零。
此时 cache 形状和写路径都还是 vLLM 自己的，那两项要到 S6 才验证。

### S3 — 护栏

**做什么**

在 backend 初始化处加入 §6.1 的全部检查，每条都给出可操作的错误信息
（说明为什么不支持、怎么改配置）。

**验收**

单元测试：每种错误配置都抛出预期异常。特别是
`block_size != 128`、`enable_prefix_caching=True`、`pipeline_parallel_size > 1`、
`kv_transfer_config != None`、`kv_offloading_size != None`。

### S4 — GPU slot control plane 与 BF16 尾巴 buffer

**做什么**

- 预分配 `slot_keys[8]`、`slot_last_seq_lens[8]` 与所有 output scratch
- 实现 §6.2 的 once-per-step GPU control kernel
- 输入直接使用 device `block_table` / `seq_lens` / `query_start_loc`
- 输出 `row_to_slot`、`token_to_slot`、长度拆分和 `promotion_mask`
- 尾巴 buffer：`[max_num_seqs, L, 2, P, H_kv, D]` bf16，`max_num_seqs=8` 时 128 MiB
- 不清零整个 slot；只覆盖本次有效 token，依赖长度保证不读 stale tail

**验收**

GPU kernel 对 Python oracle：slot 分配/回收/行重排/key 复用/抢占、连续 200
个请求不泄漏。poison 未使用 tail 后输出不变。profile 中本步骤：

```text
0 DtoH, 0 HtoD, 0 .item(), 0 .tolist(), 1 control kernel / step
```

### S5 — 零同步 metadata builder

**做什么**

`build()` 只做三件事：

1. 从 `CommonAttentionMetadata` 取 device tensor；
2. 发射 S4 的 control kernel；
3. 返回引用 persistent scratch 的 `NVFP4Metadata`。

禁止在 `build()` 里使用 `.cpu()`、`.item()`、`.tolist()` 或 Python request loop。
`seq_lens_cpu_upper_bound` 只可用于启动/调试断言，production 热路径不用它。

**先钉死 `seq_lens` 语义**（§6.3）：在 `build()` 读到它的时候，
本步要写入的 token 算进去了没有。写一个断言把这个约定固定下来。

**验收**

GPU 输出对 Python oracle，覆盖边界：
`seqused ∈ {1, 127, 128, 129, 255, 256, 257, 1023, 1024, 1025}`。
重点是 128 的整数倍及其 ±1，那里 `n_fp4` 和 `residual` 同时跳变。
用 profiler 证明 control kernel once-per-step，而不是 per-layer。

### S6 — prefill 写路径

**做什么**

- **切换 `kv_cache_dtype="nvfp4"`**，用 S1 选定的 layout
- 满页 → qpack 成 FP4 写进 vLLM 的 block
- 余数 → 写进尾巴 buffer
- **任何时候都不往 vLLM 的 cache 里写 BF16**
- 所有层 qpack 完成之后才算这一页可见（`1.vllm_tag_redesign.md` §4.4，见 §8）

**验收**

把写进去的 FP4 反量化出来，和参考 BF16 逐层比 cosine。
另外验证 prompt 长度取 `{100, 128, 129, 900, 1024, 1025}` 时页划分正确。

**关于反量化**

生产用的 FP4 → BF16 kernel 是延后项（§7.1），但这里不需要它——
`tests/kernel/test_fp4_decode_correctness.py` 里的 `_nvfp4_round_trip`
已经是一个 torch 实现的量化/反量化参考，直接复用即可。

### S7 — decode 读路径

**做什么**

- decode 行走 `fp4_decode`
- prefill 行走 stock FlashAttention 的 cache-free varlen 路径
  （`flash_attn.py:1156` 那个模式，只吃原始 `key`/`value`，不碰 block_table）
- 给 `fp4_decode` 增加 trusted-metadata fast path：跳过
  `_check_device_values(...).item()`，shape/dtype/stride host 检查保留
- 缓存每层 carved KV views，预分配 Q / scale / output scratch

**验收**

promotion 还没实现，所以这一步**不能拿 GSM8K 做门槛**。GSM8K 的 prompt 长度不一，
到下一个页边界的距离大致均匀分布在 `[1, P]`，只要生成长度有意义，
绝大多数行都会跨边界。

改用一个**长度已知且固定**的 prompt：pad 到 `Lp`，选生成长度 `G` 使得

```text
floor((Lp + G - 1) / P) == floor((Lp - 1) / P)
```

例如 `Lp = 897`（`= 7×128 + 1`）、`G = 100`，全程停在页 7 之内。

门槛：

- attribution：`spy.calls > 0` 且 `spy.saw_fp4_prefix`
- **数值**：抓下 decode 的 attention 输出，和
  `tests/kernel/test_fp4_decode_correctness.py` 里的 `_torch_fp4_decode`
  在同样输入上算出的结果比 cosine。那个 oracle 已经是独立的 PyTorch
  混合 FP4/BF16 模拟，直接复用，不要另写一份。
  这比比较生成文本精确得多，也能定位到具体是哪一层出问题。
- 生成文本通顺

不要用「输出和 BF16 逐 token 一致」做门槛：页 0..n_fp4-1 此时已经是 FP4，
量化误差必然存在，greedy 解码通常前若干 token 一致、之后分叉，
拿它当门槛会得到一个既不稳定又没有诊断价值的测试。

完整的 GSM8K 门槛推到 S8。

### S8 — promotion

**做什么**

在最后一层 attention 之后（§5.3 的步内顺序）每步固定发射：

```text
promotion_kernel(
    mask = metadata.promotion_mask,   # device tensor
    对全部 L 层：qpack 尾巴 → vLLM block (seq_lens/P - 1)
)
```

不允许 `nonzero().numel()` 后在 Python 决定是否 launch。production 不清零
tail；下一页只按 `seqused_residual` 读取有效范围。

**验收**

- **完整的 GSM8K 门槛在这里生效**（S7 推过来的）：`max_tokens = 256`，
  必然跨若干次页边界，`tests/e2e/test_vllm_integration.py` 整体通过——
  attribution 有，NVFP4 相对 BF16 掉幅 ≤ 0.125，绝对值 ≥ 0.60
- 单独构造一个测试：让序列精确停在 `seqused = kP` 和 `kP+1`，
  检查页状态与推导一致
- 确认 promotion **只在最后一层后固定发射**，不是每层一次：
  launch 次数 = decode step 数（K/V 分开则各一次），不能乘以 `L`
- 真正的 payload write 行数 = 跨边界的 row 数；无 promotion 的 step
  只有固定空转 launch，无 DtoH/host branch

### S9 — 请求结束与清理

**做什么**

- slot 回收和 `seq_lens` 连续性检查已经融合在 S4 control kernel
- debug 模式检查 `error_code`；production 由 device fail-stop/gate 保证错误
  metadata 不进入 attention
- 不主动 free 任何 vLLM block（block 的生命周期归 vLLM）

**验收**

连续跑 200 个请求，slot 不泄漏，准确率不随请求数漂移
（漂移说明有跨请求的状态污染）；steady-state 全程无 custom DtoH/HtoD。

### S10 — 内存验证

这是整个项目的目的，必须是显式门槛，不能默认成立。

**做什么**

同一模型、同一 `gpu_memory_utilization`，对比 BF16 与 NVFP4：

- vLLM 报告的 `num_blocks`
- 相同显存下能跑到的最大上下文
- 加上尾巴 buffer（`max_num_seqs × 16 MiB = 128 MiB`）之后的净收益

另外测一笔**速度账**（§5.5）：BF16 开 CUDA graph 对 NVFP4 强制 eager 的
decode 延迟差。这不是门槛，是要显式记录下来的已知代价，
免得以后被人误读成「FP4 kernel 更慢」。有条件的话再测一个
BF16 也强制 eager 的对照，把「量化本身的代价」和「不能用 graph 的代价」分开。

**验收**

- `num_blocks` 比值接近 3.5
- 净内存收益为正，且随上下文增长而扩大
  （旧仓库正是在这里翻车：FP4 池是净增量，总量反而更大）
- 速度账已记录（无门槛，但必须有数）
- 自定义 steady-state decode 路径中：
  - `_check_device_values` / `aten::_local_scalar_dense` 次数为 0
  - DtoH/HtoD 次数为 0
  - metadata control kernel 为 1 次/step
  - promotion 为固定 launch，无 host-side 动态分支

### 9.11 延后项

| 项 | 解锁条件 | 参考 |
|---|---|---|
| 多轮 / prefix caching | FP4 → BF16 dequant kernel | §7.1 |
| Chunked prefill / 长上下文 | 同上（同一个 kernel） | §7.1、§7.2 |
| 投机解码 | 同上，或把 promotion 延后到投机窗口之外 | §7.4 |
| `P = W = 16` | 需要先量化性能取舍 | §4.3 |
| CUDA graph 兼容 | promotion 已谓词化；还需验证全部 buffer 地址/launch 稳定性 | §5.5 |

promotion 竞态已由 S8 的位置选择消解（FP4 在 vLLM 宣告 block 可缓存之前就写完了），
所以开启 prefix caching 时不需要额外修这一项，但要补上
`prefix_match_unit == block_size` 的护栏。

#### `src/nvfp4_vllm/layout.py` — S1 / S6

**不要手算区域字节数。** scale 张量很可能是 swizzled 布局，
手算出来的 `P × H × D/16` 未必对得上。用 kernel 自己的量化器探一次，
把真实形状记下来：

```python
import functools
import torch
from nvfp4_decode_kernel._quantize import (
    quantize_key_pages,
    quantize_value_pages,
)

PAGE_SIZE = 128


@functools.lru_cache(maxsize=None)
def region_specs(num_kv_heads: int, head_dim: int, device: str):
    """Probe the kernel's own quantizers for the real per-page layout."""
    probe = torch.zeros(
        1, PAGE_SIZE, num_kv_heads, head_dim,
        dtype=torch.bfloat16, device=device,
    )
    k_fp4, k_sf = quantize_key_pages(probe)
    v_fp4, v_sf = quantize_value_pages(probe)
    return tuple(
        (t.shape[1:], t.dtype, t.numel() * t.element_size())
        for t in (k_fp4, k_sf, v_fp4, v_sf)
    )
```

然后按 **region-major** 切分：整个 buffer 先放所有页的 `K_fp4`，
再 `K_sf`，再 `V_fp4`，再 `V_sf`。每个区域各自连续，
`k_fp4_all[page_id]` 直接就是 kernel 要的形状，不需要处理 stride。

```python
def carve(kv_cache: torch.Tensor, num_blocks: int, specs):
    """Split one layer's flat vLLM buffer into the four contiguous regions."""
    flat = kv_cache.reshape(-1).view(torch.uint8)
    out, offset = [], 0
    for shape, dtype, per_page_bytes in specs:
        size = num_blocks * per_page_bytes
        region = flat[offset:offset + size].view(dtype)
        out.append(region.view(num_blocks, *shape))
        offset += size
    assert offset == flat.numel(), (offset, flat.numel())
    return tuple(out)   # (k_fp4, k_sf, v_fp4, v_sf)
```

**为什么可以这样做。** vLLM 认为 block `p` 占的是
`[p × page_bytes, (p+1) × page_bytes)`，而我们实际是 region-major，
两者不一致。这不要紧，因为在 v1 的配置下 **vLLM 从不搬运 block 的字节内容**——
它只发 block id。会搬字节的路径包括 prefix caching 的 CoW、KV connector
和 KV offload，三者都被护栏关掉了。**将来打开其中任何一个都必须先切回
block-major layout，或者让搬运方理解 region-major。**

`backend.get_kv_cache_shape` 相应返回一个安全的字节视图：

```python
@staticmethod
def get_kv_cache_shape(num_blocks, block_size, num_kv_heads, head_size,
                       cache_dtype_str="auto"):
    # 第一维保持 num_blocks，避免踩到 vLLM 里可能存在的形状假设；
    # 真实的 region-major 解释在 layout.carve 里完成。
    page_bytes = 2 * block_size * num_kv_heads * (head_size // 2 + head_size // 16)
    return (num_blocks, page_bytes)
```

> **S1 必须验证**：`page_bytes` 要等于 `FullAttentionSpec.real_page_size_bytes`
> 算出来的 147,456，且 `layout.region_specs` 的四段之和也等于它。
> 三个数对不上就先停下来，别往下写。

#### `src/nvfp4_vllm/control.py` — S4 / S5

这个文件取代 Python `TailSlots`。核心必须是一个 **single-program /
single-CTA GPU kernel**，因为 `MAX_SLOTS=8`，O(8²) 查找比任何 host round-trip
都便宜。

```python
from dataclasses import dataclass
import torch

MAX_SLOTS = 8
PAGE_SIZE = 128
FREE_KEY = -1


@dataclass
class ControlOutputs:
    row_to_slot: torch.Tensor
    token_to_slot: torch.Tensor
    seqused_fp4: torch.Tensor
    seqused_residual: torch.Tensor
    promotion_mask: torch.Tensor
    decode_row_indices: torch.Tensor  # 固定容量 [MAX_SLOTS]
    decode_count: torch.Tensor        # device int32 [1]
    active_row_mask: torch.Tensor     # 固定容量 [MAX_SLOTS] bool
    error_code: torch.Tensor          # device int32 [1]


class ControlPlane:
    def __init__(
        self, *, max_num_batched_tokens, device,
    ):
        self.slot_keys = torch.full(
            (MAX_SLOTS,), FREE_KEY, dtype=torch.int32, device=device
        )
        self.slot_last_seq_lens = torch.zeros(
            MAX_SLOTS, dtype=torch.int32, device=device
        )
        # 以下全是 high-water-mark persistent scratch；不能在 build() 里重新分配。
        self.row_to_slot = torch.empty(MAX_SLOTS, dtype=torch.int32, device=device)
        self.token_to_slot = torch.empty(
            max_num_batched_tokens, dtype=torch.int32, device=device
        )
        self.seqused_fp4 = torch.empty(MAX_SLOTS, dtype=torch.int32, device=device)
        self.seqused_residual = torch.empty(
            MAX_SLOTS, dtype=torch.int32, device=device
        )
        self.promotion_mask = torch.empty(
            MAX_SLOTS, dtype=torch.bool, device=device
        )
        self.decode_row_indices = torch.empty(
            MAX_SLOTS, dtype=torch.int32, device=device
        )
        self.decode_count = torch.zeros(1, dtype=torch.int32, device=device)
        self.active_row_mask = torch.empty(
            MAX_SLOTS, dtype=torch.bool, device=device
        )
        self.error_code = torch.zeros(1, dtype=torch.int32, device=device)

    def prepare(self, m) -> ControlOutputs:
        # 这里只发射一次 kernel；不能读取任何输出到 host。
        launch_control_kernel(
            block0_ids=m.block_table_tensor[:, 0],
            seq_lens=m.seq_lens,
            query_start_loc=m.query_start_loc,
            num_reqs=m.num_reqs,                 # host 已知的 launch 参数
            num_actual_tokens=m.num_actual_tokens,
            slot_keys=self.slot_keys,
            slot_last_seq_lens=self.slot_last_seq_lens,
            row_to_slot=self.row_to_slot,
            token_to_slot=self.token_to_slot,
            seqused_fp4=self.seqused_fp4,
            seqused_residual=self.seqused_residual,
            promotion_mask=self.promotion_mask,
            decode_row_indices=self.decode_row_indices,
            decode_count=self.decode_count,
            active_row_mask=self.active_row_mask,
            error_code=self.error_code,
        )
        n, t = m.num_reqs, m.num_actual_tokens
        return ControlOutputs(
            row_to_slot=self.row_to_slot[:n],
            token_to_slot=self.token_to_slot[:t],
            seqused_fp4=self.seqused_fp4[:n],
            seqused_residual=self.seqused_residual[:n],
            promotion_mask=self.promotion_mask[:n],
            decode_row_indices=self.decode_row_indices,  # 固定容量，不动态切
            decode_count=self.decode_count,
            active_row_mask=self.active_row_mask,
            error_code=self.error_code,
        )
```

`launch_control_kernel` 的逐项语义必须按 §6.2 实现。特别注意：

- `query_len[row] = query_start_loc[row+1] - query_start_loc[row]` 在 device 算；
- `query_len > 1 and seq_len > query_len` → `UNSUPPORTED_CONTINUATION`；
- 同 key 且长度连续 → 复用 slot；
- 同 key 但长度不连续 → 物理 block id 已被新请求复用，重置 generation；
- 不在当前 key 集合中的 slot → `FREE_KEY`；
- `seqused_fp4` / `seqused_residual` 按 §3.2 推导；
- `promotion_mask = seq_lens % PAGE_SIZE == 0`；
- decode row 在 device 上 compact 到固定容量 `decode_row_indices`；
- `active_row_mask[i] = (i < decode_count)`，unused index 填 0；
- 禁止清空整块 per-layer `tail_k/v`；只依靠有效长度和后续覆盖。

`error_code` 只用于 debug 定位。production 必须在消费 metadata 的 device
kernel 入口做 gate/assert，不能每步把 error word `.item()` 回 host。

#### `src/nvfp4_vllm/runtime.py` — S4 / S6

builder 与 `AttentionImpl` 没有直接对象引用，不能把 tail 只存在 builder。
第一次 `do_kv_cache_update` 时，从 `ForwardContext.no_compile_layers` 找齐本模型的
NVFP4 attention modules，创建一个共享 runtime，并把同一个对象绑定回每层 impl：

```python
@dataclass
class RuntimeState:
    tail_k: torch.Tensor       # [L, 8, 128, H_kv, D]
    tail_v: torch.Tensor
    cache_views: tuple         # 每层四个 cached views
    cache_ptrs: torch.Tensor   # device uint64 [L, 4]，bind 时上传一次

    @classmethod
    def bind_once(cls, device) -> "RuntimeState":
        ctx = get_forward_context()
        modules = sorted_nvfp4_attention_modules(ctx.no_compile_layers)
        existing = modules[0].impl.runtime
        if existing is not None:
            return existing

        shape = (len(modules), MAX_SLOTS, PAGE_SIZE, H_KV, HEAD_DIM)
        views = tuple(
            layout.carve(module.kv_cache[0], ...) for module in modules
        )
        ptrs = [[tensor.data_ptr() for tensor in layer] for layer in views]
        state = cls(
            tail_k=torch.empty(shape, dtype=torch.bfloat16, device=device),
            tail_v=torch.empty(shape, dtype=torch.bfloat16, device=device),
            cache_views=views,
            cache_ptrs=torch.tensor(ptrs, dtype=torch.uint64, device=device),
        )
        for layer_idx, module in enumerate(modules):
            module.impl.runtime = state
            module.impl.layer_idx = layer_idx
        return state
```

伪码里的 `H_KV/HEAD_DIM` 从 impl 校验一致后取，不用全局常量；`kv_cache[0]`
按 vLLM 实际容器形状由 S1 probe 修正。这里的关键合同是：

- `tail_k/v` 各只有 **一次连续 allocation**；
- 每层 impl 只写 `runtime.tail_{k,v}[layer_idx]` 的 view；
- `layout.carve()` 与跨层 pointer/view table 只在 bind/rebind 时做一次；唯一一次
  host→device pointer upload 不计入 steady-state；
- runtime 挂在本模型的 module/impl 上，不用进程级 singleton，避免同进程多 engine
  或多 rank 串状态；
- promotion 可直接把 `L` 作为 kernel grid 维度，不需要 Python layer loop。

#### `src/nvfp4_vllm/impl.py` — S2 / S6 / S7

三个职责：

1. `do_kv_cache_update`：本层新 token 写尾巴；prefill 的满页 qpack 进 vLLM block
2. `forward`：decode 行走 `fp4_decode`，prefill 行走 cache-free varlen

#### `src/nvfp4_vllm/promote.py` — S8

```python
def launch(metadata, runtime) -> None:
    """Design §5.3. Exactly one fixed launch at last-layer forward end."""
    quantize_promoted_pages_indexed(
        source_k=runtime.tail_k,
        source_v=runtime.tail_v,
        source_slots=metadata.residual_page_ids,
        promotion_mask=metadata.promotion_mask,
        dest_block_table=metadata.fp4_page_table,
        seq_lens=metadata.seq_lens,
        cache_ptrs=runtime.cache_ptrs,
        error_code=metadata.error_code,
    )
```

**顺序不能错**：本层 attention 跑完 → 才 promote。
因为本步的 metadata 说「这一页还是 BF16 尾巴」，全部 32 层都按这个读。

`quantize_promoted_pages_indexed` 是新的 indexed/in-place qpack API：

- kernel 内按 `source_slots[row]` 算 BF16 源地址；
- 按 `dest_block_table[row, seq_len/P-1]` 算 FP4 目标地址；
- `promotion_mask[row] == False` 的 row 完全不读写；
- layer 是 grid 维度，不在 Python 里循环 32 层；
- K/V 可以是两个固定 launch；不能每层各发 K/V 两个 launch；
- 不允许 `tail[:, slots]` 高级索引 materialize page batch；
- promotion 后不 `zero_()` tail，下一页按有效长度覆盖。

这样消除了旧 profile 中可能重新出现的 `2 × L × N_prom` BF16 page gather。

### 10.4 已知的坑

1. **`get_name()` 必须返回 `"CUSTOM"`**，否则 `attention.py:434` 的
   `AttentionBackendEnum[...]` 直接 `KeyError`。
2. **`do_kv_cache_update` 在 attention 之前调用**，不是之后。
   promotion 不能放在这里。
3. **`m.seq_lens` / `block_table_tensor` 是 GPU 张量**。production `build()`
   禁止 `.cpu()` / `.item()` / `.tolist()`；使用 S4 control kernel。
4. **`num_computed_tokens_cpu` 是废弃的 property 不是字段**
   （`backend.py:522-528`）。`seq_lens_cpu_upper_bound` 在禁用 spec decode 时
   是精确 CPU shadow，但 production 不需要它；只用于 debug 对拍。
5. **`layer.layer_name` 只在 `forward`/`do_kv_cache_update` 的参数里拿得到**，
   `__init__` 没有。层号要用
   `vllm.model_executor.models.utils.extract_layer_index` 解析。
6. **`finished_req_ids` 拿不到**，见 §6.2 的缺席回收方案。
7. **scale 张量可能是 swizzled 布局**，别手算区域字节数，
   用 `layout.region_specs` 探。
8. **region-major 布局的前提是 vLLM 不搬 block 字节**。prefix caching、
   KV connector 和 KV offload 都必须拒绝；打开任一个前先切 block-major。
9. **不要用动态 `nonzero()` 决定 promotion/decode launch**。固定容量 scratch
   + device mask 是零同步合同的一部分。
10. **carved KV views 和跨层 pointer table 只能初始化/重绑时构造一次**，
    不能在每层每步重复 `layout.carve()`。

## 11. Bookkeeping 开销预算与优化优先级

### 11.1 旧实现的实测基线

旧 profile workload：`K=8, L=32, 64 decode tokens, 5 promotions`。
NVFP4 相对 BF16 的 bookkeeping 增量是：

```text
+8.537298 ms Self-CUDA
+2,616 CUDA events
```

来源：`nvfp4_attn/docs/kernel_new/docs/3.bookkeeping_overhead.md:56-106`。
11 个 event family 的时间不能直接相加成 wall-time 收益；这里只拿它们定位结构。

| 旧 event family | 旧增量 | 新设计状态 |
|---|---:|---|
| INT metadata index-select | +2.151698 ms / +512 | `PreGroupedViews` 四次 gather 结构性删除；由 1 次/step control kernel 替代 |
| Pageable DtoH | +1.720813 ms / +494 | v1 的自定义 steady-state 热路径目标为 **0** |
| CatArray | +1.426139 ms / +64 | **不会自动消失**；prefill 必须用 indexed/descriptor qpack 才能清零 |
| BF16 page index-select | +0.859586 ms / +320 | 旧 vLLM BF16 pool gather 删除；promotion 必须用 indexed qpack，防止从 tail 重新 materialize |
| Pageable HtoD | +0.613995 ms / +363 | views 双写删除；GPU slot control 后 custom metadata upload = 0 |
| DtoD | +0.611106 ms / +380 | count staging 删除；Q scratch/repack 等执行流量另算 |
| Pinned DtoH | +0.608677 ms / +180 | views scalar sync 删除；trusted fast path 必须让 wrapper `.item()` 归零 |
| integer add/sub | +0.296326 ms / +158 | 长度算术保留但融合进 1 次 control kernel |
| `index_kernel` | +0.176667 ms / +70 | row/destination selection 仍需要，但要融合进 control/indexed qpack |
| BF16 direct copy | +0.214558 ms / +64 | tail 写是业务数据；prefill 临时 copy 不允许换个 symbol 继续存在 |
| tagged `index_put` | +0.040257 ms / +11 | tag/state transition 完全删除 |

### 11.2 相对官方 vLLM NVFP4 的下界

官方 FlashInfer/trtllm-gen 路径：

- cache shape 直接是 `(num_blocks, 2*H_kv, P, 72)`；
- K/V 每个 token 直接量化写入；
- K/V data/scale 通过零拷贝 `split/as_strided` 暴露；
- 没有 BF16 tail、slot allocator、promotion 或第二套 page state。

它仍然有 stock vLLM 的 indptr/page-indices/last-page-length metadata，不能说
“绝对零 bookkeeping”；但 NVFP4 相对 stock backend 基本没有额外 page-state
bookkeeping。因此它是我们的下界。

我们的增量分两类：

**recent-BF16 设计固有：**

```text
固定 tail memory = 8 slots × 16 MiB = 128 MiB

每新 token/layer 的 cache write:
BF16 tail = 2 × 8 × 128 × 2 B = 4096 B
官方 FP4 = 2 × 8 × (64 data + 8 scale) B = 1152 B
差值      = 2944 B/layer/token
32 层     = 94,208 B ≈ 92 KiB/token
```

promotion 还需要读 BF16 tail 再写 FP4。这是 recent-BF16 的必要数据路径，
不是 bookkeeping bug。

**实现选择，可消除：**

- builder 的 DtoH/HtoD；
- Python slot map / request loop；
- promotion host branch；
- 每层 `_check_device_values().item()`；
- 每步重复 `layout.carve()`；
- Q scratch 的反复 allocate/zero；
- GQA scale 的 `take + index_copy_` repack；
- promotion/prefill 的 page materialization。

### 11.3 优化顺序

#### P0 — v1 必须完成：零同步 control path

1. S4 once-per-step GPU control kernel；
2. S7 trusted metadata fast path，删掉 production wrapper 的 128–160 次/step
   host scalar read；
3. S8 device `promotion_mask` + 固定 launch；
4. cache carved views 与 pointer table 缓存一次；
5. 不清零 tail，只由有效长度约束读取。

P0 没完成，不能进入 S10 性能对比。

#### P1 — v1 profile gate 前完成：indexed/in-place qpack

promotion qpack 直接接收：

```text
source_tail_base
source_slot_ids
destination_block_ids
promotion_mask
```

kernel 内算地址，不允许 `tail[:, slots]` / `index_select` 生成 contiguous page
batch。prefill qpack 同理接受 source descriptors/offsets，不能用 `torch.cat`。

目标是让旧 profile 的：

```text
320 BF16 page gathers
64 CatArray
64 BF16 direct-copy materialization
```

在新 trace 中全部为 0；只把它们换成另一类 DtoD copy 不算完成。

#### P2 — profile 证明后再做：Q 路径

当前 standalone wrapper 每层会分配/清零 padded BF16 Q、FP4 Q 和 scale scratch，
GQA scale 还会 `take + index_copy_`。优化方向：

- 按 `max_num_seqs=8` 预分配 persistent Q/output scratch；
- Q quantizer 直接写 kernel 要的 GQA scale layout；
- 用 byte-equality 和现有 `test_quantize_query.py` 守住布局。

这不是 page bookkeeping，只有 profile 显示它占比明显才做，避免提前改 kernel。

### 11.4 S10 profile 硬门槛

对 steady-state decode 的 custom delta：

```text
DtoH/HtoD attributable to nvfp4_vllm = 0
aten::_local_scalar_dense / .item()  = 0
control kernel                       = 1 / step
control work                         = once-per-step, not once-per-layer
promotion launch                     = fixed per step, no host branch
layout.carve                         = 0 / step（只在初始化/重绑）
BF16 promotion gather                = 0
CatArray / prefill materialization   = 0
```

同时记录：

- total CUDA events、Self-CUDA、wall latency；
- BF16 graph / BF16 eager / NVFP4 eager 三组；
- tail write 与 promotion payload 流量（业务数据）单独列出，不混进 bookkeeping；
- 如果某类 event 下降但 total/wall 不改善，不宣称优化完成。
