# NVFP4 KV Cache 的 vLLM 集成：v1 设计

本文取代 `1.vllm_tag_redesign.md` 作为实现依据。那份文档描述的是旧仓库
（`nvfp4_attn`）双池架构下的优化路线；v1 换了内存模型，它的大部分结论不再适用。
第 8 节说明哪些还有效。

## 1. 决策摘要

| # | 决策 | 依据 |
|---|---|---|
| D1 | Out-of-tree 包，注册 `CUSTOM` backend；非必要不改 fork | vLLM 官方扩展机制 |
| D2 | **vLLM 的 paged cache 就是 FP4 池**；BF16 尾巴在我们自己的 per-slot buffer | §2 |

## 2. 反转：vLLM 的 block 就是 FP4 页

### 2.1 旧仓库为什么会更费内存

旧架构里 vLLM 拥有 BF16 blocks，FP4 池是另开的、在 vLLM 记账之外的一块内存。
vLLM 仍然按 `gpu_memory_utilization` 把显存填满 BF16 blocks，FP4 池是净增量。
结果是用了 FP4 反而比纯 BF16 更费内存。

### 2.2 v1 的做法

反过来：**vLLM 的 paged cache 直接存 FP4**，并且如实告诉 vLLM 页有多大。
BF16 尾巴不进 vLLM 的 block，住在我们自己的固定 buffer 里。

以 Llama-3.1-8B（`L=32, H_kv=8, D=128, P=128`）为例：

```text
nvfp4_kv_cache_full_dim(128) = 128/2 + 128/16 = 72 字节/token/头

FP4  页 = 2 × 128 × 8 × 72  × 1 = 147,456 字节/层   (144 KiB)
BF16 页 = 2 × 128 × 8 × 128 × 2 = 524,288 字节/层   (512 KiB)
比值 = 3.556×
```

同样的显存预算下 vLLM 会分配约 3.56 倍的 block，调度器自动接纳更长的上下文。
不需要 `kv_cache_memory_bytes` 之类的手工干预——vLLM 的页大小记账是唯一真相来源。

BF16 尾巴 buffer：

```text
每 slot = P × H_kv × D × 2字节 × 2(K,V) × L
        = 128 × 8 × 128 × 2 × 2 × 32 = 16 MiB
总量 = max_num_seqs × 16 MiB
```

**注意 `max_num_seqs` 因此变成一个显存旋钮**：vLLM 默认 256，那就是 4 GiB 的隐形开销。

**v1 定为 8**（128 MiB）。选 8 而不是 1，是因为多行 decode 路径
（批量 metadata、slot 分配与复用）正是集成 bug 最容易藏的地方，
而 kernel 测试虽然覆盖了 multi-batch，集成层没有。
e2e 测试要相应地批量跑，所以 `NVFP4_GSM8K_MAX_NUM_SEQS` 的默认值已经从 1
改成 8（S0）——留在 1 会让这条路径完全测不到。以后要放大只是改个 buffer 尺寸。

### 2.3 单缓冲就够

promotion 时先读尾巴、qpack 写出 FP4，再把新 token 写回同一块缓冲。
读写有先后，不需要双缓冲。

### 2.4 实际量化的是 Q/K/P/V，不只是 Q/K

准确的数据路径是：

```text
FP4 prefix:
    FP4 Q × FP4 K
    → softmax
    → P 量化为 FP4
    → FP4 P × FP4 V

recent tail:
    BF16 Q × BF16 K
    → BF16 softmax/P
    → BF16 P × BF16 V

最后在线合并两部分的输出与 LSE。
```

- Q/K 沿 `head_dim` 每 16 个元素一组做 block-scaled NVFP4；
- V 沿 **token 轴**每 16 个 token 一组；
- P 也在 FP4 prefix 分支里量化。

对应代码证据：`fp4_decode_kernel.py` 的 `quant_qk` / `quant_pv` 两条路径，
以及 `quantize_kv_kernel.py` 中 V 的 K-major（token-contiguous）布局。

因此 bookkeeping 的根因不是 Q 量化，也不是 P 量化，而是 **V 沿 token
轴量化不能处理半页**：recent token 必须先留在 BF16 staging page，填满后再
promotion。Q/P 量化没有跨 step 状态，只带来当前 wrapper 的 scratch/repack
执行开销。

## 3. 不需要 dtype tag

### 3.1 判据

> 当且仅当一页的精度取决于**无法从 `(页索引, seqused)` 推导出来的运行时历史**时，
> 才需要存储 per-page tag。

tag 是一个物化的事实；只有当这个事实推不出来时，它才值得存。

### 3.2 v1 的推导

```python
n_fp4    = (seqused - 1) // P     # 页 [0, n_fp4) 是 FP4，在 vLLM 的 block 里
residual = ((seqused - 1) % P) + 1  # 尾巴，在 per-slot buffer 里
```

页 `n_fp4` 是唯一的 BF16 页，且它永远不在 vLLM 的 block 里。
于是 tag 存的信息量为零。

这不是新发明的方案：`tests/kernel/test_fp4_decode_correctness.py:260-261`
里的 fixture 用的就是逐字相同的两行。**kernel 从设计之初就假定调用方这么算**，
`seqused_fp4` / `seqused_residual` 本来就是它的输入合同。
这是对「不需要 tag」的一个独立佐证。

旧架构需要 tag，是因为 FP4 池和 vLLM blocks 是两套独立的 id 空间，
一个逻辑页可能落在任意一边。反转之后不存在这种二义性。

### 3.3 连带消失的东西

`PreGroupedViews`、FP4 池分配器、pending/release ownership ledger、
`sp_id // 4` oracle 分叉、自定义 GC 与 vLLM teardown 之间的 double-free 风险，
以及 `1.vllm_tag_redesign.md` 的 Phase 1–3。

§4.1 的 tag-aware metadata kernel 退化成三个 elementwise op：

```python
fp4_page_ids     = block_table                      # 直接透传，无 gather
seqused_fp4      = ((seq_lens - 1) // P) * P
seqused_residual = ((seq_lens - 1) % P) + 1
has_bf16         = 可省略                           # v1 每行必有尾巴
residual_page_ids = row_to_slot                     # GPU control kernel 输出
```

### 3.4 多轮也推得出来

多轮的关键在于：**推导不需要知道 prefix cache 命中在哪里断开，
因为断开点两边都是 FP4**——命中的部分是上一轮写的，新算的部分是这一轮写的。

例：第一轮 prompt 900 + 生成 300 = 1200 token，页 7、8 在 decode 中 promote，
页 9（48 token）随请求结束丢弃。vLLM 缓存了 block 0-8（1152 token）。
第二轮 prompt = 1300，命中 1152，重算 148 个 token：

```text
n_fp4 = (1300-1) // 128 = 10
页 0-8  ← 缓存来的 FP4          ✓
页 9    ← 本次 prefill 填满，qpack 成 FP4  ✓
页 10   ← 20 个 token，进尾巴    ✓
```

丢掉的尾巴每轮最多 `W` 个 token，8B 模型上约 2 ms 的重算，可忽略。

这依赖 vLLM 只 hash 填满的 block（`kv_cache_utils.py` 的
`request_block_hasher`，注释 "We only hash full blocks"），
且单 KV cache group 时 `hash_block_size == block_size`，
所以命中一定落在页边界上，和 promotion 的粒度天然对齐。

### 3.5 什么情况下 tag 才该回来

- **位置性策略不需要**：例如「前 N 个 token 保持 BF16」（attention sink），
  仍然是 `(页索引, seqused)` 的函数，加个特例即可。
- **真正需要 tag 的**：FP4 页和 BF16 页可以**任意交错**。
  典型触发场景是「按运行时测量的误差/重要性决定每页精度」，
  或者「每轮结束保留一个 BF16 岛」（见 §7.3）。

即使到了那一步，也要先问：状态是不是仍然是一个**二分**（低精度前缀 + 高精度窗口）？
如果是，最多只需要**每序列一个 int32**（边界在第几页），而不是每页一个 tag。
只有真正任意交错才需要 per-page tag。

## 4. W = P

BF16 窗口长度和页大小之间没有自由度，被两个方向夹死。

### 4.1 `W ≥ P`：FP4 必须整页写

V 沿 token 轴打包（`[pages, heads, head_dim, page_size/2]`），
且 kernel 接口要求 `seqused_fp4` 是页大小的整数倍。
所以必须先在 BF16 里攒够一整页才能量化写出去。
**BF16 窗口是暂存区（staging），不是保护区（protection）。**

### 4.2 `W ≤ P`：promotion 的触发条件必须是 block 内在属性

`W > P` 时，BF16 窗口会占据 `W/P` 个 block，其中除最后一个外都是**填满的**。
此时出现两个互相关联的问题：

**（a）promotion 时机没有唯一答案。**
`W = P` 时触发条件是「这个 block 填满了」，是 block 内容的属性，谁看都一样。
`W > P` 时触发条件是「序列已走过这个 block 之后 W 个 token」，是**读者位置**的属性。
而 prefix caching 下同一个 block 被多个序列共享，各自走的距离不同。

**（b）格式变成读者的函数。**
同一个物理 block，`seqused` 较小的请求认为它在窗口内（BF16），
`seqused` 较大的请求认为它已滑出（FP4）。两边推导都对，但字节只有一份。

即便把 BF16 放在自己的 buffer 里（block 只写 FP4，不存在格式变更），
`W > P` 仍然会把 promotion 竞态从 1 步拉宽到 `W - P` 个 token：
vLLM 按 token 数判定 block 满了就对外缓存，而我们要等它滑出窗口才写 FP4。

**结论**：`W = P` 是唯一让「离开 BF16 窗口」和「block 填满」重合的取法，
而「填满」是唯一 block 内在的、共享安全的触发条件。

### 4.3 P 的取值

`P = W = 128` 是当前 kernel 的写法（`quantize_kv_kernel.py` 的 `PAGE_SIZE = 128`）。

`P = W = 16` 在维度上也成立（V 变成 `[pages, heads, 128, 8]`，
恰好一个 scale 组，因为 `SF_VEC_SIZE = 16`），**且量化质量完全相同**——
NVFP4 的 scale 组本来就是 16 个 token，`P` 只决定一页装几个 scale 组。
它的收益是尾巴 buffer 从 16 MiB/slot 降到 2 MiB/slot、prefix cache 粒度细 8 倍；
代价是 block table 大 8 倍、kernel 多迭代 8 倍页数、高精度近期窗口短 8 倍。

v1 用 128，`P` 不做成运行时参数（kernel 里是编译期常量）。

## 5. Promotion 时机：本步最后一层之后

### 5.1 三个候选位置

| 位置 | 数据是否安全 | 竞态窗口 | 是否需要改 fork |
|---|---|---|---|
| 第 N 步 layer 0 | ✗ layer 1..L-1 还没写 boundary token | — | 否 |
| 第 N+1 步 layer 0（旧仓库做法） | ✓ | 1 步 | 否 |
| **第 N 步 layer L-1 的 attention 之后** | ✓ | 0 | 否 |

旧仓库用的是第二种（`vllm_hook.py` 里 `_unified_step_promotion_done`
在每步第一层复位，promotion 只在该步跑一次，内部对所有层循环）。

### 5.2 为什么最后一层可行

- 此时 32 层都已写完本步的 boundary token → 数据安全
- 本层自己的 attention 已经跑完 → 它这一步仍需把该页当 BF16 读
- vLLM 的 block caching 发生在整个 model forward 之后 → 我们赶在它之前写完 FP4，
  竞态归零
- backend 知道自己是第几层，不需要 patch fork

### 5.3 步内顺序

```text
第 N 步 build()：
    seq_lens = 1024 → n_fp4 = 1023//128 = 7
    页 0-6 FP4，页 7 是尾巴（128 token）      ← 全部 32 层共用这份 metadata

layer 0 .. L-2：写 KV 到尾巴 → attention
layer L-1     ：写 KV 到尾巴 → attention → **promotion**
                  条件 seq_lens % P == 0
                  对全部 L 层：qpack 尾巴 → vLLM block (seq_lens/P - 1)
                  重置尾巴 buffer

第 N+1 步 build()：
    seq_lens = 1025 → n_fp4 = 1024//128 = 8
    页 0-7 FP4（页 7 刚 promote），页 8 是尾巴（1 token）  ✓
```

### 5.4 限制

`PP > 1` 时最后一层不一定在本 rank 上，需要另行处理。v1 强制 `PP == 1`。

### 5.5 promotion 不允许 host-side 分支

promotion 条件 `seq_lens % P == 0` 必须在 GPU 上计算。最后一层后**每步固定**
发射 promotion kernel，由 device 上的目标页号决定哪些 row 真正 qpack：

```text
promotion_pages[row] = block_table[row, seq_lens[row]//P - 1]  跨界
                     = -1                                      否则
固定 launch → kernel 内按页号取舍 → 0 或多行 promotion
```

禁止下面这种写法：

```python
rows = (seq_lens % P == 0).nonzero()
if rows.numel() == 0:       # 动态 nonzero / host 控制流
    return
```

这会把 promotion 变成每步一次固定 launch，其中约 127/128 的 step 只做 mask
检查，但换来：

- promotion 路径没有 DtoH 或 Python 分支；
- launch 数与 batch 内容无关；
- 将来可以进入 CUDA graph。

v1 仍强制 `enforce_eager=True`，因为完整 graph 兼容还取决于其他 kernel 和 buffer
地址稳定性，不能仅凭 promotion 谓词化就宣称已经支持。S10 同时测
BF16 graph、BF16 eager、NVFP4 eager，把 graph 代价与量化代价分开。

## 6. 实现约定

### 6.1 护栏（一律 fail closed）

| 检查 | 原因 | 落点 |
|---|---|---|
| `block_size == 128` | V 量化组跨页会读不了；见 §4 | `supports_block_size` |
| SM100 | kernel 只为 SM100 编译 | `supports_compute_capability` |
| `head_size == 128` | 同上 | `supports_combination` |
| `kv_transfer_config is None` | connector 会把 block 字节发给一个不认识 NVFP4 页布局的对端 | `supports_kv_connector` |
| `enable_prefix_caching == False` | v1 不支持 continuation prefill；见 §7 | `guards.check_supported` |
| `pipeline_parallel_size == 1` | promotion 挂在最后一层；见 §5.4 | `guards.check_supported` |
| `cudagraph_mode == NONE` | v1 尚未验证完整 CUDA graph；promotion 本身已 host-branch-free | `guards.check_supported` |
| `max_num_seqs <= 8` | 尾巴 buffer 固定 128 MiB；不接受 vLLM 默认 256 | `guards.check_supported` |
| `cache_config.kv_offloading_size is None` | KV offload 同样按 block 地址/大小搬字节 | `guards.check_supported` |
| `enable_chunked_prefill == False` | 被切开的 prompt 第二块要在 FP4 前缀上续写；见 §7.1 | `guards.check_supported` |
| `long_prefill_token_threshold == 0` | 即使关了 chunked prefill，这个阈值仍会切长 prompt | `guards.check_supported` |
| `speculative_config is None` | decode 每步只验证一个 query token；见 §7.4 | `guards.check_supported` |
| `parallel_config.use_ubatching == False` | 每个 ubatch 各自 build 一次 metadata，slot 表一步会走两次；见 §6.2 | `guards.check_supported` |
| `kv_cache_dtype_skip_layers` 为空 | 分层 dtype 会切出多个 KV cache group，各自一个 builder，slot 表一步会走多次；而且 vLLM 会去清零新分的 block | `guards.check_supported` |
| 报告 `num_computed_tokens > 0 且 query_len > 1` | 上面三条的运行期兜底 | control kernel `error_code`（S4） |

`prefix_match_unit == block_size` 不单独设护栏：它只在 prefix caching 开着时
才有意义，而 prefix caching 本身已经被拒。

前四条是 backend 能力，与 `kv_cache_dtype` 无关，交给 vLLM 的
`supports_*` hook；其余是引擎配置，只在 `kv_cache_dtype == "nvfp4"` 时生效。
分界的原因见 S3。

**关于 TP**：`TP > 1` 不设护栏。KV 头分片后每个 rank 的尾巴 buffer 按比例变小，
而每个 rank 都持有全部层，promotion 挂最后一层照常成立，所以设计上应当直接可用。
但 v1 **不测它**，算未验证状态。

### 6.2 GPU-resident slot control plane

BF16 尾巴需要跨步跟着**请求**走，而 vLLM 的 batch 行号跨步不稳定
（`InputBatch` 在请求结束时会压缩行）。所以需要一个稳定的 key。

**不能用 request id。** 这一点是查证过的，不是猜测：`CommonAttentionMetadata`
（`v1/attention/backend.py:411-488`）里**完全没有字符串 request id**，只有 batch
索引；`finished_req_ids` 只存在于 `SchedulerOutput`
（`v1/core/sched/output.py:219-222`），`ForwardContext`、
`AttentionMetadataBuilder.build()`、`AttentionImpl.forward()` 三处都拿不到。

**改用 `block_table_tensor[row, 0]` 作为 key**，也就是逻辑页 0 的物理 block id。
理由：

- 它在请求的整个生命周期内不变（prefix caching 关闭，没有 CoW）
- 它在所有存活请求之间唯一（block 被独占持有）
- 它每步都在 `CommonAttentionMetadata` 里，不需要任何额外管道

slot 表必须常驻 GPU，不使用 Python `dict` / `set`。表宽等于 `max_num_seqs`，
一个 CTA 就能完成所有工作。persistent state：

```text
slot_keys       int32 [S]   # -1 表示从未用过
slot_last_seq   int32 [S]   # 该 slot 上一次记录的 seq_len
slot_last_seen  int64 [S]   # 上一次被认领的 step，LRU 用
step            int64 [1]
```

once-per-step control kernel 输入：

```text
block_table        int32 [num_reqs, max_blocks]   # 只读第 0 列，按 stride 取
seq_lens           int32 [num_reqs]
query_start_loc    int32 [num_reqs + 1]
num_reqs, num_actual_tokens                # host 标量，caller 本来就有
```

读的是 vLLM 原本的二维 block table 而不是 `block_table[:, 0]`：后者是 stride
视图，要么在 kernel 里按 stride 取，要么每步 `.contiguous()` 复制一次。选前者。

输出到 persistent scratch：

```text
row_to_slot              int32 [S]
token_to_slot            int32 [num_actual_tokens]
seqused_fp4              int32 [S]
seqused_residual         int32 [S]
promotion_source_tokens  int32 [S]   # slot × P，尾巴在 tail buffer 里的起点
promotion_pages          int32 [S]   # 目标 block id，不跨界为 -1
decode_row_indices       int32 [S]   # 紧凑化的 decode 行，尾部填 -1
decode_count             int32 [1]
active_row_mask          bool  [S]
error_code               int32 [1]   # 粘性位标志，debug 用
```

同一 kernel 内完成：

1. 用 `block_table[row, 0]` 查找/分配 slot；
2. 按 LRU 挑本步无人认领的 slot 给新 key；
3. 用 `seq_len` 连续性检测 key 复用与丢失的 slot；
4. 推导 `seqused_fp4` / `seqused_residual`；
5. 展开 `token_to_slot`；
6. 生成 promotion 的源偏移与目标页号，以及紧凑的 decode 行列表。

这样不需要 `finished_req_ids`、DtoH、Python 逐请求循环，也不需要把 Python slot
list 再 HtoD。

**回收是惰性的，不是「缺席即死亡」。** 「缺席」不能当死亡看：token budget 用完
时调度器会把活着的请求整步跳过，按缺席释放会丢掉它最近的 K/V，而这是唯一一份。
所以 slot 只在**新 key 需要**时才被拿走，牺牲者是最久没被认领的那一个。
代价是被跳过太久的请求可能真的被挤掉——这一条由 `error_code` 精确报出来
（有 computed token 却匹配不到 slot），不再是静默错误。

**「活着」的判据是 `seq_len > 0 且 key != 0`，不是 `row < num_reqs`。** 两个条件
缺一不可，各挡一类假行：

- **padding 行**：full CUDA graph 把 batch 补齐到捕获宽度，vLLM 只把补出来的行的
  `seq_lens` 清零（`gpu/input_batch.py:258-262`），block table 那一行还留着
  `condense()` 之前的内容。按行数算存活会把 slot 发给几步之前就结束的请求。
  cudagraph 现在被护栏挡着，这条是为了让护栏放开时 kernel 本身是对的。
- **dummy batch 行**：引擎启动时会跑一次 profile forward 来量峰值显存，那一批是
  满宽的（`max_num_seqs` 行、每行 `max_num_batched_tokens / num_reqs` 个 token），
  但 block table 是没写过的零缓冲，所以每行的 key 都是 0。block 0 是 vLLM 的 null
  block，`BlockPool.__init__` 开机就把它从空闲队列里 pop 掉、永不分配
  （`v1/core/block_pool.py:187-191`），所以 `key == 0` 就等于「这行不是请求」。
  少了这一条，profile run 会白占满 slot 表，并且因为八行同 key 而误报
  `ERR_DUPLICATE_KEY`——sticky flag 一置上，`error_code` 就再也不能用来判断健康。

**同一步里两行拿到同一个 key** 在 vLLM 里不可能发生（一个物理 block 不会同时属于
两个未结束的请求），但 kernel 的归约必须在这种输入下仍然给出范围内的答案：匹配用
`min` 而不是「匹配项索引求和」，slot 写回也取行号最小的那一行，然后由
`ERR_DUPLICATE_KEY` 把这一步标出来。求和会答出一个不存在的 slot 号，然后越界写。

**同一步里两行拿到同一个 key** 在 vLLM 里不可能发生（一个物理 block 不会同时属于
两个未结束的请求），但 kernel 的归约必须在这种输入下仍然给出范围内的答案：匹配用
`min` 而不是「匹配项索引求和」，slot 写回也取行号最小的那一行，然后由
`ERR_DUPLICATE_KEY` 把这一步标出来。求和会答出一个不存在的 slot 号，然后越界写。

四个必须处理的边界：

1. **block 复用**：请求结束后 block 0 可能立刻被新请求拿去用，于是新请求
   撞上同一个 key。这是对的：新主人接手这个 slot，它 `num_computed_tokens == 0`，
   不会读到旧内容。用 `seq_lens` 连续性做校验——匹配上却接不上、而且带历史，
   说明前提被破坏了，报 `error_code`。
2. **抢占**：V1 的抢占是「释放 block 重算」，所以被抢占的请求下次出现时
   `block_table[:, 0]` 已经变了，天然走「新请求」分支。
3. **被跳过的请求**：整步缺席不释放 slot，回来时按 key 找回原 slot。
4. **稳态不丢 slot**：所有活着的请求每步都被调度时，它们的 slot 每步都被认领，
   LRU 只可能挑到已结束请求的 slot。这是一条测试断言，不只是论证。

### 6.3 必须钉死的实现细节

`seq_lens` 在我们读取时**是否已包含本步要写入的 token**。
差一个 token，§3.2 的整套推导就错位一页。
错了的表现是「精度偶尔掉一点」，极难定位，所以要在写代码前先验证。

**已验证（S5）：包含。** 实际在跑的是 V2 model runner
（`gpu_worker.py` 打印 `Using V2 Model Runner`，走 `v1/worker/gpu/model_runner.py`，
不是 `v1/worker/gpu_model_runner.py`）。`v1/worker/gpu/input_batch.py:265-273`：

```python
num_computed_tokens = tl.load(num_computed_tokens_ptr + req_state_idx)
query_len = end - start
seq_len = num_computed_tokens + query_len
tl.store(seq_lens_ptr + req_id, seq_len)
```

同一个 kernel 把 `num_reqs` 之后的行清零（`:258-262`），我们的整宽 scratch 采用
同样约定。所以 control kernel 里 `computed = seq_len - query_len`。

**没有额外的运行期断言，靠 `ERR_SLOT_LOST` 兜住。** 原计划是在第一次 `build()` 时
用 `CommonAttentionMetadata` 上的 host 副本比对一次，但 V2 runner 构造
`CommonAttentionMetadata` 时根本不填 `_seq_lens_cpu` 和 `_num_computed_tokens_cpu`
（`gpu/attn_utils.py:538-556`），两个字段恒为 `None`，那个断言是死代码。

不另找数据源，是因为语义翻转本来就会触发已有的检测：全新 prefill 在翻转后
`seq_lens == 0`，被当成 padding 行跳过、拿不到 slot；下一步 decode 时它
`computed = seq_len - 1 > 0` 却匹配不到任何 slot，正是 `ERR_SLOT_LOST` 的定义。
也就是说第一个请求的第二步必然报出来，只晚一步，且不需要任何额外代码或 host 计算。
代价是它是 sticky flag，要靠 E2E 测试去读 `error_code`。

### 6.4 零 host-sync 合同

steady-state decode 中，我们新增的代码必须满足：

```text
0 × Tensor.cpu()
0 × Tensor.item()
0 × Tensor.tolist()
0 × 动态 nonzero 后的 Python 分支
0 × Python request/slot 循环
```

允许 Python 做的事情只有启动时配置、分配 persistent buffer、缓存 tensor views
和发射固定 kernel。每步的 request 生命周期、row→slot、长度拆分和 promotion
选择全部在 GPU 上。

当前 standalone wrapper 的 `_check_device_values()` 使用
`torch.any(...).item()`；带 residual + direct scatter 时每层最多 5 次，
32 层静态上限为 **160 次 host scalar read/step**。集成前必须提供 trusted
metadata fast path：

- shape / dtype / stride 继续在 host 校验（不读 device value）；
- value-range 检查只在 debug/test 模式启用；
- production metadata 完全由 §6.2 的 GPU control kernel 产生，不再逐层
  `.item()` 检查；
- debug 的错误必须 fail-stop，不能写一个无人读取的 flag 后继续 attention。

这个合同只约束我们相对 stock vLLM 新增的路径；vLLM 自身已有的 scheduler
CPU metadata 不计入增量，但也不得为了我们的 backend 新增一次往返。

## 7. v1 不做的事

### 7.1 Continuation prefill（多轮 + chunked prefill）

两者是同一个问题的两种外衣：**prefill 的 query 需要在已经量化成 FP4 的上下文上做 attention**。
stock FlashAttention 读不了 FP4。

解锁方式：**FP4 → BF16 dequant kernel**（现有 qpack 的逆），配一个单层 scratch buffer。
按层反量化后走 cache-free 的 `flash_attn_varlen_func`。

成本估算（8k 历史，Llama-3.1-8B）：

```text
反量化流量 ≈ 1.4 GB / 32 层  →  B200 上约 0.5 ms
从头重算 8k ≈ 131 TFLOP      →  约 120 ms
```

即反量化能拿到 prefix caching 几乎全部的收益，代价约 0.4%。
scratch 峰值内存约 4 MiB / 1k token（单层复用）。

一个 kernel 同时解锁多轮和长上下文。

### 7.2 长上下文

v1 的 prompt 上限由 `max_num_batched_tokens` 决定（必须单次 prefill 完）。
测试里设 16384，GSM8K 的 prompt 约 900 token，余量充足。
128k 需要 §7.1。

### 7.3 中间的 BF16 岛

「每轮结束不 promote，把尾巴留作 BF16 供下一轮复用」这个想法**不采纳**：

- 会在序列中间留下位置任意的 BF16 岛 → 这正是唯一真需要 per-page tag 的情形
- vLLM 一个 KV cache group 只有一个 page size，BF16 岛（524,288 字节）
  装不进按 FP4 尺寸分配的 block（147,456 字节）
- 放进自己的 buffer 则进不了 vLLM 的 prefix cache（cache 只能指向 vLLM 的物理 block），
  要复用就得自己再实现一套 hash → buffer 的缓存 + 引用计数 + 淘汰
  ——那等于把旧仓库的双池架构镜像着搬回来
- 每个岛 16 MiB，每轮一个，随对话轮数无上限增长
- 收益只有每轮省下约 2 ms 的重算

如果将来发现**质量上**必须在序列中间保留高精度页，这套成本才值得重新评估。

### 7.4 投机解码

回滚可能把 `seqused` 退到已 promote 的边界以下，需要反量化回 BF16
（依赖 §7.1 的 kernel），或者把 promotion 延后到投机窗口之外
（仍是位置性规则，不需要 tag）。

## 9. 实施计划

### 9.0 排序原则

1. **每一步做完系统都能跑、能测**，不存在「写了三天还没法验证」的阶段。
2. **最高风险的未知项排在最前**：如果页大小声明这条路走不通，整个内存模型要重来，
   宁可第一天就知道。
3. **先把管道跑通，再引入 FP4**。S2 结束时全链路已经通了但一个 FP4 字节都没写，
   这样后面出问题时可以确定是量化逻辑而不是集成管道。

### S1 — 页大小声明（最高风险未知项）

上一轮设计讨论结束时唯一悬而未决的问题，先解决它。

**要回答的三个问题**

1. `kv_cache_dtype="nvfp4"` 能不能拿到我们要的页大小？
   `FullAttentionSpec.real_page_size_bytes`（`v1/kv_cache_interface.py:203-218`）
   在 `is_nvfp4` 时用 `nvfp4_kv_cache_full_dim(head_size)`，
   `head_size=128` 时是 72，算出 `2 × 128 × 8 × 72 = 147,456` 字节/层。

2. 这个 dtype 还会连带触发什么？fork 里 FlashInfer 那条 NVFP4 路径要求
   trtllm-gen backend、FP8 query、FP8 输出缓冲
   （`v1/attention/backends/flashinfer.py:1977-1986` 等）。
   我们用自己的 backend，理论上不受影响，但需要逐一确认
   `config/cache.py`、`config/model.py`、`platforms/interface.py`、
   `model_executor/layers/attention/attention.py` 里对 `nvfp4` 的分支
   不会在引擎启动阶段拦下我们。

3. `get_kv_cache_shape` 返回什么形状？字节预算对得上（K_fp4 + K_sf + V_fp4 + V_sf
   合计也是 147,456），但内部排布和 upstream 不同。两个候选：
   - **block-major**：每个 block 内部依次放四个区域。符合 vLLM 的直觉，
     但四个区域各自跨 block 不连续，kernel 要处理 stride。
   - **region-major (SoA)**：整个张量先放所有 block 的 K_fp4，再 K_sf，再 V_fp4，再 V_sf。
     四个区域各自连续，kernel 拿到的就是四个正常张量。
     前提是 vLLM 不会把 block 当成连续字节去搬——关闭 prefix caching
     和 KV connector 之后应该成立，需要验证。

   S6 选了 block-major，理由见那一节。

**做什么**

`tests/e2e/test_kv_cache_memory.py`：在同一进程里先后构造 BF16 与 NVFP4 两个
引擎，从活的 model runner 上读 `page_size_bytes` 与实际分配的 KV 张量，比较两者
的 token 容量。做成常驻测试而不是一次性脚本，是因为这个比值就是整个项目的目的，
它必须是一条会失败的门槛，而不是一次手工观察。

**S0 已经测出的 BF16 分母**

`num_blocks` 的比值需要一个同配置的 BF16 对照。S0 那次 BF16 GSM8K 运行已经
把它顺带测出来了，S1 不必再启一次 BF16 引擎：

```text
配置：Llama-3.1-8B-Instruct，单卡 178.35 GiB，TP=1，L=32，H_kv=8，D=128
     gpu_memory_utilization=0.9，block_size=128，max_model_len=4096
     enforce_eager=True，enable_prefix_caching=False

Available KV cache memory: 143.57 GiB
GPU KV cache size:         1,176,064 tokens
num_blocks = 1,176,064 / 128 = 9,188
```

对账：BF16 每层页 `2×128×8×128×2 = 524,288` 字节，L=32 → 每 block 16 MiB，
`9,188 × 16 MiB = 143.56 GiB`，与日志一致。

于是 NVFP4 的期望值可以事先写死，而不是「约 3.5 倍」这种软目标：

```text
NVFP4 每 block = 32 × 147,456 = 4,718,592 字节 = 4.5 MiB
143.57 GiB / 4.5 MiB ≈ 32,670 blocks
比值 32,670 / 9,188 = 3.556
```

同一次 S0 运行还确认了 BF16 侧的准确率基线 **24/32 = 0.7500**（门槛 0.60）。
NVFP4 的 KV cache 内存额度不会和 BF16 完全相同（权重与峰值激活不变，但
profiling 的余量会有几十 MiB 级别的浮动），所以比对 `num_blocks` 时应当用
实际的 `Available KV cache memory` 重新折算，而不是直接除以 9,188。

**验收**

- 引擎能启动，不因 `nvfp4` dtype 报错
- `page_size_bytes == 147456`
- `num_blocks` 落在 32,670 附近，与 BF16 的 9,188 之比接近 3.556

**结果（已完成）**

```text
BF16 : page 524,288 B/layer,  9,188 blocks, 1,176,064 tokens, 143.56 GiB
NVFP4: page 147,456 B/layer, 32,720 blocks, 4,188,160 tokens, 143.79 GiB
page size ratio 3.5556 | token capacity ratio 3.5612
```

`page_size_bytes` 的比值 3.5556 是确定性的（`524288/147456 = 32/9`），
token 容量比 3.5612 略高，因为两个引擎各自 profile 出的可用显存差了 0.23 GiB。
这类抖动来自「权重 + non-torch 显存」那一项的测量，与 cache 格式无关，所以测试
用 3.0 作为下限而不是卡在 3.5556 上，同时单独断言 `page_size_bytes` 的比值精确。

引擎侧的 spec 也如预期：`FullAttentionSpec`、`dtype=torch.uint8`、
`kv_quant_mode=KVQuantMode.NVFP4`、`real_page_size_bytes == page_size_bytes ==
147,456`、`page_size_padded=None`、`indexes_kv_by_block_stride=False`，
每层张量是 `(num_blocks, 147456)` uint8，与我们 `get_kv_cache_shape` 的返回值逐字相同。

**测试本身踩到的坑**：两个引擎同进程先后构造时，第一个必须显式
`llm.llm_engine.engine_core.shutdown()`。vLLM 在 `EngineCore.__init__` 里
`gc.freeze()` 了启动期的分配（权重、KV cache），`del llm` + `gc.collect()`
根本看不到它们；`shutdown()` 里的 `gc.unfreeze()` 才是关键
（`v1/engine/core.py:751-755` 的注释明确说了这是为了 in-process 测试）。
测试因此在两次测量之间断言空闲显存已经恢复，否则比值测的是显存释放而不是页大小。

**第二个问题的答案：`nvfp4` 连带触发了什么**

vLLM 侧没有任何东西拦我们——FlashInfer 那条 trtllm-gen / FP8 query 的要求只挂在
FlashInfer backend 上，自定义 backend 完全不受影响。`nvfp4` 在
`CacheDType` 的合法值里，映射到 `torch.uint8`，`FullAttentionSpec` 自动带上
`KVQuantMode.NVFP4`，页大小走 `nvfp4_kv_cache_full_dim`。

真正需要处理的两处都在我们自己这边，且都源于「返回一个二维扁平字节 shape」：

1. `get_kv_cache_stride_order()` 必须与 shape 同秩。继承 FlashAttention 的
   四元 order 会在 `v1/worker/gpu/attn_utils.py:329` 的
   `assert len(stride_order) == len(shape)` 上炸，而那个 assert **不在**
   外层 `except (AttributeError, NotImplementedError)` 的捕获范围内。
   解法是在 `kv_cache_dtype == "nvfp4"` 时 `raise NotImplementedError`，
   让调用方退回恒等排列。不能无条件抛：FlashAttention 在 NHD 下的 order 是
   `(0, 2, 1, 3)`，抛了会改变 BF16 的物理布局，破坏 S2 的逐 token 一致性验收。
2. **KV cache 分配之后还有一次 dummy forward**，会打到
   `do_kv_cache_update`。继承来的 FlashAttention 版本假设 cache 是四维，
   `kv_cache.transpose(1, 2)` 直接 IndexError。

**layout 决定推迟到 S6**

`get_kv_cache_shape` 返回 `(num_blocks, 147456)` 的扁平字节视图，不承诺内部
排布——region-major 与 block-major 在 `page_size_bytes` 和 `num_blocks` 上给出
完全相同的数，所以这个决定不必在 S1 做。S6 真要写入时再定。已经查清的两条约束：

- **region-major**：四个区域各自 `is_contiguous()`，现有 kernel 接口一行不用改。
  但 `_decode.py:87` 的 `scales.storage_offset() != 0` 会拦住切片出来的
  K_sf / V_fp4 / V_sf（`flat[offset:offset+size]` 的偏移必然非零）。这个检查是
  保守的，它下面的 `as_strided` 在 `storage_offset=None` 时会沿用输入偏移、
  本身正确，所以放宽成只校验 stride 即可。
- **block-major**：四个区域跨 block 的 stride 是 147,456 字节，
  `_decode.py:499/510` 的 `is_contiguous()` 断言会全部失败，必须改 kernel
  的寻址让它接受 page stride。

S6 选的是 block-major，这两条约束都兑现了：contiguity 和 storage_offset 检查都
放宽，K/V 与 scale 的 page stride 变成显式参数。scale 那边还多出一件当时没查到的
事——kernel 内部会重建 layout，见 S6 的 S5.5 一段。

**如果走不通**

退路是自定义 `KVCacheSpec` 子类，但那需要改 `Attention.get_kv_cache_spec`
（fork 里它按 `kv_cache_dtype` 字符串硬编码分支），违反 D1。真到这一步要重新评估 D1。

### S2 — 直通 CUSTOM backend（已完成）

**做什么**

- out-of-tree 包 `src/nvfp4_vllm/`（S1 已建），通过 vLLM 的 plugin entry point 注册
- backend 继承 FlashAttention，**行为完全不改**
- 把 S0 拆掉的 NVFP4 arm 加回测试：`CUSTOM_ATTENTION_CONFIG = {"backend": "CUSTOM"}`
- **仍然用默认的 BF16 cache dtype**（见 §9.1）

**验收**

GSM8K 与 `FLASH_ATTN` **逐 token 一致**（greedy 且没有引入任何量化，
所以应当完全相同，不是「接近」）。

**为什么单列一步**

这一步把「插件 entry point 加载、backend 被正确选中、metadata 能构建、
forward 能被接管」全部验证完，而 FP4 风险为零。
此时 cache 形状和写路径都还是 vLLM 自己的，那两项要到 S6 才验证。

**结果**

```text
Using AttentionBackendEnum.FLASH_ATTN backend.   KV 143.57 GiB, 1,176,064 tokens
Using AttentionBackendEnum.CUSTOM backend.       KV 143.82 GiB, 1,178,112 tokens
GSM8K FLASH_ATTN 24/32 (0.7500) | CUSTOM 24/32 (0.7500)
32/32 条请求的 token id 序列逐个相同        1 passed in 102s
```

准确率与 S0 的 BF16 基线逐样本相同，说明换 backend 之后连中间输出都没变。

**注册走 entry point，测试不再手动 `register()`**

`pyproject.toml` 声明：

```toml
[project.entry-points."vllm.general_plugins"]
nvfp4_vllm = "nvfp4_vllm:register"
```

并把本仓库 editable 装进共享 env：
`uv pip install --python <vllm-nvfp4>/bin/python -e . --no-deps`。
`--no-deps` 是必须的，否则我们 `pyproject` 里的 pin 会去动共享 env 已经调好的
cutlass-dsl / tvm-ffi 版本（装 flash-attn-4 时踩过同一个坑）。

装进这个 env 不是妥协而是目的：BitKV 的 nvfp4 training 要 import
`nvfp4_decode_kernel`，两边本来就该共用一份。

`EngineCore.__init__`（`v1/engine/core.py:110`）会调 `load_general_plugins()`，
所以即使 `VLLM_ENABLE_V1_MULTIPROCESSING=0`，entry point 也走的是真实的
「发现 → 加载 → 注册」，不需要开多进程才能验证。测试里**不允许**再手动调
`register()`——那样这条声明会变成死的，退化回 S1 的临时办法。
`tests/e2e/test_kv_cache_memory.py` 里的那行手动注册据此一并删掉。

**没有加 attribution 断言**

vLLM 在这件事上已经是 fail-closed：显式指定 `backend: CUSTOM` 时，未注册会在
`AttentionBackendEnum.get_path()` 抛错，注册了但配置非法会在 `cuda.py:417` 抛
`ValueError`，**不存在静默回退到 FLASH_ATTN**。加上 S1 的内存测试断言
`page_size_bytes == 147,456`（这个数只可能来自 `NVFP4Backend`），
「CUSTOM 真被选中」已经有一条会失败的门槛守着，S2 再读一遍
`model_runner.attn_groups` 只是重复，还多绑一个 vLLM 私有属性。

**没有加 `GSM8K_MAX_ACCURACY_DROP`**

逐 token 相同严格强于任何准确率容差，此时加 drop 门槛只会削弱验收。
S6 之后 identity 不再成立，那时再建 drop 门槛。

**测出来的一个事实：两个 arm 的 `num_gpu_blocks` 本来就不同**

`9,188` vs `9,204`（143.57 vs 143.82 GiB）。差异来自「权重 + non-torch 显存」
那一项的 profiling 抖动，与 backend 无关。这是 identity 验收事先识别出的风险：
block 数不同若触发抢占/换出，两个 arm 的 batch 组成就会分叉，而 FlashAttention
不是 batch-invariant 的，greedy 也会选出不同 token。实测在这个规模下没有发生
（9 千个 block 对 32 条 ~1k token 的请求，离抢占很远）。
**若将来把 `NVFP4_GSM8K_N` 或 `max_model_len` 调大到接近容量，这条假设会失效。**

事先约定过：identity 若跑不出来，按真 bug 查到根因，不预设放宽退路。
正确的修法是把配置改到确定（缩短生成长度或固定 `kv-cache-memory`），
而不是把门槛降成准确率比较。

**测试本身的改动**

`tests/e2e/test_vllm_integration.py` 从 S0 的单臂基线改成
`test_custom_backend_matches_flash_attn`：一次运行跑两个 arm，同时断言
BF16 准确率 ≥ 0.60（基线还站得住，否则两个 arm 一起输出垃圾也能满足相等）
和两臂 token id 全等。合并成一个测试省掉一次 8B 引擎构建；
BF16 基线的绝对数字由 S0 记录，不需要独立测试反复重跑。

`_run_gsm8k` 的收尾补上 `llm.llm_engine.engine_core.shutdown()`。S0 只建一次
引擎所以没暴露，S2 连建两次时第二个引擎必然撞上 S1 那个 `gc.freeze()` 坑。

### S3 — 护栏（已完成）

**做什么**

在 backend 初始化处加入 §6.1 的全部检查，每条都给出可操作的错误信息
（说明为什么不支持、怎么改配置）。

**验收**

单元测试：每种错误配置都抛出预期异常。特别是
`block_size != 128`、`enable_prefix_caching=True`、`pipeline_parallel_size > 1`、
`kv_transfer_config != None`、`kv_offloading_size != None`。

**结果**

```text
tests/e2e/（不带 NVFP4_RUN_VLLM_E2E）      13 passed, 3 skipped in 29s
tests/e2e/（带上）                         16 passed in 124s
tests/kernel/                              33 passed in 59s
```

**护栏分成两处，因为 backend 选择器有缓存**

`AttentionBackend.validate_configuration` 看起来是自然的落点，但它由
`_cached_get_attn_backend` 调用，缓存 key 是 `AttentionSelectorConfig`——
里面只有 `head_size` / `dtype` / `kv_cache_dtype` / `block_size` 这类
**张量形状级**字段，`max_num_seqs`、`enable_prefix_caching`、
`pipeline_parallel_size` 一个都不在。同一进程里先建一个合法引擎、再建一个
`max_num_seqs=256` 的，第二个会直接命中缓存，护栏永远不会被调用。

所以只有进得了缓存 key 的检查才放选择器：

- `supports_block_size` / `supports_compute_capability` /
  `supports_kv_connector`：与 `kv_cache_dtype` 无关的能力，无条件生效
- `supports_combination`：`head_size == 128`，只在
  `kv_cache_dtype == "nvfp4"` 时判——`head_size` 和 `kv_cache_dtype`
  都在缓存 key 里，所以这个条件判断是安全的

其余全部放 `NVFP4Impl.__init__`。它每引擎每层各跑一次，不经过任何缓存，
拿到的 `get_current_vllm_config()` 是这个引擎真实的配置。
检查放在 `super().__init__()` **之前**，否则报出来的会是 FlashAttention
自己在错误配置下先撞上的那个错，而不是护栏。

**`supports_block_size` 覆盖了继承来的实现**

FlashAttention 的版本接受「128 的倍数」，vLLM 会把一个 256 的 cache block
拆成两个 kernel block。我们的 V 沿 token 轴按整页量化，页不可切分，
所以收紧成恰好 128。`get_supported_kernel_block_sizes()` 返回 `[128]`
不足以表达这一点，那只约束 kernel block。

**`enforce_eager` 改判 `cudagraph_mode`**

§6.1 原文写的是 `enforce_eager == True`。实际判的是
`compilation_config.cudagraph_mode == NONE`，因为这才是 graph 到底捕不捕的
唯一真相：`enforce_eager=True` 会把它设成 `NONE`，但反过来通过
`compilation_config` 直接开 graph 也是合法路径，判 `enforce_eager` 会漏掉。
错误信息仍然建议用户传 `enforce_eager=True`，那是通常的改法。

**`max_num_seqs` 从 `== 8`放宽成 `<= 8`**

尾巴 buffer 是按 8 个 slot 预分配的，跑 4 行只是浪费一半 buffer，不会错。
卡死等号只会挡住小批量的调试跑。

**配置矩阵不建引擎**

`VllmConfig()` 无参可构造（`model_config` 为 `None`，不碰权重也不占显存），
所以 13 个 case 直接喂 `check_supported` 就够，22 秒全部跑完，
其中大部分还是 import vLLM 的时间。改成每个 case 建一次 `LLM(...)` 要约
6 分钟，还要 8B 权重。

真正让这个选择不只是省时间的是**反向对照**：每条护栏都配一个
`cache_dtype="auto"` 的 case，BF16 下 backend 是纯 pass-through，同样的非法
配置必须**放行**。少了这组，把 `check_supported` 写成无条件抛异常也能让正向
case 全绿。而走引擎的话，「放行」的唯一证据就是引擎真的起来了——这 5 个反向
case 会变成 5 次成功的引擎构建，其中 `pipeline_parallel_size=2` 那次还要占
两张卡。

**wiring 单独一个 case**

同一个文件里的 `test_engine_refuses_more_rows_than_tail_slots` 建一个
`max_num_seqs=16` 的 nvfp4 引擎，断言 `UnsupportedConfigError` 出现在异常链里
（vLLM 会包装启动期异常，所以不能只看最外层）。选 `max_num_seqs` 是因为 vLLM
本身对任何批宽都没意见，拒绝只可能来自我们。正向对照是
`test_kv_cache_memory.py`——它在 slot 限制之内启动同一个 nvfp4 引擎，
本来就一直在跑。

没有这一条，配置矩阵可以全绿而 `check_supported` 从没被任何人调用过。

**两半合在 `tests/e2e/test_guardrails.py` 一个文件里**

配置矩阵严格来说不是 end-to-end，但把它单独放进第三个目录换来的只是命名上的
准确。§10.2 原本规划的 `tests/unit/` 因此取消：`tests/e2e/` 往后读作
「vLLM 集成测试」，S4/S5 的 control plane 与 metadata 测试也进这里。

只有 wiring 那个 case 挂 `NVFP4_RUN_VLLM_E2E=1`。不带环境变量跑
`pytest tests/e2e` 仍然会执行护栏矩阵，几十秒、不碰 GPU。

### S4 — GPU slot control plane（已完成）

**做什么**

- 预分配 §6.2 的 persistent state 与全部 output scratch
- 实现 once-per-step GPU control kernel
- 输入直接使用 device `block_table` / `seq_lens` / `query_start_loc`

尾巴 buffer 本身**不在 S4**，挪到 S6。S4 只产生「哪个请求用哪个 slot」，
buffer 的形状要由真正往里写的那条路径决定，先建一个 128 MiB 的空壳没有任何
东西会去读它。

**结果**

```text
test_control.py + test_guardrails.py       39 passed, 1 skipped in 29s
test_kv_cache_memory.py（带 E2E 环境变量）  1 passed in 155s
```

第二行是新护栏的正向对照：真引擎带着 `enable_chunked_prefill=False` +
`max_num_batched_tokens=4096` 确实起得来，护栏没有把唯一可用的配置也堵死。
`tests/kernel/` 没跑，S4 完全没碰 kernel 侧。

**为什么是 Triton**

候选是 CuTeDSL、纯 torch 算子链、Triton。这个 kernel 只有一个 CTA、几十个
int32，算力无关紧要，唯一的成本是发射开销和它能不能进 CUDA graph。实测：

```text
8 decode 行 / 8 token       eager 27.3 us    graph replay  4.4 us
8 行 / 4096 prefill token   eager 27.1 us    graph replay  8.2 us
8 行 / 16384 prefill token  eager 27.2 us    graph replay 20.5 us
```

eager 的 27 µs 与 token 数无关，全是 Triton 在 Python 侧绑定 16 个 tensor 参数
的开销；GPU 上的活见 replay 那一列。8B 模型一个 decode step 是毫秒量级，
所以 27 µs 在 0.5% 以下，而 v1 本来就把 `cudagraph_mode` 钉死成 `NONE`。
纯 torch 算子链要发十几个 kernel，反而更贵；CuTeDSL 在这里没有任何可用的
性能余量去换它的复杂度。Triton 还是 vLLM 自己到处在用的东西。

**capacity 取 `max_num_seqs`，不是硬编码 8**

kernel 里唯一和表宽有关的东西是 `[rows, slots]` 的比较矩阵，`S=256` 也就是
64 K 个 bool，仍然放得进寄存器。所以 8 这个数字不属于 control plane，它属于
S6 的尾巴 buffer 预分配。`MAX_SUPPORTED_SLOTS` 定义在 `control.py`，
`guards.py` import 它——一处定义，且就在 slot 概念旁边。

**新增三条护栏**

写 `error_code` 的时候顺手把「一步要么整段 prefill、要么恰好续一个 token」
这条不变量的漏洞都堵上了：`enable_chunked_prefill`（vLLM 默认开）、
`long_prefill_token_threshold`（关了 chunked prefill 也照切）、
`speculative_config`（decode 带多个 draft token）。都进了 §6.1 表。

V1 确实支持 `enable_chunked_prefill=False`：
`v1/core/sched/scheduler.py:848-854` 在预算装不下整个 prompt 时直接 `break`，
把请求留到下一步而不是切开。代价是 vLLM 要求
`max_num_batched_tokens >= max_model_len`。异步调度不受影响——
`num_output_placeholders` 和 `num_computed_tokens` 同步推进，
每个 decode step 仍然只有一个 token。

**测试：脚本化场景 + 调度器模拟器，对同一个 oracle**

kernel 的分配逻辑是「给需要 slot 的行排名、给空闲 slot 按年龄排名、把两个
排名配对」，没有分支。oracle 反过来按人话写：一张 dict 形状的表，逐行走，
每次取最老的空闲 slot。两者结构不同，一致才有意义。

脚本化的部分钉住设计明确开启的行为（行压缩后 slot 跟着请求走、缺席一步不丢
slot、LRU 挑最久没见的、复用的 block id 不误判），也当文档读。模拟器负责没人
想到的组合：随机到达/结束/跳过、block id 从一个 12 个 id 的池子里回收、
prefill 与 decode 混排。四个 seed × 300 步，实测覆盖到 mixed batch 约 70 次、
slot 换行约 60 次、key 复用约 30 次、promotion 约 13 次、满表约 20 次。

变异测试确认这套测试真的会失败：把 LRU 改成 MRU，5 个 case 红；
去掉匹配时的存活位，15 个红。

两条性质单独测：`set_sync_debug_mode("error")` 下跑一步不许有任何 host 同步；
以及 skip 概率为 0 时跑 400 步、周转近 90 个请求，`error_code` 必须一直是 0
（§6.2 边界 4）。

**`error_code` 是粘性的**

位标志按位或累积，只有 `reset()` 清。读它要 DtoH，所以生产路径不读；
做成粘性是为了让一次瞬时违例在几百步之后仍然查得到。其中
`NO_FREE_SLOT` 在正常输入下不可达（caller 先拒绝行数超过表宽），它检查的是
排名配对逻辑本身；`STALE_SLOT_HISTORY` 与 `DUPLICATE_KEY` 同样不可达，
测试各用一个伪造的 step 证明探测器有效。

**S5 期间的三处修订**

接 builder 的时候发现 S4 的几个假设是被护栏或者「没真跑过引擎」撑着的，都改成
kernel 层面成立（详见 §6.2）：

1. 存活判据从 `row < num_reqs` 改成 `seq_len > 0`，挡 cudagraph 的 padding 行；
2. 匹配与 slot 写回的归约从「求和」改成「取 min」，配 `ERR_DUPLICATE_KEY`；
3. 接上真引擎之后又追加 `key != 0`，挡 profile run 的 dummy batch。第 2 条的
   `ERR_DUPLICATE_KEY` 一开始在每次启动都会误报，就是因为 dummy batch 的八行
   全是 null block。

另外 `prepare()` 现在直接吃二维 block table 加 stride，不再要求调用方把第 0 列
拷成连续内存。

### S5 — 零同步 metadata builder（已完成）

**做什么**

`NVFP4MetadataBuilder` 继承 `FlashAttentionMetadataBuilder`，`build()` 里：

1. `super().build()` 拿到 FlashAttention 原本的 metadata；
2. 发射 S4 的 control kernel；
3. `NVFP4Metadata.from_flash()` 把 control plane 的输出接上去。

`NVFP4Metadata` 继承 `FlashAttentionMetadata`，不是包一层。原因是 S5–S7
之间引擎必须一直能跑：decode kernel 还没接上，每一层仍然走 FlashAttention，
它们通过基类字段读这个对象。基类尾部全是带默认值的字段，所以子类要
`@dataclass(kw_only=True)`，否则新增的必填字段声明不出来。

`kv_cache_dtype != "nvfp4"` 时 builder 整个是直通的，连 `ControlPlane` 都不建：
backend 是按引擎选的，不是按 cache dtype 选的，所以 BF16 的跑法拿到的也是这个
builder。

**`build()` 一步一次，这是全部前提**

LRU 顺序、连续性检测、尾巴长度，每一条都假设 control plane 的 step 计数增量等于
调度步数。这件事由 vLLM 决定，不由我们决定，所以有两条护栏和一个实测：

- microbatching 每个 ubatch build 一次 → `use_ubatching` 进护栏（§6.1）；
- full CUDA graph 在 capture 时也 build → `cudagraph_mode == NONE` 本来就在
  护栏里；
- 多个 attention group 会各自持有一个 control plane → engine 测试里断言只有
  一个 group。

**启动阶段确实会 build，而且不需要挡。** 原本以为 profile / warmup 都碰不到
attention metadata，实测不是——V2 runner 启动时会走三次 `build()`：

| # | 来源 | num_reqs | `block_table[:,0]` | `seq_lens` |
|---|---|---|---|---|
| 0 | profile forward（量峰值显存） | 8 | `[0]*8` | 512 |
| 1 | `warmup_kernels` prefill | 8 | `[1..8]` | 2 |
| 2 | `warmup_kernels` decode | 8 | `[1..8]` | 3 |

第 0 次靠 §6.2 的 null block 判据整批判死。第 1、2 次用的是真 block id，看起来
和真实请求毫无区别，会真占 slot，然后请求被 `finished_req_ids` 清掉、再也不回来
——这正是惰性回收本来就要处理的情况：真实请求到来时 LRU 把这些最老的 slot 拿走。
实测里第一个真实请求拿到 block 1，匹配上 warmup 留下的 slot，因为
`computed == 0` 走「block id 复用」分支（§6.2 边界 1），不报错，行为正确。

所以测试量的是**增量**而不是绝对值：`plane.step` 在 generate 前后的差。
单请求 16 token → 差 16，4 token → 差 4；三个并发请求各 12 token → 差 12，
最后这个 case 才能区分「一步一次」和「一个请求一次」。另外在 generate 之前断言
`error_code == 0`，那是启动这三步干净通过 slot 表的直接证据——`ERR_DUPLICATE_KEY`
最初就是被这条抓出来的。

**`error_code` 不进 metadata**

`ControlOutputs` 九个字段里只有八个接到 `NVFP4Metadata` 上。读 `error_code`
要 host 同步，而步内没有任何东西会根据它改变行为。测试断言
「metadata 新增字段集合 == `ControlOutputs` 字段集合 - {error_code}」，
这样以后加输出时漏接是个会红的决定，不是个沉默的遗漏。

**验收**

单元部分不需要 GPU 也不需要模型：字段拼接——基类每个字段身份不变、新增字段
集合正好等于该接的那些。用 marker 对象而不是 tensor：这是管线测试，
少接一个字段表现为身份不等，与字段声明的类型无关。

engine 部分两个 case：NVFP4 引擎的 step 增量与 `error_code == 0`，
BF16 引擎 `plane is None`。

**结果**

```text
tests/e2e（不含 E2E 开关）                49 passed, 5 skipped in 26s
tests/e2e（NVFP4_RUN_VLLM_E2E=1）        54 passed in 170s
```

环境是 `BitKV_nvfp4/_local/envs/vllm-nvfp4`，其中 vLLM 是 editable 指向
`BitKV_nvfp4/third_party/vllm`（`1ad84fea8`）；本仓库的 `third_party/vllm`
（`d6dbdb9`）只是参考副本，两者在本设计涉及的文件上只差 `KVBlockZeroer` 参数和
一个 logprobs 常量。本文档引用的行号以前者为准。

### S6 — prefill 写路径（已完成）

**做什么**

- **切换 `kv_cache_dtype="nvfp4"`**，block 里躺的就是 FP4 页
- 满页 → qpack 成 FP4 写进 vLLM 的 block
- 余数 → 写进尾巴 buffer
- **任何时候都不往 vLLM 的 cache 里写 BF16**
- 所有层 qpack 完成之后才算这一页可见（`1.vllm_tag_redesign.md` §4.4，见 §8）

**layout 从 region-major 改成 block-major**

原计划（§10.3 旧版）是 region-major：整个 buffer 先放所有页的 `K_fp4`，
再 `K_sf`，依此类推，每个区域自己连续，`k_fp4_all[page]` 直接就是 kernel
要的形状。这么写的唯一理由是「不用处理 stride」，而它的代价是 block `p`
的字节不在 `[p × page_bytes, (p+1) × page_bytes)`，vLLM 一旦按地址搬 block
就全错。

改成 block-major：四个区域按顺序排在**每个 block 内部**。代价是每个区域多一个
page stride——qpack 的目标和 decode kernel 的源都得吃这个 stride，多出来的就是
下面 S5.5 那段活。收益是 block 仍然是 vLLM 认为的那段自包含字节，
prefix caching / KV connector / KV offload 将来打开时不必回头重切 layout，
护栏也从「布局前提」降级成「功能尚未支持」。

区域字节数仍然是探的，不是手算的：`layout.region_specs` 拿真量化器跑一次
throwaway，把 shape、stride、dtype 和 page pitch 记下来，`carve` 只把 page
那一维的 stride 换成 block pitch。scale 是 swizzled 布局，这一点没变。
探针喂**两页**，一页读不出 page stride。

**S5.5 —— decode kernel 吃显式 page stride（block-major 的前置硬化）**

`_decode.py` 原来要求 K/V 页数组 `is_contiguous()` 且 scale 的
`storage_offset == 0`。carve 出来的 view 两条都不成立。放宽成：
最内层 stride 必须是 1，其余各维 stride 必须 16 字节对齐（scale 收紧到 512
字节，见下），page stride 从 tensor 自己身上读，不再另开参数让调用方声明——
调用方声明的话，说谎就是静默读错地址。

真正的坑在 scale。`fp4_decode_kernel.py` 里 `mSFK`/`mSFV` 的 layout 不是从传进来
的 tensor 抄的，是 `cute.tile_to_shape` 按 shape 现搭的，所以无论传什么 stride
都会被覆盖成密排。加了 `_sf_layout_with_page_stride`：在 `tile_to_shape` 之后把
page 那一维的 pitch 换成实际值，其余维度原样保留。scale 的 page stride 因此必须
512 字节对齐，否则 TMA 的 box 对不上——这是比 K/V 数据更严的要求，单独校验。

**qpack 扩成 indexed，不另起一个 kernel**

`quantize_kv_kernel.py` 之前只会「密排页数组 → 密排页数组」。S6 需要的是从这一步
的 activation 里按 token 起点取一页、写到 block table 指定的那个 block。加两个
索引数组 `source_tokens` / `destination_pages`，原来的 `quantize_*_pages`
变成传 `None` 的薄封装，密排调用者一行没改。

`destination_pages[i] < 0` 表示这一格没活干。CuTeDSL 不允许在 kernel 里 early
return，所以核心逻辑抽成 `_quantize_vector`，在 `if page >= 0:` 里调用，
不是 `if page < 0: return`。

**work table 每步一次，不是每层一次**

「这一步要 qpack 哪些页」只取决于 batch，与层无关，所以在 builder 里跟 slot
分配一起算完（`PageWorkTable`，一个 Triton kernel），32 层共用一份。

它是 `rows × columns` 的定宽矩形而不是压紧的列表：压紧需要一个 host 拿不到的
计数。矩形很小（行数和每行页数都被调度器上限卡着），空格填 -1。
只有 fresh prefill 的行才贡献页——decode 行的旧页在写进来那一步就量化过了，
再量化一次会拿这一步的 activation 覆盖历史。

**尾巴必须在 profile run 里分配**

原计划写「第一次 `do_kv_cache_update` 时 bind」。实测这是错的：profile run
里 `do_kv_cache_update` **根本不会被调用**（那一步 kv_cache 是零元素的空壳），
它第一次被调用时 KV cache 已经分配完了——那时再分配 128 MiB 尾巴，
拿的是已经许诺给 cache 的显存，正是旧仓库「FP4 池是净增量」翻车的形状。

`forward` 倒是会在 profile run 里被调用，而且那时 `no_compile_layers` 里 32 层
全都注册好了。所以拆成两次 lazy-once：

| 做什么 | 在哪 | 为什么不能换个地方 |
|---|---|---|
| 分配 tail、给每层编号 | profile run 的 `forward` | 晚一步就不进显存预算 |
| `layout.carve` 出四个 view | 第一次 `do_kv_cache_update` | 早一步 cache 还没有存储 |

实测：加上尾巴之后 vLLM 报告的 block 数按尾巴字节数成比例下降，
差值与 `tail_bytes` 对得上。

**验收：逐字节，不是 cosine**

原计划是「把写进去的 FP4 反量化出来比 cosine」。换成逐字节相等，
理由是这一步要测的根本不是数值：两边跑的是同一个量化器，
唯一可能错的是**位置**——token 有没有落到该落的 page、block、区域、slot、offset。
cosine 会把「V 的两个 head 写反了」这类错误糊成 0.999。

`tests/e2e/test_write_path.py` 起一个真引擎，prompt 长度
`{100, 128, 129, 900, 1024, 1025}`（正好卡在一页和八页的前一个、整数个、后一个），
在 `do_kv_cache_update` 外面截一层，只抓第 0 层和第 31 层：

- 每个满页 == 同样 token 喂给 `quantize_*_pages` 的输出，四个区域各自 `torch.equal`；
- 尾巴里的 token == 层交出来的 BF16 原值；
- 页/尾划分是 `{100:(0,100), 128:(0,128), 129:(1,1), 900:(7,4), 1024:(7,128), 1025:(8,1)}`
  ——**长度 L 的 prompt 量化 `(L-1)//P` 页，不是 `L//P`**，最后一个 token
  所在的页还要接着写，不能封；
- decode 那一步的 token 落在 `seq_len - 1 - seqused_fp4`，接在 prefill 尾巴后面；
- 断言「至少有一步同时带了多个 prefill 行」。不断言这条的话，
  调度器哪天不再合并 prompt，上面几条就退化成「单行也能过」的测试，
  而且不会红。

另外两组更小的：`tests/kernel/test_quantize_kv.py` 直接测 indexed qpack
（打乱的 src/dest、-1 跳过、不越界写进 pitch 里的 padding），
`tests/e2e/test_layout.py` 测 carve 出来的 view 写进去再读回来，
与密排 quantizer/decode 逐字节一致。

**顺带加的一条护栏**

`kv_cache_dtype_skip_layers` 非空一律拒绝（§6.1）。它会把模型切成多个 KV cache
group，每个 group 一个 builder，slot 表一步就要走好几次；而且分层 dtype 会让
vLLM 去清零新分配的 block，那是按 BF16 语义清的。

**这一步之后引擎还不能用**

`kv_cache_dtype="nvfp4"` 打开后，block 里是 FP4，FlashAttention 读不了它，
所以 `NVFP4Impl.forward` 在 nvfp4 下把 `output` 清零就返回。
cache 是对的，attention 什么都不贡献，S7 才接上读路径。
GSM8K 门槛（§9.1）也因此仍然留在 S7/S8。

清零而不是原样返回那块 buffer：里面躺着上一次用它的人留下的东西，
读到 NaN 的话整条 residual stream 就 NaN 了，后面每一层的 K/V 也跟着 NaN——
写路径测试比的是字节，而 NaN 和自己不相等，一次忠实的拷贝会被判成放错位置。
（这条是实测出来的：`test_write_path.py` 单独跑过、跟在别的引擎测试后面就挂。）

promotion 也还没有，所以一行跨过页边界之后，`seqused_fp4` 会往前走一页，
尾巴 offset 绕回 0，而那一页从来没被量化进 FP4——数据就丢了。
S8 补上。写路径测试只看 prefill 那几步的快照，不受影响。

**结果**

```text
tests/kernel                              46 passed in 60s
tests/e2e（不含 E2E 开关）                 54 passed, 10 skipped in 44s
tests/e2e（NVFP4_RUN_VLLM_E2E=1）         64 passed in 190s
```

### S7 — decode 读路径（已完成）

**做什么**

- decode 行走 `fp4_decode`
- prefill 行走 stock FlashAttention 的 cache-free varlen 路径
  （`flash_attn.py:1156` 那个模式，只吃原始 `key`/`value`，不碰 block_table）
- trusted-metadata fast path 已随性能主线落地，backend 传 `trusted_metadata=True`
- 预分配 padded-Q scratch，缓存每层 carved KV views

**batch 重排：decode 排到前面（取代原计划的行紧凑化）**

原计划是：control kernel 交出 `decode_row_indices` / `decode_count` /
`active_row_mask`，decode kernel 固定按 8 行发射，靠 `query_row_indices` 找 Q、
靠 `out_indices` 散射回 `output`、靠 `active_row_mask` 在 device 上抹掉无效行。
这套作废。它要付三笔代价，而 vLLM 已经有一个一等机制把三笔全免掉。

`AttentionMetadataBuilder.reorder_batch_threshold`（`backend.py:624`）让 builder
声明一个 query 长度阈值，model runner 就在建 metadata 之前把不超过该阈值的请求
搬到 batch 最前面。FlashInfer、Mamba、GDN、FlashMLA 都在用；同一棵树里的
`turboquant_attn.py`——另一个量化 KV cache 后端——的写法就是我们要的形状。

声明 `reorder_batch_threshold = 1` 之后，decode 行是连续前缀 `[0, num_decodes)`；
因为每行 query_len 恰好是 1，它们的 token 也是同一段前缀；prefill 是连续后缀。
`split_decodes_and_prefills` 读 `query_start_loc_cpu` 算出 `num_decodes` 与
`num_decode_tokens`，是 **host 侧的 int，零 GPU 同步**。三笔代价于是都不存在：

| 原计划要付的 | 重排之后 |
|---|---|
| control kernel 多 emit 四组紧凑数组，外加一次 page table gather | `seqused_fp4[:n]`、`block_table[:n]`、`row_to_slot[:n]` 全是切片视图 |
| `out_indices` 散射，而它会关掉 split-K | decode 输出就是 `output[:n]`，一次连续 `copy_`，split-K 不受影响 |
| `active_row_mask` 进 CuTeDSL，在 epilogue 里抹掉无效行 | 按 `num_decodes` 精确发射，没有无效行 |

split-K 那一笔尤其贵。`_kernel.py` 里 `direct_scatter` 一旦成立就把 split 数按回 1，
而 `_decode.py` 的 split 路径把 `use_out_indices` 写死为 False，所以这不是启发式的
疏忽而是能力缺口。按 `split_k_heuristic`（`heads_kv=8`，148 SM），8 个 decode 行是
2 路，4 行 4 路，2 行 8 路，**单行 16 路**——而 S7 的验收测试正是单条 prompt。

重排唯一的致命风险是它改变行号，而 tail slot 必须跨步跟着请求走。`control.py` 的
slot 是按 block-id key 匹配的（「Slot state follows its owner」），不是按行号，
所以重排不会认错 tail。builder 里另加一条 CPU 侧断言守住「decode 在前」这个前提，
读的是 `query_start_loc_cpu`，不引入同步。

**padded-Q scratch**

residual 需要 BF16 Q 去和 BF16 尾巴做 MMA，所以生产路径必须传 BF16 query，Q 的量化
只能发生在 `fp4_decode` 内部——预量化的 FP4-Q 路径下 `query_padded_bf16` 是 `None`。
而 `_kernel.py` 现在每次调用都 `torch.zeros(rows, 128, heads_q, 128)`，8 行就是
8 MiB，32 层一步 268 MiB 的 memset。

量化 kernel 只写这块 buffer 的 `[row, 0, head, :]`（`quantize_q_kernel.py:119`），
1..127 行从来不碰，`torch.zeros` 就是为了让它们是零。所以预分配一次、只清零一次，
语义完全等价。`fp4_decode` 加一个可选 `query_padded_scratch`，由 `WriteRuntime` 在
profile run 里跟 tail 一起分配（晚一步就不进显存预算，这是 S6 的教训），32 层共用。

**验收**

promotion 还没实现，所以这一步**不能拿 GSM8K 做门槛**。GSM8K 的 prompt 长度不一，
到下一个页边界的距离大致均匀分布在 `[1, P]`，只要生成长度有意义，
绝大多数行都会跨边界。

改用一个**长度已知且固定**的 prompt：pad 到 `Lp`，选生成长度 `G` 使得

```text
floor((Lp + G - 1) / P) == floor((Lp - 1) / P)
```

取 `Lp = 897`（`= 7×128 + 1`）、`G = 100`。账是：prefill 后量化 `(897-1)//128 = 7`
页，`seqused_fp4 = 896`，尾巴里 1 个 token；此后 `seqused_fp4` 不动，尾巴每步涨 1。
页边界在 seq = 1024，所以 `G = 126` 时 seq = 1023、residual = 127 仍然安全，
`G = 127` 时尾巴填满整页、跨界标记变 True，进入 S8 的地界。`G = 100`
留了 26 个 token 的余量。

这个前提不能只活在算术里。改动 `Lp` 或 `G` 会让测试**静默**开始丢数据——
跨界发生但 S7 没人消费它——而每一层每一步的 cosine 可能都还过得去。
所以直接断言全程没有行跨界（S8 之后写作 `promotion_pages < 0` 全为真）。

门槛：

- **attribution**：`spy.calls > 0` 且 `spy.saw_fp4_prefix`
- **数值**：抓下 decode 的 attention 输出，和
  `tests/kernel/test_fp4_decode_correctness.py` 里的 `_torch_fp4_decode`
  在同样输入上算出的结果比 cosine，沿用同一个 `FP4_MIN_COSINE = 0.99`，
  不另立一套常数。覆盖全部 32 层 × 四个 residual 长度（1 / 2 / 64 / 101）。
  层覆盖买的是定位能力——各层拿自己的真实输入独立比较，误差不叠加；
  step 则挑在 residual 长度这条唯一在变的轴上。
- **非退化**：生成的 100 个 token 非空、无 NaN、不是单 token 或短周期重复。
  cosine 只看单层单步，跨步状态的错误（比如尾巴 offset 每步漂一格）能让每一次
  cosine 都过而生成塌掉，这条补的是那个洞。

oracle 吃什么：`_torch_fp4_decode` 的入参是 BF16 页，它自己在内部量化，而引擎跑起来
之后 cache 里是 FP4，所以要么把 cache 反量化回去，要么在写入前截获 BF16。**选后者**，
在 `do_kv_cache_update` 上截获模型算出的原始 K/V 再按页重组——截获与页/尾划分这两段
S6 的 `test_write_path.py` 已经实现并验证过，直接沿用。

前者曾是首选，被否掉的理由是成本估反了：scale 是 `BlockScaledBasicChunk` 的 swizzled
布局，FlashInfer 的 `nvfp4_kv_dequantize*` 只认 linear layout，读不了，得自己写解码；
而且 oracle 会把喂进去的值再量化一遍，还要额外证明「已量化的值再量化不变」。截获这条
一行新的布局代码都不用写。

代价是比对的链条更长：不是「同样的字节进、答案应该一样」，而是「同样的 BF16 进、
两条独立的量化 + attention 流水线出」，两个量化器的实现差异会进到误差里。这正好也是
`tests/kernel` 现有比对的形状，所以沿用 `FP4_MIN_COSINE = 0.99` 是同源的而非硬套。

不要用「输出和 BF16 逐 token 一致」做门槛：页 0..n_fp4-1 此时已经是 FP4，
量化误差必然存在，greedy 解码通常前若干 token 一致、之后分叉，
拿它当门槛会得到一个既不稳定又没有诊断价值的测试。

完整的 GSM8K 门槛推到 S8。

**落地顺序**

直接在 main 上，三个绿灯 commit，只有最后一个走独立审阅。

| | 做什么 | 门槛 |
|---|---|---|
| C1 | kernel 侧的 `query_padded_scratch` 参数 | 传与不传逐字节相等；同一块 buffer 连用两次结果不变（这才是「只清零一次」成立的证据） |
| C2 | builder 的重排接线，同时删掉被它取代的三个字段 | `tests/e2e` 单元半。对 BF16 路径行为无变化 |
| C3 | 读路径本体 + `WriteRuntime` 里分配 scratch + 验收测试 | 上面三条门槛 |

scratch 的分配跟着它的消费者走，留在 C3。放进 C1 的话会先交付 8 MiB 没人用的显存，
而「必须在 profile run 里分配」这个理由只有在真的有人读它的时候才成立。

C2 与 C3 分开，是因为 C2 单独可测且不改变行为；把「接线」和「换算法」分成两次，
出问题时二分范围小一半。

**C3 实测：split-K 的 partial buffer 依赖未初始化显存**

读路径接通后，e2e 大约每 200 个 decode step 出一次非有限输出，之后靠残差流扩散到
全部后续 token。拿同样的输入重跑那一次调用总是干净的，据此最初判成瞬时竞态——**那是
错的**，而错因本身值得记下来：故障是「读了一块从没人写过的显存」，重跑时分配器交回的
正是上一次算出的**有限** partial，所以必然干净。同一个道理让一个反复发同一调用的
kernel 级 hammer 累计 180 万次调用全部失明。

真正的形状是：`num_splits` 个 split 里，没有页可算的那些**从不写自己的
`output_partial`**，只发布 `LSE = -inf`。combine 并不是「只累加有效的 split」，而是
**沿连续前缀 `[0, max_valid_split]` 累加**，且那个上界取的是**同一个线程所负责的若干
行里最长的那个**（`split_k_combine.py` 里的 `thr_max_valid_split`）。于是批次内行长
不齐时，短行会被拖着走完长行的 split 数，途中读到自己从没写过的 `output_partial`，
再乘上 `-inf` 换来的那个 0——`0 × inf = NaN`。空 split 的 `output_partial` 每次调用
都是未写的（实测 5000/5000），`lse_partial` 则每次都写满。

这条路径**静态可判定**（2026-08 复核 combine 源码得出），与 C4 的流竞态无关，也不
依赖运气：一步里同时存在长短不一的解码行，它就成立。这也解释了为什么单请求的
`test_read_path.py` 永远看不到它，而多请求变长度的 soak 一跑就撞上。所以
`output_partial` 归零那 6% 是**必要开销**而非纵深防御；要拿回来得走后续 1 那条——让
combine 在 `-inf` 上分支跳过，而不是靠乘 0 掩盖。

证明它的是阳性对照，不是 A/B：保持代码不动，只把 `output_partial` 填成 `+inf`
（`lse_partial` 留真实值），命中率从 0.53% 涨到 3.1%。combine 若从不读这些条目，
改变它们的内容不可能改变任何东西。

修法是让两块 buffer 有确定初值：`output_partial` 归零，`lse_partial` 填 `-inf`。
后者是语义正确的默认值——「没写过的 split」与「没有活的 split」从此不可区分。
验证：8 进程 × 150 轮共 1200 次 generation 零故障，对照组 750 轮 4 次（折算预期
6.4 次，p≈0.002）；解码调用开销 +6%。

**这个验证是不够的，后来被 C4 推翻了一半。** 它用的是单请求负载：一个引擎服务一条
请求、跑完就退，既不复用 tail slot，也几乎没有内核重叠。真正的主导缺陷（C4 的流
竞态）在这种负载下曝光极低，所以「零故障」只证明了这条路径上的这一个隐患被堵住，
不能读作「NaN 已解决」。教训是负载的形状比样本量重要：1200 次同形状的运行，抵不过
一次多请求、变长度、有 slot 易手的运行。

需要一并记下的反证：一个「无关 memset」的安慰剂对照同样跑出 1200 轮零故障。原因是
那个常驻缓冲区挪动了分配器的块布局，让 partial 落到不含无穷值的块上——它没有消除
隐患，只是换了运气。所以结论建立在阳性对照上，A/B 只是佐证。这也说明这类故障对
「显存里恰好是什么」有多敏感，不要用 A/B 单独给这类修改结案。

`split_k_combine.py` 与上游 flash-attn 4.0.0b23 的 `flash_fwd_combine.py` 逐字节
相同，上游同样用 `torch.empty` 分配 partial。我们会被咬到而上游不会，是因为我们长期
运行在一个上游几乎不进入的区间——见下面第一条后续。

**上游现状（2026-07 查证）**

flash-attention 对此**没有任何 issue 或 PR**：搜 `flash_fwd_combine` /
`max_valid_split` / `sMaxValidSplit` 零结果，上述四个实现细节在 HEAD
（`c75d019dea9d`）里原样都在。C++ 版本里那行修复是**写好又注释掉**的：
`// We don't need to zero out the rest of the LSEs... / // cute::fill(tLSEsLSE(_, _, m), -INFINITY);`。
更早的 FA2 combine（`csrc/.../flash_fwd_kernel.h`）是无条件给越界行填 `-INFINITY`
的，这个不变量在 FA3/FA4 重写时被当作优化去掉了——所以我们给 `lse_partial` 填 -inf
是把 FA2 就有的性质补回来，不是新发明。上游的 combine 测试（2026-03 才加）永远用
`torch.randn` 把 `out_partial` 和 `lse_partial` 填满，结构上测不到这个失效模式。

因此若要上游修，我们会是第一个报告者。**暂不提**：先把自己这边收干净，等第一条后续
（`num_splits_dynamic_ptr`）落地、拿到一个不依赖分配器内容的最小复现之后再说——
上游对「乘 0 屏蔽」的立场已经明确，带着复现和分支修法去谈比只报一个初始化改动有力。

同类缺陷在别处有充分先例，可作为交叉验证与设计参考：vLLM PR #47188（Triton MLA
split-KV）是同一缺陷的另一个触发器，措辞可直接套用——「stage 1 里空掉的 split 在
stage 2 仍被合并，结果取决于所选 `num_kv_splits` 和未初始化的临时显存」，它还附了个
好用的不变量测试：断言输出与 split 数无关。FlashInfer #1046 是这套算术最干净的公开
演示（分配含 `inf` 的张量、释放、重跑，NaN 精确落在那些位置）。FlashInfer 文档则把
「`float_workspace_buffer` 首次使用前必须清零」写进了 split-k 的参数说明。

一条反面教训：vLLM 落过一模一样的零初始化修复（#37442，实测零开销），一周后因内存
回退（#38359）——他们用的是**每层常驻**缓冲区，61 层各约 256 MiB 合计约 15 GiB，
且惰性分配绕过了 profiling run。我们现在按调用分配，不踩这个坑；将来若为省掉那 6%
改用常驻 workspace，必须在 profile run 里分配（与 S6 的教训同一条）。

顺带排除的两条：`griddepcontrol_wait()` 需要启动时带 `use_pdl=True` 才有意义，我们的
封装没传，PDL 根本没开，那条 wait 是空转，combine 本就流序排在解码之后。
`cute.arch.warp_reduction_max` 把 membermask 硬编码成全 warp 而不管
`threads_in_group`，在运行时分叉下是 UB；但归约位于第 399 行那个 `if` 之内，而我们
`num_splits_dynamic_ptr is None` 与 `varlen` 都是编译期常量，条件在 tracing 时就化简
掉了，没有分叉。**采纳后续第 1 条时要重新核这一点**：传了 `seqused` 之后 `varlen`
变真，那个条件成为运行时判断（虽然按 `m_block` 取值，仍是 CTA 内一致）。

**C4 实测：combine 内核跑在默认流上，与写它输入的注意力内核并发**

C3 收工后换了个负载：一个引擎连续服务很多条**长度不同**的请求，让 tail slot 反复
易手，并在设备端统计每层每步的输出（见 `tests/e2e/test_soak.py`）。提交状态在这个
负载下 4/4 失败，**22688 个 layer-step 里约 16300 个非有限（72%）**。也就是说
「跑几次 generation 就 NaN」从来不是偶发，只是过去没有任何测试进入过这个形状。

定位它的是一个反直觉的观察：一个每步都读回输出、因而每步都同步的诊断脚本，24 轮
一次都复现不出来；同一棵树、同样轮数、不同步的 soak 却 4/4 失败。同步就干净，是
竞态的签名。

根因是流。`split_k_combine.py` 是全仓唯一一个用
`make_fake_stream(use_tvm_ffi_env_stream=True)` 编译、且调用时不传 stream 的内核；
其余每个 CuTeDSL 内核（两个量化、两个解码）都显式传
`torch.cuda.current_stream()`。在引擎里实测两个句柄：

| 句柄 | 值 |
| --- | --- |
| decode 时 `torch.cuda.current_stream()` | 519359632（vLLM 自己的流） |
| 同一时刻 tvm-ffi 环境流 | 0（遗留默认流） |

于是 combine 去读 `output_partial` / `lse_partial` 时用的不是写它们的那条流。这不是
从编译方式推断的，是拍下来的：把一次解码交给 profiler，量化、注意力、`torch.full`
的 memset 全部落在一条流上，`FlashAttentionForwardCombine` 独自落在另一条。它们之间
没有任何 GPU 侧依赖。这也解释了为什么 60 个 kernel 测试从没抓到——独立测试里 torch
的当前流就是 0，与环境流恰好一致，那个环境下无从暴露。

归因用的是 4 张卡一组、24 轮的对照，不是单次运行：

| 版本 | 结果 |
| --- | --- |
| 提交状态 | 4/4 失败，约 16300 / 22688 个 layer-step 非有限（72%） |
| 只加 tail 重置 | 4/4 失败，约 10300 / 22688（44%） |
| **只改流** | **4/4 通过** |
| 三项齐备 | 4/4 通过 |

即改流单独一项既必要又充分，而 tail 重置单独一项只把放大器堵住。第三个独立干预同向：
在注意力与 combine 之间插一次 `torch.cuda.synchronize()` 也通过。修法取「显式传当前
流」，零同步开销，且与其余内核的写法一致。收尾验证：kernel 60 项、e2e 75 项全通过，
重负载 soak 6 卡 × 60 轮（约 34 万 layer-step）零非有限。

C3 与 C4 是两个独立的源头，不是一个问题的两种说法。C3 那条与流无关：短行被拖着走完
同线程内长行的 split 数，读到自己从没写过的 partial，这在单流下同样成立（见上面 C3
一节的静态论证）。C4 是 vLLM 集成里占主导的那条。C3 的修复没有白做，但它只堵住两个
源头中的一个，这就是当时「NaN 变少却没消失」的原因。

守这条不变量的是 `tests/e2e/test_soak.py`，不是一个内核级测试。**试过写后者，没成功，
记下来免得重走**：在侧流里调用解码，profiler 证实 combine 确实落到另一条流上，但输出
每次都对。逐一排掉了两个原因——两次调用输入相同时，分配器交回的残值恰好就是想要的
答案（与 C3 那个「重跑总是干净」是同一个陷阱），换成不同负载做诱饵后仍对；以及宿主端
launch 开销盖过了内核时长（实测注意力 802.5→807.9 µs，combine 926.7 µs，晚了 119 µs），
但用 `torch.cuda._sleep` 把侧流堵住 100 ms 后**依然**对。所以合成场景里还有一层顺序
来源没查清（有个反常观测：一条 `cudaStreamGetFlags` 报 non-blocking 的流，却让默认流
等满了 500 ms）。这不影响修复的定性——归因是靠上面那张 4×4 的表立住的——但它意味着
这条缺陷目前只能由 e2e soak 守住。

一条方法论教训：我曾用单次运行做二分，把嫌疑落到页表裁剪上（裁剪版失败一次、提交
状态通过一次）。把曝光量提上去后，提交状态 4/4 失败得更狠，裁剪当庭无罪。对概率性
故障，单次运行的归因价值是零。

**S7 留下的三条后续**

1. **页表宽度违反了 `split_k_heuristic` 的书面契约。**（已做）它的 docstring 要求调用方
   「按本批次最长行裁剪页表」，而 `impl.py` 传的是全局容量宽度的整张
   `block_table`（`max_model_len / P`，验收配置下是 32 列）。于是 7 页真实数据被
   规划成 16 个 split，其中 9 个是空的——既浪费 CTA，又把系统长期泡在上述未测试
   区间里。`CommonAttentionMetadata.max_seq_len` 是现成的主机端 int，
   `max_seq_len // P` 是紧的上界，裁剪不引入任何同步。修好之后很可能把 +6% 赚回来。

   更要紧的是它同时是**正确性**收尾，不只是性能。上游对这类 bug 的共识是：靠「乘 0」
   屏蔽一个 split 本身不成立（`0 × inf = NaN`），可持续的修法是在 `-inf` 上分支
   跳过，缓冲区初始化只算纵深防御——vLLM 的 `merge_attn_states` 就是这么收的
   （PR #28181 加 `isinf(max_lse)` 早退；注意 reviewer 提的简化写法
   `max_lse = isinf ? 0 : max_lse` 被作者否掉，因为会导致 `0/0 = nan`）。
   把每行真实 split 数经 `num_splits_dynamic_ptr` 交给 combine（上游为此设计的
   机制，我们现在传 `None`），空 split 便完全不进入读取范围，那才是那个分支。

   已按 `max_seq_len` 裁剪（`impl.py` 传 `block_table[:rows, :pages]`，
   `pages = (max_seq_len - 1) // P`；页表最后一页永远属于 tail，所以边界比长度少
   一格）。切片是非连续视图，行跨度仍是原始容量，实测与密排页表逐位相同——内核只
   要求最后一维连续，布局本身是 dynamic 的。**需要更正一处记述**：上一版把这条写成
   「同时是正确性收尾」，实测不支持。裁剪版在高曝光对照里与提交状态无差别，真正的
   正确性缺口是 C4 的流竞态。裁剪的价值是契约与性能（本配置下 `num_splits` 从随行数
   变化的 16/8/4/2 收敛到恒定 2），`num_splits_dynamic_ptr` 那条分支仍然待做。

2. **tail buffer 跨请求不清理，是个 30 倍放大器。**（已做）机制这次是直接量出来的，
   不是推断：往一行 tail 页的**活跃长度之外**灌 NaN，整行输出 4096/4096 全成 NaN；
   只灌 K 则完全无害。原因在残差路径的掩码——它把 `n_coord >= seqused_k` 的 S 覆写成
   `-inf`（所以 K 的 NaN 被中和），于是 P = 0，而 PV 里算的是 `P(=0) × V`，V 的 NaN
   直接穿透。这正是 flash-attention issue #2374 / PR #2407 在我们自己代码里的翻版。

   平时无害是因为残留值都是有限的；一旦有 NaN 进过某个 slot 的 tail，此后每个落到该
   slot 的请求都确定性地输出 NaN。`runtime.py` 里 tail 用 `torch.zeros` 而非 `empty`
   分配，注释写明了「注意力会把整页读回来，序列之外的位置不能是 NaN」——不变量在设计
   时就认识到了，缺的是它只在启动时建立一次。

   修法是把这个不变量维持到每一位租户：新请求上台时把它那一页清零
   （`write.py::reset_new_request_tails`）。判据是 `seq_len <= query_len`（即
   `computed == 0`），比「prefill 行」更严，能一并覆盖单 token 提示词（被批次重排归进
   decode 段）和块 id 被回收从而匹配到旧 slot 这两种情况。必须是独立的一次发射：塞进
   `_tail_write_kernel` 会让负责 offset 0 的 program 去清 [1,128)，把同批次其他 token
   刚写的值抹掉。在第一层发射、覆盖所有层，因为一个 slot 的历史必须对整个模型同时终止。
   代价是每步一次空发射（该步没有新请求时所有 program 直接返回）。

3. ~~**未转置 softmax 路径确定性损坏。**~~ **这条结论是错的，已撤销。** 当时关掉
   `_TRANSPOSE_S` 后 40 轮里 11 轮失败、重跑全坏，被判成一条独立的确定性缺陷；但那是
   在流竞态和 tail 放大器都还在的树上测的，「重跑全坏」正是 tail 中毒的表现而非确定性
   损坏的证据。在修好之后的树上重测：soak 4/4 通过，kernel 套件 60 项全过。

   顺带把这个布局值多少钱量了出来（profiler 取设备时间，不是 CUDA event 套 Python
   调用——后者量的是宿主）：

   | rows | 转置 attention | 未转置 attention |
   | --- | --- | --- |
   | 1 | 5.8 µs | 10.6 µs |
   | 8 | 6.3 µs | 11.6 µs |

   即注意力内核快约 1.8 倍。但端到端量不出来：一次解码调用的设备时间共约 33 µs，
   32 层合计约 1 ms，而 eager 模式下一个解码步约 21.8 ms，所以这 1.8 倍折算到端到端
   只有约 0.8%，两轮对调实验的符号都反了（-2.8% / +1.7%），完全落在噪声里。

   **真正该记住的是 `_TRANSPOSE_S = True` 不是一道保险。** 它只是「请求」，内核用
   13 个条件的合取去收窄（`fp4_decode_kernel.py` 第 613 行），任何一条不满足就静默
   回落。其中一条是模型相关的：`qhead_per_kvhead` 必须是 2 的幂。Llama-3.1-8B 是
   32/8 = 4 满足，但例如 24/8 = 3 的模型会悄悄走未转置路径，`guards.py` 里没有任何
   检查拦它。既然那条路径现在被证明是好的，这只是性能问题而非正确性问题——但静默
   损失 1.8 倍仍然值得一个显式提示。

### S8 — promotion

**做什么**

在最后一层 attention 之后（§5.3 的步内顺序）每步固定发射两次 qpack（K 一次、
V 一次），把跨过页边界那些行的整页尾巴量化进 `block_table[row, seq_lens/P - 1]`。
不允许 `nonzero().numel()` 后在 Python 决定是否 launch。production 不清零
tail；下一页只按 `seqused_residual` 读取有效范围。

**「不能乘以 L」是量出来的，不是风格偏好**

最朴素的写法是 Python 里循环 32 层、每层发 K/V 两次。实测这条路走不通：

| 方案 | 每步 launch 数 | 每步 host 开销 |
|---|---|---|
| 每层循环（现成 API） | 64 次 CuTeDSL | **约 3.0 ms** |
| 每层循环 + 预存参数 | 64 次 CuTeDSL | 约 0.83 ms |
| 跨层一次 | 2 次 | **约 0.10 ms** |

单次 `quantize_*_tokens_into` 固定约 **49 µs，与它有没有活干无关**（全 -1 空转
和满载 8 行同价）。拆开是 36.5 µs 在 Python 包装（30 个 `Int32(...)` 构造、
5 次 `make_ptr`、两处 validate），12.9 µs 在 CuTeDSL dispatch；同机 Triton 一次
launch 是 7.4 µs。而 promotion 是**每步都发**的，127/128 的步纯空转——3.0 ms
是 32 层注意力设备时间（约 1 ms）的三倍，占 eager 一步（约 21.8 ms）的 14%。

**跨层一次的障碍与解法**

32 层的 KV cache 是 **32 次独立的 `torch.zeros`**（`v1/worker/gpu/attn_utils.py:186`；
单 KV cache group 走 `get_kv_cache_config_from_groups` 的 general case，每层一个
`KVCacheTensor`）。指针不保证等差——同形状实测过，大部分等差但有例外——所以
「拼成一个 `[L, blocks, ...]` view」是假的。

解法是给量化器一张 device 上的 **per-layer 基址表**。`cutlass.cute.core.make_ptr`
接受运行时 `Int64`，spike 验证过 kernel 内能用它造出目标张量并写入。对齐也成立：
四个区域在 block 内的偏移是 0 / 65536 / 73728 / 139264，全是 512 的倍数，满足
scale 那条比 K/V 更严的 512 字节要求（§10.4 第 8 条）。

表里**不允许有空项**。spike 阶段设想过「置 0 的项干净跳过」，实现时否掉了：少一层
的表是调用方的 bug，跳过它就是安静地不写那一层的整页历史，而 null 解引用会当场炸。
`_base_pointers` 因此校验形状与 dtype，缺项由 `LayerRuntime.destination_bases`
在组表时报出层号。「哪些行不用写」是 `promotion_pages` 的 -1 负责的事，两套机制
不能混。

曾经考虑过、被否掉的两条：**把量化结果写进 staging 再用 Triton 按指针表整页
scatter**（3 次 launch，成本相当，但要多 36 MiB 且多一层间接）；**用一张私有
CUDA graph 捕获那 64 次 launch**（host 降到约 10 µs，但设备侧仍是 64 个内核，
且为此引入 graph 捕获这套新机制）。

**layer 是 grid 的第三维，不是 work 的一部分**

`grid = (heads, work = S, layer = L)`。索引数组维持宽度 `S`，和 control plane
其余输出同构；基址表长度 `L`。源按层跨步：

```text
source_token = promotion_source_tokens[row] + layer × (S × P)
目标         = destination_bases[layer] 给出的四个区域基址，页号 promotion_pages[row]
```

另一种接法是把 layer 折进 work（`work = L×S`、三张长度 256 的数组）。CTA 总数和
设备时间完全相同，差别只在契约形状：折进 work 要每步把 8 个值平铺成 256 个，还要
让 metadata builder 拿到 `L` 这个本属于模型侧的常量。`destination_bases is None`
时 grid z = 1、layer stride = 0，退化成今天的行为，现有两个调用方一字不改。

**索引数组在 control kernel 里算，不另发 kernel**

`block_table`、`seq_lens`、`row_to_slot` 已经在那个 single-CTA kernel 的寄存器里，
加一次按 `seq//P - 1` 的 masked gather 和两个 store 就够，**零额外 launch**：

```text
promotion_source_tokens[row] = row_to_slot[row] × P
promotion_pages[row]         = block_table[row, seq_lens[row]//P - 1]   跨界
                             = -1                                       否则
```

两个数组按**全宽 S** 暴露，不按 `num_reqs` 切片——切了 launch 形状就跟着 batch
变，那正是要避免的。`promotion_mask` 同时删除：`promotion_pages[row] >= 0` 与它
恒等而严格更有信息量，留着就是两套「哪些行跨界了」的机制（同 S7 删掉
`decode_row_indices` 三件套的理由）。

新增 `ERR_PROMOTION_COLUMN` 粘性位。`seq//P - 1` 结构上不可能越过 block table 的
宽度，但越界的 masked gather 会安静地读到**隔壁行**的 block id，然后往别人的 KV
上写一整页 FP4——这是那种一旦发生就完全无法归因的错误。

**谁来发射：`layer_index == L-1`，外加常驻的顺序断言**

`layer_index` 按 `no_compile_layers` 的 dict 顺序（构造顺序）编号，用它触发依赖的
是「构造顺序 == 执行顺序」。这对标准 decoder 栈成立但没人检查；不成立的话
promotion 会在某些层还没写入本步 token 时就封页，表现为「精度偶尔掉一点」，正是
§6.3 说的那种极难定位的错误。runtime 上放一个 `expected` 计数，每层 `forward`
断言自己的序号然后自增取模 `L`，纯 Python 整数比较。计数放在 `attn_metadata is
None` 提前返回**之后**，profile run 不会打乱它。

基址表由 `do_kv_cache_update` 顺手登记本层 cache 来组装，不走
`no_compile_layers[name].kv_cache`——用**我们真正写进去的那个张量**、按**我们自己
编的 layer_index**，不依赖 vLLM 内部两者是同一个对象。有了顺序断言，最后一层跑到
时 32 层必定已登记齐。

**验收**

- **字节等价是主门槛**（同 S6 的理由：两边跑同一个量化器，唯一可能错的是位置）。
  跨界之后 `block_table[row, n]` 的四个区域，与 `quantize_*_pages(那一页 BF16)`
  逐字节相等。比**全部 32 层**而不是只比首尾：D 方案新引入的正是那张基址表，它最
  可能的坏法是错位/乱序，两端对了中间错。跑**至少两行、错步跨界**，这样「写串到
  别人的 block 上」会表现为另一行比对失败；单行只能证明「该写的写对了」。
- 跨界之后 decode 读得回来：`_torch_fp4_decode` 对照，覆盖跨 ≥2 次边界。字节对了
  不等于状态对了——`seqused_fp4` 有没有进位、尾巴 offset 有没有绕回，不在字节比对
  的射程内。
- 序列精确停在 `seqused = kP` 和 `kP+1` 时页状态与推导一致；含一个正好 `P` 的整数
  倍长度的 prompt，覆盖「prefill 的最后整页也走 promotion」这条路（work table 只
  量化 `(L-1)//P` 页，第 `(L-1)//P` 页进尾巴由 promotion 收尾，这和 metadata 说的
  一致，不能抄近路直接量化 `L/P` 页）。
- launch 次数 = decode step 数（K/V 各一次），不能乘以 `L`；真正的 payload 行数 =
  跨边界的 row 数（device 上累加 `(promotion_pages >= 0).sum()`，最后读一次）。
- soak 改成跨界：prompt 长度贴着边界，让若干行在 30 步内跨 1–2 次，slot 易手与跨界
  叠加。
- **完整的 GSM8K 门槛在这里生效**（S7 推过来的）：`max_tokens = 256`，必然跨若干次
  页边界，NVFP4 相对 BF16 掉幅 ≤ 0.125、绝对值 ≥ 0.60。
  诚实记一句它的效力：`N = 32` 里的 0.125 就是 4 道题，两条 arm 跑同一批题目，差值
  的标准差约 0.06，所以这道关是**灾难报警器**——能抓住整页写错、写串层、丢一页
  历史，抓不住 5 个百分点的渐进退化。默认保持 32（快），S8 签收另跑一次 N=200 记进
  本文档。真正守「安静地丢一页历史」的是上面的字节等价，不是它。
- 再加一条 vLLM 自带 NVFP4 cache 的 arm（FlashInfer trtllm-gen）。对 BF16 的掉幅
  分不开「4 bit 的代价」和「这套 layout 的代价」，因为对照组两样都不付；机器上另一个
  4 bit 方案只付前者。门槛单边：只在我们落后超过 0.125 时失败。
- 记录 promotion 给每个 decode step 加了多少延迟，供 S10 的速度账使用。

**落地顺序**

直接在 main 上，四个绿灯 commit。

| | 做什么 | 门槛 |
|---|---|---|
| C1 | `quantize_kv_kernel.py` 加 `destination_bases` + layer 作 grid 第三维 | `destination_bases=None` 时与今天逐字节相同（现有 kernel 测试**一个不改**、全绿）；新测试用打乱的基址表 + 部分 -1 写进 N 块独立分配，与密排路径逐字节一致 |
| C2 | control kernel 加两个输出 + `ERR_PROMOTION_COLUMN`，删 `promotion_mask` | `test_control.py` 的 oracle 与调度器模拟器扩出这两个数组；此时还没有消费者，对现有行为零变化 |
| C3 | `promote.py` + 最后一层挂钩 + 顺序断言 + `test_promotion.py` + soak 改造 | 上面的字节等价、oracle 对照、发射次数账、soak 零非有限 |
| C4 | 打开 GSM8K 的 NVFP4 arm，外加 vLLM 自带 NVFP4 cache 作对照 | 掉幅 ≤ 0.125 且绝对值 ≥ 0.60；落后 vLLM 自带那条不超过 0.125；另跑一次 N=200 记进本文档 |

C1 和 C2 都能独立测、独立回滚，且都不改变任何现有行为——这是它们分开的理由。C4
单独一个，因为它是「宣布 §9.1 那笔从 S6 欠到现在的账还清了」，值得能单独 revert。
C3 走独立审阅（CLAUDE.md 第 10 条）。

C1 的门槛必须是「现有测试一个不改、全绿」而不是「改一改还能过」：它动的是全项目
逐字节正确性的锚点。

**C1 实测：写路径的页偏移在 2 GiB 处回绕（S6 就带着，不是 promotion 引入的）**

给量化器接基址表时顺手探了一下高页号，结果不是新代码的问题：`_launch_*_pages` 的
`fp4_strides` / `scales_strides` 一直是 `Int32`，页号乘页距在 **14563 块** 上过
`2^31`，也就是 **2 GiB**。而 §7.1 那次实测里单层区域是 143.82 GiB / 32 ≈ 4.49 GiB，
**一半以上的块落在回绕区**。回绕后的偏移要么没映射（illegal access），要么映射了
——那就是往别人的显存上写一整页 FP4。

之所以到现在才发现，是因为测试和 GSM8K 都只用少量请求，block id 全挤在低位。这正是
§6.3 说的那类错误：能力边界之内、负载之外。修在 `175761c`，只加宽目的地一侧（源是
一批激活或一层尾巴，都够不着边界），并加了一个直接把页写到 2 GiB 之外再读回来的
kernel 测试。同时探了读路径：`fp4_decode` 走 TMA descriptor，本来就是 64 位寻址，
不受影响。

**C3 实测：行号不是请求的身份**

`test_promotion.py` 第一版把 `metadata` 里的行号当成请求编号，跨步拼历史，四个测试
一起挂。实际是 **prefill 那一步和之后的 decode 步之间，vLLM 会把 batch 重新编号**
（backend 的 `reorder_batch` 把 decode 行排到前面）：第 0 步的第 0 行长度 894，第 1
步的第 0 行长度 1025。

这不影响实现——promotion 的每个输入都是同一步之内的，行号在一步之内当然是自洽的
——但影响任何**跨步**比对。测试改成按 `seq_lens[row] - step` 认人（每个请求每步都
被调度、每步恰好长一个 token，所以这个差就是它的 prompt 长度，而四个 prompt 长度
互不相同），并单独用一个测试守这条前提。写进这里是因为下一个要跨步比对的人会踩
同一颗雷：`num_reqs` 宽度的任何数组，行号只在本步有意义。

**C3 实测：每步 158 µs，soak 27 条请求封了 18 页**

`test_promotion.py` 量到的 promotion 每步 host 开销：中位数 **158.3 µs**，p95
179.6 µs，最大 236.6 µs；设备侧中位数 169.9 µs。比上表估的 0.10 ms 高一点（估算按
两次 49 µs 的裸 launch 算，没算 `metadata` 上那几次取值和 `destination_bases` 的
惰性构造），仍是每层循环那条路的 **1/19**。门槛设在 500 µs。

跨界之后 4 层 × 7 次跨界共 28 组 decode 对照 `_torch_fp4_decode`，最差 cosine
0.9916（门槛 0.99）；全 32 层的封页逐字节相等。soak 的 prompt 长度改成四长两短
（页内偏移 0 / 40 / 72 / 100 / 118 / 124），27 条请求按长度推出应封 18 页，实际
封了 18 页，零非有限。

**C3 独立审阅：两位都没开出 blocking，改了六处**

按 CLAUDE.md 第 10 条走的内部双审（主审 GPT-5.6-Terra，交叉复核 Claude Opus）。两位
都独立复核过跨层索引、`-1` 跳过、字节等价、发射次数与流序，结论一致：没有会写错页
或写错地址的路径。值得记下来的六条：

1. **源侧的 Int32 理由在 C1 之后就不成立了**。`175761c` 的说明写「源是一批激活或
   *一层*的尾巴」，而 `25fccbc` 之后源是**所有层**的尾巴。今天 32 层 × 8 slot 距
   `2^31` 还有 64 倍余量，但它随层数和 slot 数两个旋钮一起长——80 层模型在 204 个
   slot 上就溢出，而 `MAX_SUPPORTED_SLOTS` 旁边写着「低三位数很舒服」。已把源侧也
   改成 `Int64`：与其留一个要靠两个旋钮相乘才能算出来的界，不如让这一类不存在。
2. **顺序断言会被一次无关的异常粘住**。计数走到一半时若别处抛错，之后每一步都在
   第 0 层报「层序不对」，把真正的故障盖掉。改成报错时同时重新对齐，故只吵一次。
   跨步不清零这一点保留：那正是「某一步只跑了一部分层」的唯一抓手。
3. **字节门槛的 slot 和 block 来自内核用的同两个张量**，所以控制面给错 slot 时两边
   会一起动、看不出来。这不是自比（`expected` 是新分配的），层错位一样抓得住；但
   docstring 原本说「整个契约」，改成说清它守的是「给定索引，字节落在对的层、对的
   块、对的区域」，另一半在 `test_control.py` 和 oracle 那里。
4. **`_prompt_of` 依赖四个 prompt 长度互不相同，而前提测试没查这一条**。有人把
   `PROMPT_LENGTHS` 改出重复值，两条请求的历史会并进一个 key。补了断言。
5. **`test_promotion.py` 每步同步八次**（四层 K/V 各一次 `.cpu()`，给 oracle 攒
   历史用），所以它抓不到 C4 那种流竞态——「同步就干净」正是那种缺陷的签名。守
   promotion 这条流序的只有 soak。记在这里，别以为字节门槛顺带守了它。
6. **soak 没到「上一步刚封页、下一步就易手」那么紧**。实测封页发生在各自的第 0 / 4 /
   10 / 28 步，而请求只在自己那轮生成结束时才让出 slot，所以最短也隔了两步。要做到
   贴着易手，得让同一批请求停在不同长度上，目前没有。docstring 已按实际改写。

**C4 实测：GSM8K 四条 arm，N=32 与 N=200**

`kv_cache_dtype="nvfp4"` 那条 arm 打开了，§9.1 从 S6 欠到现在的账还清。同时加了
第四条 arm：**vLLM 自带的 NVFP4 KV cache**（FlashInfer 的 trtllm-gen 路径，SM100
上唯一另一个 4 bit cache）。

```text
        FLASH_ATTN      CUSTOM          CUSTOM/nvfp4    FLASHINFER/nvfp4
N=32    24/32  0.7500   24/32  0.7500   23/32  0.7188   21/32  0.6562
N=200   154/200 0.7700  154/200 0.7700  148/200 0.7400  137/200 0.6850
```

我们这条相对 BF16 掉 0.0312（N=32）和 0.0300（N=200），门槛 0.125；绝对值 0.7188 /
0.7400，门槛 0.60。两次掉幅几乎一样，而 N=200 的标准误只有 N=32 的 0.4 倍，所以
「掉三个百分点左右」是这套 FP4 cache 在 GSM8K 上真实的代价，不是小样本抖动。前两条
arm 逐 token 相同，在 N=200 上仍然成立。

**第四条 arm 要读得克制。** N=200 上我们领先 0.0550，也就是 200 道题里多对 11 道，
但两条 arm 的差别不止 cache：vLLM 的 NVFP4 路径还把 **query 量化成 FP8**，并且
trtllm-gen 内核**只能输出 FP8**，再反量化回 BF16（`flashinfer.py` 的
`q_data_type`、`_nvfp4_fp8_out`）。所以它多背了两处我们没有的误差，这个差值不能
读成「我们的量化更准」。它能支持的结论只有一条，也正是门槛写成单边的原因：**我们
这套 layout 不是掉队的那个**——相对 BF16 掉三个点，而机器上另一个 4 bit 方案掉
八个半点。反过来若哪天他们领先超过 0.125，那就说明掉幅里有一部分是这套 layout 自己
的成本，而不是 4 bit 的成本，那才是需要查的信号。

配置上有一处必须记：四条 arm 一起加了 `enable_chunked_prefill=False`。我们那条是
被护栏要求的（切开的 prompt 第二段从页中间续写），其余三条跟着改，是因为分块与否
会改变 batch 的组成方式，组成不同的 arm 既不能比 token 也不能比准确率。BF16 基线
从 S0 的 0.7500（N=32、分块开着）到这里的 0.7500，没有变化。

### S9 — 请求结束与清理

**做什么**

- slot 回收和 `seq_lens` 连续性检查已经融合在 S4 control kernel
- debug 模式检查 `error_code`；production 由 device fail-stop/gate 保证错误
  metadata 不进入 attention
- 不主动 free 任何 vLLM block（block 的生命周期归 vLLM）

**验收**

连续跑 200 个请求，slot 不泄漏，准确率不随请求数漂移
（漂移说明有跨请求的状态污染）；steady-state 全程无 custom DtoH/HtoD。

### S10 — 内存验证

这是整个项目的目的，必须是显式门槛，不能默认成立。

**做什么**

同一模型、同一 `gpu_memory_utilization`，对比 BF16 与 NVFP4：

- vLLM 报告的 `num_blocks`
- 相同显存下能跑到的最大上下文
- 加上尾巴 buffer（`max_num_seqs × 16 MiB = 128 MiB`）之后的净收益

另外测一笔**速度账**（§5.5）：BF16 开 CUDA graph 对 NVFP4 强制 eager 的
decode 延迟差。这不是门槛，是要显式记录下来的已知代价，
免得以后被人误读成「FP4 kernel 更慢」。有条件的话再测一个
BF16 也强制 eager 的对照，把「量化本身的代价」和「不能用 graph 的代价」分开。

**验收**

- `num_blocks` 比值接近 3.5
- 净内存收益为正，且随上下文增长而扩大
  （旧仓库正是在这里翻车：FP4 池是净增量，总量反而更大）
- 速度账已记录（无门槛，但必须有数）
- 自定义 steady-state decode 路径中：
  - `_check_device_values` / `aten::_local_scalar_dense` 次数为 0
  - DtoH/HtoD 次数为 0
  - metadata control kernel 为 1 次/step
  - promotion 为固定 launch，无 host-side 动态分支

#### S9 / S10 实施计划

**为什么两步一起做**：S9 的「steady-state 无 custom DtoH/HtoD」和 §11.4 那张
profile 硬门槛是同一件事，分两次做就要搭两套一样的观测。机制侧两步都几乎不欠
代码——S9 要的东西在 S4 和 S8 里已经建好了——真正的工作是把结论测出来。

**一个必须先解决的前提：这台机器上显存不是约束。** 实测 BF16 侧 9,269 blocks =
1,186,432 token，而本地唯一模型 Llama-3.1-8B 的 `max_position_embeddings` 是
131072。BF16 的 cache 已经装得下模型上限的 9 倍，所以「相同显存下能跑到的最大
上下文」两条臂都会停在 rope 上限而不是内存上限，测出来是同一个数，验收等于没验。

改成量**并发条数**：65536 上下文下 BF16 装得下 18.1 条、NVFP4 装得下 64.4 条，
`max_num_seqs=32` 时 BF16 必须排队而我们跑得满。但这被我们自己的护栏挡着——
`MAX_SUPPORTED_SLOTS = 8`。所以 slot 上限先要抬。

**抬到多少：32，不是 128。** 参考值：vLLM 在这台机器上（显存 ≥70 GiB 且非 A100）
`LLM` 默认 `max_num_seqs=1024`；vLLM 自带的 nvfp4 **没有任何上限**，因为它用
`reshape_and_cache_nvfp4` 把每个 token 直接按 `slot_mapping` 写进 paged cache，
scale 嵌在页内，根本不需要 tail buffer。tail buffer 是我们这套 layout 独有的
成本（V 沿 token 轴整页打包，半页无法量化）。成本随宽度的走势：

| slots | 每线程每矩阵 | 大致寄存器 | tail（Llama-8B） |
|---|---|---|---|
| 8（原） | 0.5 | 可忽略 | 134 MiB |
| **32** | 8 | ~56 | 537 MiB |
| 64 | 32 | ~224，逼近 255 上限 | 1.07 GiB |
| 128 | 128 | ~896，必须重做 | 2.15 GiB |

control kernel 是**单 CTA、4 warps**，里面同时活着约 7 个 `[BLOCK, BLOCK]` 矩阵
（`match`、`owns_match`、`older`、`pick`、`same_key`、`owns`、`sole_owner`），
`BLOCK = next_power_of_2(max_num_seqs)`。32 完全安全，128 要连 `num_warps` 和
算法一起改。抬上限本身对现有测试是免费的：tail buffer 按 `max_num_seqs` 分配而
不是按上限，不加宽就不多花一个字节。

**为什么不直接对齐训练需求。** `1.golongrl_nvfp4_vllm_clipping_N0_N3.md` 那条
rollout 要 `max_num_seqs=128`，但 slot 数是它四个缺口里最不要紧的一个：它还要
`enforce_eager=False`（护栏只收 `CUDAGraphMode.NONE`）、`block_size=16`（我们的
FP4 页固定 128）、以及 `max_num_batched_tokens=32768 < max_model_len=38912`——
这个组合 vLLM 强制要求 chunked prefill 开着，而切开的 prompt 第二段从页中间续写，
需要 §7.1 那个 FP4→BF16 dequant kernel。所以接那条线的前提是 §7.1 和 CUDA graph，
不是 slot 宽度；128 留到那时候和 `num_warps` 一起做。

**分五个 commit：**

| # | 内容 | Gate |
|---|---|---|
| C1 | `MAX_SUPPORTED_SLOTS` 8 → 32，注释写清真实成本；`test_control.py` 在 32 宽度下与参考模型对拍 | kernel + e2e 全绿，无 spill |
| C2 | 无 host sync 门槛（S9/S10 共用）+ `NVFP4_DEBUG` 开关 | 门槛过，且开关默认关时仍过 |
| C3 | S9：200 请求，同批两遍 token 一致、`error_code == 0`、每个 slot 都换过手 | 全过 |
| C4 | S10：65536 上下文 × 32 并发，NVFP4 跑得满而 BF16 做不到，且输出仍正确 | 全过 |
| C5 | S10：速度账三臂两点回归 + tail buffer 净内存记账，数字入文档 | 有数 |

C1 与 C2 是仅有的两处动 `src/` 的改动，走独立审阅（CLAUDE.md 第 10 条）。

**观测手段的取舍。** `torch.cuda.set_sync_debug_mode("error")` 罩住 steady-state
的 forward，谁同步就当场抛在哪一行——比解析 trace 精确得多。它自己警告
「does not yet detect all synchronizing operations」，所以 profiler 仍要跑一遍
做交叉核对，但**断言**不建在 trace 上。launch 次数（control 1/step、promotion
1/step、`layout.carve` 0/step、`write_kv` 每层一次）用 monkeypatch 计数器数，
理由同样是不想让断言依赖 trace 的解析。

**漂移为什么测 token 一致而不是准确率。** 200 道不同题分前后两半比准确率，会被
题目难度差异混淆，掉几个点说明不了是污染还是运气。改成同一引擎里把同一批 100 题
跑两遍——即第 1–100 与第 101–200 个请求——断言两遍逐 token 相同。C4 已经证明这条
路径的确定性足够（BF16 下 FLASH_ATTN 与 CUSTOM token 完全一致）。若两遍不一致，
那本身就是发现，退路是比对逐题一致率。

**速度账用两点回归。** 同一 prompt 分别生成 32 和 128 个 token，取斜率就是每步
decode 延迟，prefill 和启动这些常数项自动抵消，不必去 hook `execute_model`。
三条臂：BF16+graph、BF16 eager、NVFP4 eager。不设第四条 BF16/CUSTOM——BF16 下
`forward` 第一行就 `return super().forward(...)`，builder 也是 pass-through，
量到的只会是噪声。

**净内存账要显式记出来。** 现在 `test_kv_cache_memory.py` 里 tail buffer 是隐形的：
实测 NVFP4 拿到 144.94 GiB 而 BF16 是 144.83 GiB，我们**多**拿了 110 MiB，尽管
为 tail 付了 134 MiB——两个 backend 别处预留量的差异盖过了它。C5 要把 tail 的成本
单独列出来，并在扣掉它之后仍然断言收益为正。

#### `src/nvfp4_vllm/layout.py` — S1 / S6

**不要手算区域字节数。** scale 张量是 swizzled 布局，
手算出来的 `P × H × D/16` 未必对得上。用 kernel 自己的量化器探一次，
把真实形状、stride 和 page pitch 都记下来（`region_specs`，`lru_cache`
一次）。探针喂两页而不是一页，因为 page stride 只有 ≥2 页时才读得出来。

四个区域按 **block-major** 排：每个 block 内部依次是 `K_fp4`、`K_sf`、
`V_fp4`、`V_sf`。`carve` 保留量化器在页内的全部 stride，只把最外层
（页）那一维的 stride 换成 block pitch：

```python
def carve(kv_cache, num_kv_heads, head_dim):
    blocks, pitch = kv_cache.shape          # [num_blocks, page_bytes], uint8
    flat = kv_cache.view(torch.uint8)
    views, offset = [], kv_cache.storage_offset()
    for shape, strides, dtype, region_bytes in region_specs(...):
        typed = flat if dtype is torch.uint8 else flat.view(dtype)
        views.append(typed.as_strided((blocks,) + shape, (pitch,) + strides, offset))
        offset += region_bytes
    return tuple(views)                     # (k_fp4, k_sf, v_fp4, v_sf)
```

offset 和 pitch 都是字节数，而 `as_strided` 数的是元素——四个区域现在恰好都是
1 字节 dtype（`uint8` 和 `float8_e4m3fn`），所以两者相等。这不是可以默认成立的
事，`carve` 里有一条显式检查：探到非 1 字节的区域 dtype 就报错，
而不是安静地写到 2 倍远的地址上。

**为什么不是 region-major。** region-major（整个 buffer 先放所有页的 `K_fp4`，
再 `K_sf`……）能让每个区域连续、完全不用处理 stride，代价是 block `p` 的字节不再
落在 `[p × page_bytes, (p+1) × page_bytes)`。在 v1 的护栏下没人按地址搬 block，
所以它能跑；但 prefix caching 的 CoW、KV connector、KV offload 三条路径任意打开
一条就得回头重切。block-major 把这笔债提前还了：多出来的 page stride 由
qpack 和 decode kernel 各吃一次（S5.5），换来 block 永远是 vLLM 认为的那段字节。

`backend.get_kv_cache_shape` 返回 `(num_blocks, page_bytes)` 的字节视图：
第一维保持 `num_blocks`，避免踩到 vLLM 里可能存在的形状假设，
真实解释在 `layout.carve` 里完成。

> **验证过**：探针加起来的 `layout.page_bytes` 与 backend 报给 vLLM 的
> `nvfp4_page_size_bytes` 相等，`heads_kv ∈ {1, 8, 16}` 各测一次
> （`tests/e2e/test_layout.py`）；后者等于 `FullAttentionSpec` 的 147,456
> 由 S1 的 `test_kv_cache_memory.py` 守着。页小了写坏下一个 block，
> 页大了安静浪费 cache，两个数对不上就先停下来。

```python
ControlPlane(*, max_num_seqs, max_num_batched_tokens, device, page_size=128)
ControlPlane.prepare(
    *, block_table, seq_lens, query_start_loc, num_reqs, num_actual_tokens,
) -> ControlOutputs
ControlPlane.reset()      # 忘掉全部 slot，只在没有在途请求时合法
```

几处容易写错的地方：

- `query_len[row] = query_start_loc[row+1] - query_start_loc[row]` 在 device 算，
  `computed = seq_len - query_len`；
- `decode_row_indices` 固定容量 `[S]`，尾部填 `-1`。不能按 `decode_count` 切片，
  那要 DtoH；也不能填一个真实行号，decode kernel 会把那一行的 KV 重读一遍；
- `slot_last_seen` 用 int64，长跑的服务不能让 LRU 的序号回绕；
- `slot_keys` 初值 `-1` 而不是 0，因为 0 是 vLLM 的 null block，而 null block
  在存活判据里表示「这行不是请求」（§6.2）；
- 死行的 `seqused_*` 写 0 而不是留旧值，这样读整宽 buffer 的消费者看到的是
  「什么都不 attend」；
- 禁止清空整块 per-layer `tail_k/v`；只依靠有效长度和后续覆盖。

`error_code` 只用于 debug 定位。production 必须在消费 metadata 的 device
kernel 入口做 gate/assert，不能每步把 error word `.item()` 回 host。

#### `src/nvfp4_vllm/runtime.py` — S4 / S6

builder 与 `AttentionImpl` 没有直接对象引用，不能把 tail 只存在 builder。
`WriteRuntime` 挂在 attention module 上，由第一个跑起来的层创建、绑回全部层：

```python
class WriteRuntime:
    def __init__(self, *, num_layers, num_slots, num_kv_heads, head_dim, device):
        shape = (num_layers, num_slots, PAGE_SIZE, num_kv_heads, head_dim)
        self.tail_key = torch.zeros(shape, dtype=torch.bfloat16, device=device)
        self.tail_value = torch.zeros(shape, dtype=torch.bfloat16, device=device)
        self._views = {}

    def views(self, kv_cache):          # 按 data_ptr 缓存 layout.carve 的结果
        ...
```

**分成两次 lazy-once**（见 S6 的实测）：tail 在 profile run 的 `forward` 里分配
（`NVFP4Impl._bind_runtime`），carve 在第一次 `do_kv_cache_update` 里做。
中间那句「第一次 `do_kv_cache_update` 时创建 runtime」是错的，
那时显存已经全被 KV cache 拿走了。

关键合同：

- `tail_key/value` 各只有 **一次连续 allocation**，layer 是最外层维度，
  这样 promotion 可以直接把 `L` 当 grid 维度，不用 Python 循环 32 层；
- 每层 impl 只写 `runtime.tail_{key,value}[layer_index]` 的 view；
- `layout.carve()` 每层只做一次，按 `data_ptr` 记住——carve 本身只是地址算术，
  但它每次都造 4 个 Python 对象，而这条路径是每层每步都走的；
- tail 是 `zeros` 不是 `empty`：attention 会把整页尾巴读回来，
  序列长度之外的位置不能是 NaN 或 denormal；
- runtime 挂在本模型的 module/impl 上，不用进程级 singleton，避免同进程多 engine
  或多 rank 串状态；
- 写路径不需要 pointer 表：四个 view 是普通 tensor，直接当 kernel 参数传。
  跨层一次 launch 的 promotion 需要，所以 S8 加了 `destination_bases`
  （`int64 [4, L]`，由 `register_cache` 收到的每层 cache carve 出来，
  首次用到时组装一次）。

#### `src/nvfp4_vllm/write.py` — S6

两个 Triton kernel 加一个每层调用的入口。

`PageWorkTable.build()`（每步一次，在 builder 里）算出一张定宽表：
第 `row × columns + column` 格记着「从 activation 的第几个 token 起读一页」
和「写到哪个 block」，用不上的格 destination 填 -1。
grid 是 `(num_reqs,)`，每个 program 处理一行的全部列。
`max_query_len <= 1` 的步（纯 decode）直接返回空 slice，
省掉每层两次 launch。

`write_kv()`（每层一次，在 `do_kv_cache_update` 里）：

```python
quantize_key_tokens_into(key, key_pages_fp4, key_scales,
                         source_tokens, destination_pages)
quantize_value_tokens_into(value, ...)
_tail_write_kernel[(num_actual_tokens,)](...)
```

tail writer 的 grid 是 token 数，一个 program 搬一个 token 的
`heads_kv × head_dim` 个元素。它需要知道 token 在**序列**里的位置，
而这一步的 metadata 只说了 token 在 **batch** 里的位置——V2 runner 不填
`num_computed_tokens_cpu`（§10.4 第 4 条），所以位置是倒推的：

```text
position = seq_len[row] + token - query_start_loc[row + 1]
offset   = position - seqused_fp4[row]
```

即「离本行最后一个 token 有多远」加「本行总长」。prefill 和 decode 用的是同一个
式子，不需要分支。`offset < 0` 的 token 属于已经量化进 FP4 的页，不写。

行号也是在 kernel 里算的（`query_start_loc` 里有多少个边界 ≤ 本 token），
因为传一张 token→row 的表意味着 builder 要多发一个 kernel，
而这个求和最多 8 项。

#### `src/nvfp4_vllm/metadata.py` — S5 / S6 / S7

`NVFP4Metadata` 继承 `FlashAttentionMetadata`，加上 `ControlOutputs` 除
`error_code` 外的八个字段，S6 又加了 work table 的
`source_tokens` / `destination_pages`；`from_flash()` 负责拼接。
FP4 页表就是基类的 `block_table`，不另起名字透传。设计取舍见 S5。

S7 用 `num_decodes` / `num_decode_tokens` 换掉 `decode_row_indices` /
`decode_count` / `active_row_mask` 三个字段。那三个是为「固定 8 行 launch 加
device 侧 mask」准备的，batch 重排之后没有任何消费者；control kernel 里为算紧凑
排名而做的 `[8, 8]` 比较矩阵和 cumsum 也一并去掉。删除与新增放在同一个 commit，
是为了不让两套「哪些行是 decode」的机制共存——共存的话下一个读代码的人会选错。

#### `src/nvfp4_vllm/builder.py` — S5 / S6 / S7

`NVFP4MetadataBuilder` 继承 `FlashAttentionMetadataBuilder`，`build()` 在
`super().build()` 之后发一次 control kernel，再发一次 work table kernel。
`build()` 里没有任何读 device 值的断言，§6.3 讲了为什么以及靠什么替代。

S7 在此声明 `reorder_batch_threshold = 1`（仅 nvfp4，其他 cache dtype 下留 `None`
以免改变 BF16 路径的行为），并用 `split_decodes_and_prefills` 算出 `num_decodes` /
`num_decode_tokens` 放进 metadata。这两个数来自 `query_start_loc_cpu`，是 host 侧的
int，不构成同步——这是唯一允许的 host 断言例外，因为它读的本就是 CPU 张量：
断言前 `num_decodes` 行的 query_len 都是 1、其余都大于 1，把「decode 在前」这个
S7 赖以成立的前提钉死。

> `build()` 每步一次，跨全部层复用——**不要**把这些放进 `forward`。
> v1 的 `seqused_residual` 永远在 `[1, 128]`，调用 `fp4_decode` 时省略可选的
> `has_bf16`；kernel 直接由 `seqused_residual > 0` 推导，避免额外 tensor/op。

#### `src/nvfp4_decode_kernel/{interface.py,_kernel.py,_decode.py}` — S7

默认关闭的 trusted-metadata fast path **已随性能主线落地**：

```python
def fp4_decode(..., *, trusted_metadata: bool = False) -> torch.Tensor:
    ...
```

三层接口原样向下传，`_decode.py` 里 `if not trusted_metadata:` 跳过
`_check_device_values` 的 device 扫描，shape/dtype/device/stride 等不读 device
value 的 host 检查一条不删。production vLLM backend 传 `trusted_metadata=True`，
因为 `seqused_fp4`、`seqused_residual`、`residual_page_ids` 都由 S4 control kernel
生成。已有测试：`test_trusted_metadata_matches_checked_path_exactly` 与
`test_trusted_metadata_keeps_host_shape_checks`。

原计划里的 `active_row_mask` 参数不再需要。它是为「固定按 8 行 launch、在 device 上
抹掉无效行」服务的，而 batch 重排之后 decode 行是连续前缀，按 `num_decodes` 精确
发射，根本没有无效行——理由见 S7。

S7 只需再加一个可选 `query_padded_scratch`（同上），门槛是传与不传逐字节相等。
profile 中 `_check_device_values` / `aten::_local_scalar_dense` 为 0 这条检查保留。

#### `src/nvfp4_vllm/impl.py` — S2 / S6 / S7

三个职责：

1. `do_kv_cache_update`：满页 qpack 进 vLLM block，其余写尾巴（S6，已完成）
2. `forward`：decode 行走 `fp4_decode`，prefill 行走 cache-free varlen（S7）
3. 最后一层的 `forward` 末尾固定调用 `promote.launch(...)`（S8）

S6 的形状：

```python
def _bind_runtime(self, device):
    # profile run 里调用：这时 no_compile_layers 已经全了，KV cache 还没分配。
    modules = [m for m in get_forward_context().no_compile_layers.values()
               if isinstance(getattr(m, "impl", None), NVFP4Impl)]
    runtime = WriteRuntime(num_layers=len(modules), num_slots=self.num_slots, ...)
    for index, module in enumerate(modules):
        module.impl.runtime = runtime
        module.impl.layer_index = index

def do_kv_cache_update(self, layer, key, value, kv_cache, slot_mapping):
    metadata, _, _, _ = get_attention_context(layer.layer_name)
    write_kv(key=key, value=value,
             *self.runtime.views(kv_cache),
             tail_key=self.runtime.tail_key[self.layer_index], ...)

def forward(self, layer, query, key, value, kv_cache, attn_metadata, output, ...):
    if self.runtime is None:
        self._bind_runtime(query.device)
    return output          # S7 之前，nvfp4 下 attention 输出没有意义
```

`_bind_runtime` 会校验本模型全部 NVFP4 层的 `(num_kv_heads, head_size)` 一致，
并检查自己确实在 `no_compile_layers` 里——不在的话说明这层跑在一个不认识它的
forward context 里，共享的 runtime 就绑错了对象，宁可报错。
`layer_index` 用 dict 顺序，也就是层的构造顺序；它只需要是个稳定的双射，
顺带还可读。

`slot_mapping` 完全没用到：vLLM 按 token 给的是「第几个 block 的第几格」，
而我们的划分是「整页量化 / 尾巴」，两者对不上，位置全部从 control plane 的
每行答案推。

S7 的 `forward` 按 `num_decodes` / `num_decode_tokens` 把 batch 切成两段，两个数都由
builder 在 host 侧算好放进 metadata。decode 那段走
`fp4_decode(query[:n], ..., seqused_fp4[:n], block_table[:n], ...)` 再
`output[:n].copy_(...)`；prefill 那段走 `flash_attn_varlen_func` 的 cache-free 用法，
照抄 `flash_attn.py:1156-1164` 那个模式（`k=key, v=value`，
`cu_seqlens_k=cu_seqlens_q`，不传 `block_table`），只吃后缀
`[num_decode_tokens:]`。两段的 token 区间不相交，所以顺序无关。

prefill 那段的 `cu_seqlens` 需要减去 `num_decode_tokens` 重新起算。这一步由 builder
每步做一次，不在 `forward` 里每层重算——理由同 work table：它只取决于 batch，与层无关。

尾巴的可见性由 vLLM 保证：`unified_kv_cache_update` 的返回值被喂给
`unified_attention`，就是为了让 torch.compile 保住这个顺序，所以本步的 decode token
在 attention 读尾巴之前已经落进去了。`seqused_residual` 把它算在内，正依赖这一点。

#### `src/nvfp4_vllm/promote.py` — S8

```python
def launch(metadata, runtime) -> None:
    """Design §5.3. Exactly two fixed launches at last-layer forward end."""
    quantize_key_tokens_into(
        runtime.tail_key.view(-1, heads, head_dim),   # 层在源里是最外维
        *runtime.promotion_key_regions,               # 层 0 的两个区域视图
        metadata.promotion_source_tokens,
        metadata.promotion_pages,
        destination_bases=runtime.destination_bases,  # int64 [4, L]
    )
    quantize_value_tokens_into(...)                   # 同上，V 的两个区域
```

**顺序不能错**：本层 attention 跑完 → 才 promote。
因为本步的 metadata 说「这一页还是 BF16 尾巴」，全部 32 层都按这个读。

契约：

- kernel 内按 `promotion_source_tokens[row] + layer × S × P` 算 BF16 源地址；
- 按 `promotion_pages[row]` 算 FP4 目标页号，`< 0` 的 row 完全不读写；
- 层的基址来自 `destination_bases`，因为 32 层 KV cache 是独立分配的，
  指针不成等差（见 S8）；
- layer 是 grid 第三维，不在 Python 里循环 32 层；
- K/V 各一个固定 launch；不能每层各发 K/V 两个 launch；
- 不允许 `tail[:, slots]` 高级索引 materialize page batch；
- promotion 后不 `zero_()` tail，下一页按有效长度覆盖。

这样消除了旧 profile 中可能重新出现的 `2 × L × N_prom` BF16 page gather。

`runtime` 侧配套三样：`register_cache(layer_index, kv_cache)` 由
`do_kv_cache_update` 每层调用一次（用我们真正写进去的那个张量，不问 vLLM 要）、
`destination_bases` 首次用到时组装并缓存、`expect_layer(index)` 是那条常驻的
执行顺序断言。

#### `tests/e2e/test_kv_cache_memory.py` — S1

### 10.4 已知的坑

1. **`get_name()` 必须返回 `"CUSTOM"`**，否则 `attention.py:434` 的
   `AttentionBackendEnum[...]` 直接 `KeyError`。
2. **`do_kv_cache_update` 在 attention 之前调用**，不是之后。
   promotion 不能放在这里。
3. **`m.seq_lens` / `block_table_tensor` 是 GPU 张量**。production `build()`
   禁止 `.cpu()` / `.item()` / `.tolist()`；使用 S4 control kernel。
4. **`num_computed_tokens_cpu` 是废弃的 property 不是字段**
   （`backend.py:522-528`），而且 V2 runner 连它背后的 `_num_computed_tokens_cpu`
   字段都不填（`gpu/attn_utils.py:538-556`），所以任何依赖它的断言都是死代码。
   `seq_lens_cpu_upper_bound` 是 V2 唯一保证会填的 CPU shadow，禁用 spec decode
   时精确，但 production 不需要它；只用于 debug 对拍。
5. **`layer.layer_name` 只在 `forward`/`do_kv_cache_update` 的参数里拿得到**，
   `__init__` 没有。层号要用
   `vllm.model_executor.models.utils.extract_layer_index` 解析。
6. **`finished_req_ids` 拿不到**，见 §6.2 的缺席回收方案。
7. **scale 张量是 swizzled 布局**，别手算区域字节数，
   用 `layout.region_specs` 探；探针要喂两页，一页读不出 page stride。
8. **`carve` 出来的 view 不 contiguous、storage_offset 也不为 0**。
   任何要吃它的 kernel 都得接受显式 page stride，见 S6 的 S5.5 一段。
   scale 的 page stride 还必须 512 字节对齐（TMA），比 K/V 数据严。
9. **不要用动态 `nonzero()` 决定 promotion/decode launch**。固定容量 scratch
   + device mask 是零同步合同的一部分。
10. **carved KV views 和跨层 pointer table 只能初始化/重绑时构造一次**，
    不能在每层每步重复 `layout.carve()`。
11. **profile run 里 `do_kv_cache_update` 不会被调用，`forward` 会**。
    任何需要计进显存预算的 allocation 必须挂在 `forward` 上；
    等到第一次 `do_kv_cache_update`，KV cache 已经按「没有它」的前提分好了。
12. **长度 L 的序列量化 `(L-1)//P` 页，不是 `L//P`**。最后一个 token 所在的页
    还要接着写，封了它下一步就没地方放。`L = 128` 的 prompt 有 0 个 FP4 页和
    128 个尾巴 token，不是 1 个页和 0 个尾巴。
13. **CuTeDSL 的 JIT 函数里不能 early return**。「这一格没活干」要写成
    `if page >= 0: 做事`，不能写成 `if page < 0: return`。
14. **`cute.tile_to_shape` 会重建 layout，忽略传进来的 stride**。
    给 scale 换 page stride 只能在它之后动手（`_sf_layout_with_page_stride`）。
15. **真正在跑的是 V2 model runner**（`v1/worker/gpu/model_runner.py`），
    不是 `v1/worker/gpu_model_runner.py`。两者的 batch 准备、dummy run、warmup
    路径都不一样，读错文件会得出「profile/warmup 不会 build attention metadata」
    之类的错误结论（V2 会，见 S5）。启动日志里的 `Using V2 Model Runner` 是判据。
16. **启动阶段会有几步假的 `build()`**：profile forward 的 batch 全部 key 在
    null block 上，warmup 的两步则和真实请求无法区分。任何「引擎刚起来时状态是
    干净的」假设都不成立，测试要量增量而不是绝对值。
17. **32 层的 KV cache 是 32 次独立的 `torch.zeros`**
    （`v1/worker/gpu/attn_utils.py:186`），指针不成等差。任何「把各层拼成一个
    `[L, ...]` view」的写法都是错的，要靠显式基址表。
18. **一次 `quantize_*_tokens_into` 固定约 49 µs，与它有没有活干无关**
    （36.5 µs 在 Python 包装，12.9 µs 在 CuTeDSL dispatch）。凡是每步都要发的
    路径，launch 次数不能随层数或 batch 内容增长。
19. **KV cache 里的页偏移必须 64 位算**。页号乘页距在 14563 块（2 GiB）上过
    `2^31`，而单层区域是几个 GiB。CuTeDSL 的 shape/stride 默认 `Int32`，写成
    `Int32` 不会报错，只会在高页号上安静地写到别处。见 S8 的 C1 实测。
20. **`num_reqs` 宽度的数组，行号只在本步有意义**。vLLM 在 prefill 步和之后的
    decode 步之间会重排 batch，同一个请求换行号。跨步比对必须另找身份。

## 11. Bookkeeping 开销预算与优化优先级

### 11.1 旧实现的实测基线

旧 profile workload：`K=8, L=32, 64 decode tokens, 5 promotions`。
NVFP4 相对 BF16 的 bookkeeping 增量是：

```text
+8.537298 ms Self-CUDA
+2,616 CUDA events
```

来源：`nvfp4_attn/docs/kernel_new/docs/3.bookkeeping_overhead.md:56-106`。
11 个 event family 的时间不能直接相加成 wall-time 收益；这里只拿它们定位结构。

| 旧 event family | 旧增量 | 新设计状态 |
|---|---:|---|
| INT metadata index-select | +2.151698 ms / +512 | `PreGroupedViews` 四次 gather 结构性删除；由 1 次/step control kernel 替代 |
| Pageable DtoH | +1.720813 ms / +494 | v1 的自定义 steady-state 热路径目标为 **0** |
| CatArray | +1.426139 ms / +64 | **不会自动消失**；prefill 必须用 indexed/descriptor qpack 才能清零 |
| BF16 page index-select | +0.859586 ms / +320 | 旧 vLLM BF16 pool gather 删除；promotion 必须用 indexed qpack，防止从 tail 重新 materialize |
| Pageable HtoD | +0.613995 ms / +363 | views 双写删除；GPU slot control 后 custom metadata upload = 0 |
| DtoD | +0.611106 ms / +380 | count staging 删除；Q scratch/repack 等执行流量另算 |
| Pinned DtoH | +0.608677 ms / +180 | views scalar sync 删除；trusted fast path 必须让 wrapper `.item()` 归零 |
| integer add/sub | +0.296326 ms / +158 | 长度算术保留但融合进 1 次 control kernel |
| `index_kernel` | +0.176667 ms / +70 | row/destination selection 仍需要，但要融合进 control/indexed qpack |
| BF16 direct copy | +0.214558 ms / +64 | tail 写是业务数据；prefill 临时 copy 不允许换个 symbol 继续存在 |
| tagged `index_put` | +0.040257 ms / +11 | tag/state transition 完全删除 |

### 11.2 相对官方 vLLM NVFP4 的下界

官方 FlashInfer/trtllm-gen 路径：

- cache shape 直接是 `(num_blocks, 2*H_kv, P, 72)`；
- K/V 每个 token 直接量化写入；
- K/V data/scale 通过零拷贝 `split/as_strided` 暴露；
- 没有 BF16 tail、slot allocator、promotion 或第二套 page state。

它仍然有 stock vLLM 的 indptr/page-indices/last-page-length metadata，不能说
“绝对零 bookkeeping”；但 NVFP4 相对 stock backend 基本没有额外 page-state
bookkeeping。因此它是我们的下界。

我们的增量分两类：

**recent-BF16 设计固有：**

```text
固定 tail memory = 8 slots × 16 MiB = 128 MiB

每新 token/layer 的 cache write:
BF16 tail = 2 × 8 × 128 × 2 B = 4096 B
官方 FP4 = 2 × 8 × (64 data + 8 scale) B = 1152 B
差值      = 2944 B/layer/token
32 层     = 94,208 B ≈ 92 KiB/token
```

promotion 还需要读 BF16 tail 再写 FP4。这是 recent-BF16 的必要数据路径，
不是 bookkeeping bug。

**实现选择，可消除：**

- builder 的 DtoH/HtoD；
- Python slot map / request loop；
- promotion host branch；
- 每层 `_check_device_values().item()`；
- 每步重复 `layout.carve()`；
- Q scratch 的反复 allocate/zero；
- GQA scale 的 `take + index_copy_` repack；
- promotion/prefill 的 page materialization。

### 11.3 优化顺序

#### P0 — v1 必须完成：零同步 control path

1. S4 once-per-step GPU control kernel；
2. S7 trusted metadata fast path，删掉 production wrapper 的 128–160 次/step
   host scalar read；
3. S8 device 侧目标页号 + 每步固定两次 launch；
4. cache carved views 与 pointer table 缓存一次；
5. 不清零 tail，只由有效长度约束读取。

P0 没完成，不能进入 S10 性能对比。

#### P1 — v1 profile gate 前完成：indexed/in-place qpack

promotion qpack 直接接收：

```text
source_tail_base
promotion_source_tokens
promotion_pages
destination_bases
```

kernel 内算地址，不允许 `tail[:, slots]` / `index_select` 生成 contiguous page
batch。prefill qpack 同理接受 source descriptors/offsets，不能用 `torch.cat`。

目标是让旧 profile 的：

```text
320 BF16 page gathers
64 CatArray
64 BF16 direct-copy materialization
```

在新 trace 中全部为 0；只把它们换成另一类 DtoD copy 不算完成。

#### P2 — profile 证明后再做：Q 路径

当前 standalone wrapper 每层会分配/清零 padded BF16 Q、FP4 Q 和 scale scratch，
GQA scale 还会 `take + index_copy_`。优化方向：

- 按 `max_num_seqs=8` 预分配 persistent Q/output scratch；
- Q quantizer 直接写 kernel 要的 GQA scale layout；
- 用 byte-equality 和现有 `test_quantize_query.py` 守住布局。

这不是 page bookkeeping，只有 profile 显示它占比明显才做，避免提前改 kernel。

### 11.4 S10 profile 硬门槛

对 steady-state decode 的 custom delta：

```text
DtoH/HtoD attributable to nvfp4_vllm = 0
aten::_local_scalar_dense / .item()  = 0
control kernel                       = 1 / step
control work                         = once-per-step, not once-per-layer
promotion launch                     = fixed per step, no host branch
layout.carve                         = 0 / step（只在初始化/重绑）
BF16 promotion gather                = 0
CatArray / prefill materialization   = 0
```

同时记录：

- total CUDA events、Self-CUDA、wall latency；
- BF16 graph / BF16 eager / NVFP4 eager 三组；
- tail write 与 promotion payload 流量（业务数据）单独列出，不混进 bookkeeping；
- 如果某类 event 下降但 total/wall 不改善，不宣称优化完成。
