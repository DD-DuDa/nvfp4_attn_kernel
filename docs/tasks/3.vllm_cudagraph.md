# 为 NVFP4 vLLM 路径开启 CUDA graph

本文是任务计划。目标是让 `nvfp4_vllm` 后端能被 vLLM 捕获成 CUDA graph，从而把
`docs/reports/2.bf16-comparison.html` 记录的那笔 **9,888 µs/step** 的 host 开销拿
回来，使这套引擎能承担 RL rollout。

**写这份计划时没有修改任何代码。** 下文所有代码引用都是当前 `HEAD` 的事实，行号
在改动落地后会漂移。

> **哪个 vLLM 说了算。** PATH 上的 python 跑不了本仓库的任何一个测试套件——它的
> CuTeDSL 没有 `iket`，也没有编译好的 vLLM。测试必须经 `scripts/run_tests.sh`，它
> 指向 `BitKV_nvfp4/_local/envs/vllm-nvfp4`（cutlass 4.6.0，与 `pyproject.toml` 的
> pin 一致）。那个环境里的 `vllm` 解析到 **`BitKV_nvfp4/third_party/vllm`**
> （`1ad84fe`），而不是本仓库的 `third_party/vllm`（`d6dbdb9b0`）。两者只有
> `gpu_model_runner.py` 不同，且 §3.2 引用的三处在两份里都成立；下文行号取本仓库
> 那份，运行时行为以前者为准。

**本计划由 §2 的六项决策定稿，全部已与用户拍板，无待决项。**

---

## 1. 为什么现在做这件事，以及能拿回多少

`docs/reports/2.bf16-comparison.html` 用两点差分测了三条臂（Llama-3.1-8B，SM100，
batch 8 / prompt 1000）：

| 臂 | µs/step | 是什么 |
| --- | ---: | --- |
| BF16 + CUDA graph | 3,807 | BF16 部署实际跑的配置 |
| BF16 eager | 13,695 | 同样的算术，去掉 graph |
| NVFP4 eager | 23,142 | 我们今天 |

报告把 23,142 对 3,807 的 6.1× 拆成两笔独立的账：**四个 bit 收 +9,447 µs**，
**不能用 CUDA graph 另收 +9,888 µs**。后者与量化无关，是本计划的全部标的。

而 9,447 那一笔里 GPU 只占 239 µs（4,522 对 4,283），attention kernel 本身反而比
BF16 快 208 µs。也就是说 NVFP4 的 GPU 侧已经基本合格，**剩下的几乎全是主机没跟上
设备**——`unified_attention_with_output` 的纯前端 self-CPU 时间就占 host delta 的
56.8%。这类开销正是 CUDA graph 消除的对象。

### 1.1 可证伪的目标

本计划的两项 GPU 侧改动在报告的逐 kernel 表上是可加的：

- 临时缓冲清零 **196.2 µs**（131 次 launch），
- split-K combine **74.2 µs**（32 次 launch）。

两笔去掉后 NVFP4 的 GPU 总时间应从 4,522 µs 落到约 **4,250 µs**。报告自己的自校验
给了换算依据：graph 下 wall 约等于 GPU 时间（BF16 那条臂 wall 3,807 对 profiler 下
GPU 4,283，profiler 抬高约 12%）。

> **验收目标**：`NVFP4 + graph` 落在 **4.0–4.5 ms/step**，相对 `BF16 + graph` 的
> 比值 **≤ 1.25×**。今天这个比值是 6.1×。

这个目标是可证伪的：做完一量就知道。若落不进区间，说明 host gap 不是按 launch 数
线性的，报告 §「没解决的」第 1 项（attention wrapper 的 Python/CuTeDSL 前端，
≈5.2 ms/step）的归因需要重做，那是下一个任务而不是本任务的失败。

## 2. 六项决策（已定稿）

> **D1 范围只做 graph。** `max_num_seqs ≤ 32`、拒绝 chunked prefill、`block_size`
> 固定 128 这三条 guard 全部保留不动。它们只影响 RL rollout 的快慢，不影响能不能
> 跑；而 CUDA graph 不做，整体慢 6.1×，那才是 blocker。RL 侧的配置适配见 §7.3。

> **D2 split-K 全局钉死 1。** 见 §4.3 的三条理由。`split_k_heuristic` 保留为文档化
> 函数，继续服务 benchmark 与 probe，只是不再参与生产派发。

> **D3 padding 行的处理方式是「核实并写成契约」**，不是加防御分支。§3 的核查结论
> 是控制面已经把两种假行都判成非 live，所以要做的是把这个行为固化成
> `tests/kernel` 的用例，而不是在 kernel 里加运行期检查。

> **D4 guard 放行 vLLM 自己解析出的 `FULL_AND_PIECEWISE`。** 不限制到
> `FULL_DECODE_ONLY`。理由见 §4.1。

> **D5 顺手做两件、不做第三件。** 做：量化 scratch 改常驻（§4.4）、capture 后清
> slot 表（§4.5）。**不做**：把 BF16 尾巴 buffer 注册进 `CuMemAllocator` 以便 sleep
> 时归还那 576 MiB。第三件会动到 profile run 的显存记账，且对「图能不能跑」不是
> 必需的，留给后续任务。

> **D6 验收到端到端。** `tests/e2e` 全套在 graph 开/关两种配置下各跑一遍都要绿；
> `tests/e2e/test_speed_account.py` 加第四臂给出 §1.1 的数字；真跑一次 dapo_math
> rollout 量吞吐。

## 3. 核查结论：哪些地方**不需要**改

这一节是本计划最重要的部分。开 CUDA graph 通常要处理四类问题——缓冲地址稳定性、
padding 行语义、主机侧状态跨步一致性、捕获期同步——**在这个代码库里前三类都已经
被提前解决了**。逐条给证据，避免实现时重复劳动或误加防御代码。

### 3.1 控制面一行都不用改

`src/nvfp4_vllm/control.py:154-158`：

```python
    # ``num_reqs`` only bounds how far the input tensors may be read. A row is
    # a request only if vLLM gave it both a length and a block: padding rows
    # keep a stale block table entry under a zeroed length, and the rows of a
    # dummy batch keep a nonzero length over the null block.
    live = in_batch & (seq > 0) & (key != _NULL_BLOCK)
```

这条注释写的就是 CUDA graph 的两种假行：

- **replay 时的 padding 行**——vLLM 把它们的长度清零，于是 `seq > 0` 不成立；
- **capture 时的 dummy 行**——block table 读到 `NULL_BLOCK`（`control.py:75` 记录了
  「vLLM's block pool takes block 0 out of the free list at startup」），于是
  `key != _NULL_BLOCK` 不成立。

两种都被判成非 live，落成 `row_to_slot = -1`、`seqused_fp4 = 0`、
`seqused_residual = 0`。

宽度也对得上：控制 kernel 的 store 用的是 `mask=is_slot`（`idx < NUM_SLOTS`）而非
`in_batch`，**每步都把整个 slot 宽度写满**，所以 `num_reqs` 之外的行不会留下上一步
的残值。

地址稳定性同样已经就位，`ControlPlane` 的 docstring（`control.py:360-366`）直接写
着：

> All buffers are allocated once at the high-water mark. Reallocating inside a
> step would both cost a synchronization and move the addresses a captured graph
> would have baked in.

`ControlOutputs` 返回的是这些常驻缓冲的切片视图（`control.py:503-511`），切片与母
张量共享基址，所以捕获期烙进图里的指针在 replay 时仍然指向本步写入的数据。

### 3.2 vLLM 侧的配合已经核实

- `gpu_model_runner.py:2314-2316` 把 padding 行的 block table 填成 `NULL_BLOCK_ID`，
  与 §3.1 的 `key != _NULL_BLOCK` 正好咬合。
- `_build_attention_metadata` 用 `num_reqs_padded` / `num_tokens_padded` 建
  `CommonAttentionMetadata`（`gpu_model_runner.py:2283-2285`、`:2408`），所以我们的
  `ControlPlane.prepare` 每步覆盖的宽度**等于图捕获的宽度**，不存在「图读 32 行、
  控制 kernel 只写了 5 行」的错位。
- 捕获时 `max_seq_len` 被设成 `max_model_len`（`gpu_model_runner.py:2291-2295`）。
  这会把 `decode_page_columns` 冻结成最大值——见 §3.3。

### 3.3 `decode_page_columns` 冻结成 max 不再是问题

`builder.py:205-207` 从 `common_attn_metadata.max_seq_len` 算出它，捕获时会取到模型
容量对应的最大列数。乍看是个隐患，但 `_decode.py:50-51` 说清楚了它的唯一语义：

> ``max_pages_per_row`` is the page table's second extent, not the pages the rows
> actually consume, because the real lengths live in ``seqused_fp4`` on device.

它的唯一消费者是 `split_k_heuristic`。D2 钉死 split-K 之后这条担心自动消失——真实
工作量始终由 `seqused_fp4` 界定，与页表宽度无关。

### 3.4 `expect_layer` 不会失步

`runtime.py:154-172` 的层序检查跨步累加而不在层 0 重置，用意是「一个只跑了部分层的
步会被下一步的第一层撞出来」。图 replay 时一行 Python 都不跑，计数器零增量——而
一个完整步结束后它本来就回到 0，所以 replay 前后一致。

这个检查在 replay 期间确实不生效，但它保护的不变量（promotion 在最后一层之后触发）
是在捕获时定型并烙进图的：捕获时对，之后永远对。

### 3.5 padding 行的契约是被构造性验证的

由 §3.1，capture 用的 dummy batch 里**每一行都是非 live**。也就是说捕获出来的那张
图本身就是「所有行都是 padding」的极端情况。**图能捕获成功且 replay 不崩，等价于
padding 行契约成立。**

这不免除 D3 要求的单元测试——测试的价值在于把行为钉在 `tests/kernel` 里，防止后续
kernel 改动悄悄破坏它——但它说明这条路径不需要新的运行期防御。

### 3.6 promotion 本来就能进图

`impl.py:203-206` 在最后一层调 `promote.launch`。它跑在 attention custom op 内部，
形状是固定的整个 slot 宽度（`control.py:349-352` 注释：「promotion launches over the
whole table so that its shape does not follow the batch」），没有主机分支。

`guards.py` 今天拒绝 graph 的理由正是「promotion under capture is unverified」。本
计划的验证方式就是把它跑通，而不是改它。

### 3.7 两个入口都在 vLLM 的 custom op 后面

KV 写入走 `NVFP4Impl.do_kv_cache_update`（`impl.py:103`），attention 走
`NVFP4Impl.forward`（`impl.py:157`）。它们分别被 `vllm::unified_kv_cache_update` 和
`vllm::unified_attention_with_output` 包住，两者默认都在 `splitting_ops` 里
（`compilation.py:765`、`:1146`、`:1174`）。

后果有两条，都是好消息：Dynamo 不会 trace 进我们的 Triton / CuTeDSL；以及在
piecewise 图里，我们的代码**永远在图外裸跑**，piecewise 部分只包含 MLP / norm / rope
这些 vLLM 对每个模型都测过的算子。

## 4. 要改的六处

### 4.1 `builder.py`：声明正确的 CUDA graph 支持级别

**现状。** `NVFP4Builder` 继承 `FlashAttentionMetadataBuilder`，因而继承了
`_cudagraph_support = AttentionCGSupport.ALWAYS`（`flash_attn.py:352-356`，FA3 分支）。
`ALWAYS` 是在宣称「混合 prefill+decode 批也能进完整图」，对我们不成立：prefill 走
varlen FlashAttention，token 数逐步变化，形状不可能冻结。

**改法。** vLLM 把这个属性暴露成 classmethod：

```python
    @classmethod
    def get_cudagraph_support(
        cls,
        vllm_config: "VllmConfig",
        kv_cache_spec: "AttentionSpec",
    ) -> AttentionCGSupport:
        return cls._cudagraph_support
```

签名里带 `vllm_config`，所以可以按 `cache_config.cache_dtype` 分流：NVFP4 返回
`AttentionCGSupport.UNIFORM_SINGLE_TOKEN_DECODE`，其他 dtype 原样交回
`super()`。BF16 走这个 backend 的行为完全不受影响——这条路径今天是
`forward` 第一行的 `super().forward(...)` 直通，不应该因为我们而降级。

**后果。** `CompilationConfig.resolve_cudagraph_mode_and_sizes`
（`compilation.py:1353-1396`）看到 mixed-mode FULL 不被支持，且 `splitting_ops`
含 attention，就会自动落到 `FULL_AND_PIECEWISE`——正是 vLLM 的默认值
（`vllm.py:267`）。**用户什么配置都不用传。**

- 纯 decode 步 → 整个模型前向一张完整图，host 开销归零。这是 RL rollout 里绝大
  多数的步。
- 混合步（有新请求进来做 prefill 的那一步）→ piecewise 图，我们的代码在图外。

### 4.2 `guards.py`：撤掉 `cudagraph_mode` 的一刀切拒绝

删掉 `guards.py:119-127` 那条 `cudagraph_mode != CUDAGraphMode.NONE` 就抛
`UnsupportedConfigError` 的检查。

**不换成更窄的 guard。** 如果用户硬传 `FULL`，vLLM 的 resolver 会在
`compilation.py:1372-1387` 自己报错，信息里带着后端名和支持级别，比我们能写的更准。
再加一层只会产生两处措辞不同的错误。

其余 guard（32 slot 上限、拒绝 prefix caching、拒绝 chunked prefill、拒绝
speculative decoding / KV offloading / microbatching / pipeline parallelism）全部
保留。

### 4.3 `_kernel.py`：split-K 全局钉死 1

**现状。** `_kernel.py:138-153`：

```python
    splittable = (
        all(argument is None for argument in residual_arguments)
        and has_bf16 is None
    ) or (complete_residual and query_padded_bf16 is not None)
    # Only a scatter by index forces the single-tile path; the split path can
    # write into a caller's buffer, it just cannot reorder rows on the way.
    scatter_by_index = out_indices is not None
    num_splits = 1
    if splittable and not scatter_by_index:
        device = query_fp4.device
        num_splits = split_k_heuristic(
            query_fp4.shape[0],
            key_pages_fp4.shape[2],
            fp4_page_table.shape[1],
            sms=torch.cuda.get_device_properties(device).multi_processor_count,
        )
```

vLLM 的 decode 路径满足第二个析取项（`complete_residual` 成立，且 `impl.py:246` 传了
`query_padded_scratch`），所以**今天确实会走进 split-K**。

**三条理由叠加。**

1. `docs/infos/2.decode_kernel_state.md` §4.7 实测：「split-K 一致带来 13–23% 的
   开销，b1/b4 上试图用它填占用率的尝试是负收益」。
2. 捕获时页表宽度被冻结成 max（§3.3），启发式会据此给小 batch 选出高 split 数并
   **永久烙进图里**。以 `max_model_len=10240`、`heads_kv=8`、148 SM 算，捕获尺寸 1
   会拿到 8 路拆分——一个在报告里被证明是负收益的选择，从此每步都付。
3. split 路径要为 FP32 部分结果和 LSE 额外 `torch.zeros`，这些分配与清零同样会被
   录进图，每次 replay 重跑。性质与 §4.4 那一笔相同。

顺带还消掉 `torch.cuda.get_device_properties()` 这个每层一次、一步 36 次的主机调用。

**一处 API 形状的判断。** `tests/kernel/test_fp4_decode_correctness.py:988-994`、
`:1119-1124` 是**经由 `fp4_decode`** 覆盖 split 路径的（先断言启发式返回 >1，再走
公共入口）。直接钉死会让这些用例静默失去覆盖，而 split-K 的实现代码还在。

方案：给 `fp4_decode` 加显式的 `num_splits: int = 1` 参数。生产调用不传，恒为 1；
测试显式传 2/4/8 打 split 路径。`split_k_heuristic` 作为纯函数保留并保留其单测
（`tests/kernel_profile/test_bench_decode.py:105-119`），继续服务
`bench_decode.py:416` 与各 probe（`probe_graph_gate.py`、
`probe_bandwidth_headroom.py:195-221` 都直接 monkey-patch 它）。

这是全篇唯一一处在没有用户明确指示下决定的接口形状。它不违反「保持公共 API 小」
——参数有默认值，生产签名不变——但需要在 review 时被单独看一眼。

**实施后实测：默认值 1 需要用数据重新确认。** 把探针的旋钮改成显式 `num_splits`
之后顺手测了几个点，**在图重放下** split-K 在低 batch 是大幅正收益，与本节理由 1
引用的 §4.7 相反：

| 配置（hq32/hkv8，seqlen 16384 除非另注） | 1 split | 多 split |
|---|---|---|
| `probe_graph_gate` b4，图重放 | 66.7 µs | 33.3 µs（8） |
| `probe_bandwidth_headroom` b4 | 65.1 µs | 32.9 µs（8） |
| `(1, 8, 128)` | 66.0 µs | 18.8 µs（16） |
| `(1, 1, 128)` | 217.5 µs | 22.8 µs（32） |
| `(16, 8, 128)` | 68.9 µs | 85.9 µs（2） |

同一配置下 `bench_decode` 给出相反结论（b4 `fp4_pure_fp4q`：1 split 67.8 µs，
8 splits 109.6 µs）。两边 1-split 的数字几乎一致，8-split 差三倍，差别就是图重放：
split 路径多两次 launch 加 FP32 partial 的清零，eager 下这些主机开销吃光 GPU 收益还
倒亏；进了图之后 launch 免费，并行收益才露出来。batch 16 时又反过来，因为 148 个 SM
已经填满——这条曲线是自洽的。

所以 §4.7 那句「一致 13–23% 开销」多半是 eager 下的结论，而本任务恰好在拆掉它的前提。

**这不动摇本节的改法，只动摇默认值。** 理由 2 依然成立：捕获时页表冻结在
`max_model_len`，启发式据此选出的数字会被永久烙进图，所以不能让启发式在派发路径上
决定。把选择权交给显式参数是对的；1 只是当前的默认。真正该回答的问题移交 §7.2：在
真实 vLLM 图重放下扫 `num_splits ∈ {1, 4, 8}`，按 RL rollout 的实际 batch 与
序列长度定默认值。低 batch 正是 RL rollout 的常态，所以这一项的收益可能不小。

### 4.4 `_quantize.py`：量化 scratch 改成常驻

**现状。** `quantize_query` 每次调用 `torch.zeros` 两个张量
（`_quantize.py:44-64`）：`query_fp4` 与 `scale_storage`。`torch.zeros` 不只分配，还
要清零，那是真的 GPU kernel。

报告实测：这一 bucket 每步 **131 次 launch、196.2 µs GPU**，相对 BF16 的 3 次多出
128 次，占全部 165 次额外 launch 的四分之三；主机侧的 `aten::empty/zeros/fill_` 另
占 host delta 的 8.2%。

**为什么开图后更要紧。** 这些清零会被录进图，每次 replay 重跑。今天一步 23,142 µs，
196 µs 占 0.8%，是噪声；开图后一步约 4.3 ms，同样的 196 µs 占约 **4.6%**。绝对值
没变，相对权重涨了六倍。

**清零只对两个缓冲中的一个是多余的——这一点实测过。** 原本以为「量化 kernel 反正会
覆盖整块内存，清零从头到尾没必要」。对 `query_fp4` 成立，对 scales **不成立**：量化
kernel 每个 KV head 只写 `heads_q // heads_kv` 个 slot，其余永远没人写。用 `0xA5` 预填
`torch.empty` 做对照，packed query 仍与全新分配逐字节相等，scales 则发散。所以 scales
必须在分配时清零一次，此后永不再清；这是常驻化之后唯一无法靠形状检查兜住的契约。

**改法。** 在 `LayerRuntime` 里按高水位（`max_num_seqs` × heads × head_dim）分配一
次，像现有的 `query_padded` 那样通过参数传进 `quantize_query`。实测
1,114,112 B（`query_fp4` 64 KiB + `query_scales` 1 MiB），相对旁边 32 MiB 的
`query_padded` 是 3.3% 的增量。

其中 scales 那 1 MiB 有四分之三是寻址不到的：storage 按 `heads_q` 定尺寸，而
`as_strided` 出来的视图只够到 `heads_kv` 个 head slab。Qwen3-8B 是 32 取 8。真正被写的
更少——3 行 GQA 32:8 下视图 24,576 B 里只有 768 B 非零。缩它属于改 layout 而不是改缓冲
策略，不在本任务内，但那一兆在哪里浪费掉的，记在这里。

**必须在 profile run 期间分配。** vLLM 的显存模型是「跑一次 profile forward，看还剩
多少，剩下的全给 KV cache」，之后再开的任何东西都是从已经许诺给 cache 的显存里挖。
`impl.py:58-64` 的 `_bind_runtime` docstring 已经把这条写清楚了，照抄它的时机即可。

**可证伪的中间检查点。** 报告的「下一个受控实验」给了预测：改完之后每步 launch 应
从 638 掉到约 510，GPU 从 4,522 掉到约 4,326。这一项可以在开图之前先单独验证。

### 4.5 `builder.py`：capture 之后清一次 slot 表

由 §3.1，dummy batch 的行已经被判非 live，所以这是**保险而不是修复**。但它一行
代码、成本为零，能把「录图那 14 次假前向有没有污染 slot 表」这个疑问整个删掉，
而那个时刻还没开始服务，没有真实状态可丢。

**落点不需要改 vLLM。** `AttentionMetadataBuilder.build_for_cudagraph_capture` 是独立
方法，默认转调 `self.build`：

```python
    def build_for_cudagraph_capture(
        self, common_attn_metadata: CommonAttentionMetadata
    ) -> M:
        """
        Build attention metadata for CUDA graph capture. Uses build by default.
        Subclasses that override this method should call self.build or
        super().build_for_cudagraph_capture.
        """
        return self.build(
            common_prefix_len=0, common_attn_metadata=common_attn_metadata
        )
```

在 `NVFP4Builder` 里覆盖它、置一个标志位并转调 `super()`；在正常 `build()` 里发现
「上一次是 capture、这一次不是」时调一次 `self.plane.reset()`
（`control.py:417-423`）并清标志。全部逻辑留在我们自己的 builder 内。

## 5. 三个必须实测的风险

### 5.1 CuTeDSL / Triton 的 JIT 必须发生在捕获之前

捕获期间触发编译会分配、启动、同步，全都是致命的。vLLM 每个捕获尺寸会先跑 warmup
再捕获，理论上够；但 CuTeDSL 的编译缓存是按形状建键的
（`_decode.py:24-25` 的 `_decode_compile_cache` / `_split_decode_compile_cache`），
需要确认 warmup 走的形状与 capture **完全一致**，包括 §3.3 冻结后的页表宽度。

**这是我判断最可能第一次就炸的地方。** 症状会是捕获期报 illegal operation during
capture 或直接挂死。

### 5.2 `trusted_metadata=True` 必须成立

`_decode.py` 的校验里有 `seqused_fp4 < 0`、`seqused_residual > 128` 这类**设备值
扫描**（`:675-690`、`:785-802`）。它们在捕获期会引入设备→主机读取，是致命的。

`impl.py:242-245` 传的是 `trusted_metadata=True`，并附了理由（「Checking would mean
reading them back, which costs a synchronization per layer」）。这条今天已经对，但
实现过程中不能被改坏，测试里要有对应的守卫。

### 5.3 padding 的浪费有上界但不是零

捕获尺寸取 `cudagraph_capture_sizes`，vLLM 选不小于真实 batch 的最小档，所以最多
**2× 行填充**。钉死 split-K 之后每 (row, head) 的 CTA 相互独立，浪费只落在 attention
kernel 的 CTA 数上，不影响正确性，也不会跨行污染数值。

这也是 D2 的一个额外理由：图把 batch padding 到固定尺寸之后，「用 split-K 填占用率」
这个动机本身就被 padding 取代了。

### 7.2 性能

`tests/e2e/test_speed_account.py` 今天是三条臂，其 docstring 明说「only the first is
recoverable by finishing the CUDA graph work」。加**第四臂 `NVFP4 + graph`**，给出

通过条件：`NVFP4+graph / BF16+graph ≤ 1.25`。

#### `num_splits` 的默认值：已在服务中的引擎里扫完

§4.3 末尾把这一项留成了开放问题，因为支持默认值 1 的那条证据
（`docs/infos/2.decode_kernel_state.md` §4.7 的「一致 13–23% 开销」）是 eager 下测
的，而本任务恰好拆掉了它的前提。探针在图重放下给出了相反的结论，但探针不是 step：
图里装的是整个模型前向而不是一个 kernel，batch 组成会随请求退休而移动，页表还被冻结
在 `max_model_len`。所以这一轮是**在真实 vLLM 引擎里、graph 打开**重测的。

**量法。** Llama-3.1-8B（`heads_q=32`、`heads_kv=8`）、B200（148 SM）、
`kv_cache_dtype=nvfp4`、`max_num_seqs=32`、graph 走 §4.1 解析出的
`FULL_AND_PIECEWISE`。**一个进程一条臂**：split 数是编译期常量，capture 会把它烙进
图，在活引擎里改它只会留下一批装着旧值的图。`cudagraph_capture_sizes` 显式设成被测
的那几个 batch，所以每个测点重放的就是它自己那张图，不存在 padding 到别的宽度。
每步的代价取 `execute_model` **排空后**主机时间的中位数（109 个测点的 p10–p90 带宽
中位数 0.6%，九成在 1.7% 以内，所以下表里 1% 以内的差读作持平）：`execute_model`
交回的是异步输出，不排空量到的是 launch 而不是 step——不排空
时 batch 1 报 0.7 ms/step，而 16 GiB 权重在 B200 上读一遍都不止这个数。引擎循环另有
一笔不随 split 数变的开销（调度、输出处理、detokenize），短 prompt 下 batch 1 约
0.8 ms/step、batch 32 约 1.7 ms/step，是加在下表之上的常数项。脚本是
`tests/kernel_profile/sweep_split_served.py`，注入方式是在建引擎之前包住
`nvfp4_vllm.impl.fp4_decode`——测量代码，不是生产改动。

**注入的 split 数确实是跑的那个**，四条独立证据：

- capture 期进 split 路径的次数正好是「32 层 × 捕获尺寸数」，且 `num_splits`
  只见到注入值；1 路那条臂是 0 次 split、128 次单块。
- split kernel 的编译缓存键带 `num_splits`。1 路那条臂**从头到尾没编译过 split
  kernel**，多 split 那几条臂反过来没编译过单块 kernel。
- 每个纯 decode step 的 `CUDAGraph.replay` 次数与 step 数相等，所以跑的是捕获下来
  的那张图。
- CUPTI 看重放本身：同样 800 次「层 × step」的 decode 调用，1 路臂只有一个 kernel、
  63.5 ms；4 路臂是 split 版 decode kernel 22.2 ms + 800 次 combine 2.4 ms +
  1600 次 `FillFunctor`（FP32 partial 与 −inf LSE 各一次）2.3 ms。折合每层
  79.4 µs 对 33.6 µs，乘 32 层是 1.47 ms/step，与 step 级实测的 1.46 ms 差 1%。

**曲线是自洽的，解释变量是 CTA 数对 SM 数。** 单块路径每个 (row, KV head) 一个
CTA，`heads_q/heads_kv` 个 query head 打包进同一个 128 行 tile，所以一批 decode 占
`rows × heads_kv` 个 CTA。148 个 SM 除以 8 个 KV head 是 18.5 行：**行数低于它，机器
就没被填满，拆 K 拿到的是本来空转的 SM；行数到了它，拆 K 只剩 combine 与两次清零的
净开销。** 逐行核对：batch 1 是 8 个 CTA（5% 占用），拆 16 路正好填到 128 个；
batch 4 是 32 个，拆 4 路填到 128；batch 16 已经是 128 个，拆任何一路都只会亏。

序列长度不改变这条判据的方向，只决定它值多少钱：同一个 batch 1，序列从 2048 长到
16384，单块路径多花 2.0 ms/step（4,573 → 6,563），这 2.0 ms 就是拆 K 能动的全部预
算，占 step 的 30%；2048 上同一笔预算只有八分之一。预算小到一定程度，combine 与两次
清零那笔与长度无关的常数开销就开始吃掉收益，于是 2048 上的最优档位比 16384 低一档
（batch 1 是 8 而不是 16），batch 4 更是直接压回 1。

batch 24 是唯一的例外：192 个 CTA 是一个半波，第二波只填了 30%，拆 2 路把
「2 波整活」换成「3 波半活」，所以长上下文上 2 路反而最优。batch 32 的 256 个 CTA
是 1.73 波，同样的换算不成立，实测也确实是 1 路最优。

**结论一：`fp4_decode` 的默认值留 1。** 它是库的默认值，而正确的选择依赖调用方的
batch 与设备的 SM 数，两者库都不知道。§4.3 的改法（显式参数、启发式不上派发路径）
不变。

**结论二：vLLM 派发不能用一个常数，必须按捕获宽度分档。** 任何单一常数都会在半边
表上亏：4 路在 batch 32 / 16384 上 +7.7%、在 batch 32 / 2048 上 +18.4%；而 1 路在
batch 1 / 16384 上 +41%。一次 rollout 会在这些宽度之间跳，所以「按 batch 取最好的那
一个常数」这个选项不存在。

**结论三：分档规则只能读捕获时主机已知的东西，而 `rows` 正好够。** 规则是
「取最大的 2 的幂 `s`，使 `rows × heads_kv × s ≤ SM 数`」：

| 捕获宽度 | 1 | 2 | 4 | 8 | 16 | 24 | 32 |
|---|---|---|---|---|---|---|---|
| 规则给出 | 16 | 8 | 4 | 2 | 1 | 1 | 1 |
| 16384 实测最优 | 16 | 8 | 4 | 2 | 1 | 2 | 1 |

七个宽度对上六个，差的那个是 batch 24，规则给 1 而最优是 2，长上下文上让出 6.8%。
不去修它是故意的：能吃下 batch 24 的那条修正在 2048 上要倒亏 4.5%，而真实长度在捕获
时不可知（§3.3 的页表冻结正是这件事），所以只有与长度无关的那条规则是安全的。

规则本身也回答了 §3.3 的顾虑：它一个字节都不读页表，只读 `rows`、`heads_kv` 和设备
的 SM 数。而 capture 是按宽度分别录的——录尺寸 N 那一遍，Python 就是拿着 `rows = N`
跑的——所以**「按 rows 选」自动等于「按捕获宽度选」**，不需要在捕获时另做一套决定。

**规则实测过，不是推演。** 把注入换成这条规则再跑一遍全表：

prompt 256：两页的序列被拆 16 路，+3.5%。这是规则看不见长度的代价。平衡点落在 256
与 2048 之间，没有再细分；2048 上已经是持平偏赚，而 RL rollout 的序列只会更长。

三项必须一起接受的代价，都实测过：

- **每个档位多编一个 CuTeDSL kernel。** 捕获尺寸 `{1,4,16,32}` 下规则给出
  `{16,4,1,1}`，即三个 kernel（split@16、split@4、单块）。启动 41.9 s → 45.7 s。
- **capture 期编译次数仍是 0。** §5.1 点名这是最可能第一次就炸的地方，而 vLLM 在
  捕获每个尺寸之前先 warmup 同一个尺寸，warmup 就把那个宽度要的 kernel 编好了。
- **split 路径每层每步多三个 kernel**（combine 加两次清零，见上面的 CUPTI 计数）。
  这笔开销是常数，收益随序列长度涨，所以短序列上它是净亏。

**落点。** 与 `decode_page_columns` 完全平行：`NVFP4MetadataBuilder.build` 每步算一
次，作为一个主机 int 放进 `NVFP4Metadata`，`NVFP4Impl._decode` 把它传给
`fp4_decode` 的 `num_splits`。SM 数在 builder 构造时问一次并存下来，不要放在每层都
走一遍的路径上（§4.3 顺手消掉的正是这个每步 36 次的主机调用）。规则的输入是
`decode_prefix_rows`，不是 `num_reqs`：混合步里只有 decode 前缀进这个 kernel，而混合
步在图外裸跑，同一条规则对它也是对的。

这项改动不在本任务的六处之内，需要另立一轮，验收里要包含：`tests/e2e` 在 graph
开/关下各一遍，以及 `tests/kernel` 对 split 路径既有覆盖不变。本轮只测量，没有改动
生产代码。
