# NVFP4 Bookkeeping Overhead：Tag-first 精简方案

## 1. 结论

当前 unified-v2 的主要问题不是缺少 dtype tag，而是 **tagged `page_table` 与
`PreGroupedViews` 同时保存了相同 page state**：

```text
tagged page_table
    + fp4_subpages / fp4_count
    + bf16_block_ids / bf16_count
```

这套重复索引引入了 gather、count 算术、DtoH/HtoD、scalar `.item()` 和双写。
最终方案应当是：

> **tagged `page_table` 成为唯一 GPU page index；每 step 用一个 tag-aware
> metadata kernel 生成 compact attention metadata；验证完成后删除
> `PreGroupedViews` 的 runtime reads、writes 和对象本身。**

因此，旧文档中的以下局部优化不再作为最终方案保留：

- 缓存或复用 `fp4_count/bf16_count`；
- 再增加一份 CPU count mirror；
- 只把四次 `PreGroupedViews.index_select` 合成一次；
- 在旧 promotion 流程上单独增加 count-based early-out；
- 为旧 DtoH staging 单独优化 layout、但继续每 step 读回相同 page state。

这些方法可以短期降低局部成本，但会固化重复索引。

Dtype tag 也不是万能的。它不能直接删除：

- prefill `torch.cat(...).contiguous()` 的 K/V payload copy；
- promotion 对 BF16 K/V page 的 materialization；
- mixed-varlen 自身的 qlens/block-table metadata；
- 必要的 page-state transition。

这些项目分别需要 indirect qpack、scheduler metadata 直传或 GPU-resident control
plane。

本文只分析 Self-CUDA。各 family 的毫秒数不能直接相加作为 wall-time 收益。

## 3. Tag-first 的状态合同

### 3.1 Tagged entry

定义位置：

- `src/kernel_sm100/page_attn/nvfp4_paged_kv/page_table.py:25-53`
- `src/kernel_sm100/page_attn/nvfp4_paged_kv/page_pool.py:28-38`

```text
int32 entry

bits 31..28 : dtype tag
bits 27..0  : locator

FP4     = 0
BF16    = 1
FP16    = 2
INVALID = 15
```

当前 vLLM integrated path 的实际 payload 合同应统一为：

```text
FP4 payload  = NVFP4 pool subpage id
BF16 payload = vLLM physical block id
FP16 payload = reserved / unsupported in v1
```

当前 `pregrouped_views.py:105-110` 的 slow oracle 仍保留旧假设：

```python
bf16_block_id = sp_id // 4
```

它与 hot path 直接写 vLLM block id 的行为不一致。tag 成为 source of truth
之前必须修正该分叉，并让 reserved tags 3–14 fail closed。

### 3.2 两种合法状态

Active decode attention 前：

```text
ATTENTION_READY

[FP4 full page] ... [FP4 full page] [一个 BF16 active tail]
```

BF16 tail 可以包含 1–128 tokens。即使 sequence length 正好是 128 的倍数，
当前 attention 仍应使用 128-token BF16 tail：

```python
n_fp4 = (seqused - 1) // 128
residual = ((seqused - 1) % 128) + 1
bf16_page = n_fp4
```

Promotion commit 后、尚未 roll 新 page 的短暂状态：

```text
QUIESCENT_COMMITTED

[FP4 full page] ... [FP4 full page]
```

正常 decode attention 不应在该状态运行。若未来允许 FP4-only attention，
kernel 必须显式支持 `has_bf16=0`。

### 3.3 不能使用 block-0 sentinel

当前 paged residual path 中：

```text
bf16_block_ids = 0
seqused_residual = 1
```

并不是“无 residual”。它仍会读取真实 block 0 的 token 0，并参与 softmax。

所以 FP4-only row 必须：

- 显式传递 `has_bf16=0`；
- 完全跳过 residual softmax；或把整块 residual logits mask 为 `-inf`；
- normal path 与 split-K kernel 1 使用相同语义。

### 3.4 Chunked prefill 是前置 correctness 问题

当前 prefill 对每个 query chunk 独立计算：

```python
n_full = chunk_len // 128
n_tail = chunk_len % 128
```

并按 `ceil(chunk_len / 128)` 推进 logical offset。它没有把后续 chunk 合并到
已有 partial tail。

因此 `64+64`、`100+100`、`127+2` 等多 execution prefill 可能破坏
“FP4 prefix + 一个 BF16 tail”。

删除 counts 前必须二选一：

1. scheduler 保证所有非最终 prefill chunks page-aligned；或
2. 实现 merge-aware prefill，先补满已有 BF16 tail，再 promotion 并创建新
   tail。

### 3.5 CPU ownership ledger 不等于第二份 GPU index

CPU allocator 仍需要知道：

- pending FP4 allocation；
- 当前 BF16 tail 的 vLLM block id；
- tag 已 commit、但 release 尚未完成的旧 block。

允许保留：

```text
tail_owner_by_slot
pending_transaction_ledger
release_pending_ledger
```

它们只管理 ownership/lifecycle，不保存 FP4 page list 或 page counts，不能被
attention dispatch 使用。

`tail_owner_by_slot` 必须：

- prefill 创建 partial tail 时初始化；
- roll 时更新；
- promotion 时提供 previous `old_block_id`；
- request finish、GC 和 slot reuse 时清除。

## 4. 目标实现

### 4.1 Once-per-step tagged metadata kernel

新增：

```text
prepare_tagged_decode_metadata_kernel
```

输入：

```text
tagged_page_table   int32 [max_slots, max_pages]
active_slots        int32 [M]
seqused_k_total     int32 [M]
```

输出到 persistent scratch：

```text
fp4_page_table      int32 [M, max_pages]
bf16_block_ids      int32 [M]
has_bf16            bool/int32 [M]
seqused_fp4         int32 [M]
seqused_residual    int32 [M]
optional debug_error int32 [1]
```

核心逻辑：

```python
slot = active_slots[row]
total = seqused_k_total[row]
assert total > 0

active_page = (total - 1) // 128
active_entry = page_table[slot, active_page]

if tag(active_entry) == BF16:
    n_fp4 = active_page
    residual = ((total - 1) % 128) + 1
    bf16_block_ids[row] = payload(active_entry)
    has_bf16[row] = 1
elif tag(active_entry) == FP4 and total % 128 == 0:
    # QUIESCENT_COMMITTED / explicit FP4-only path
    n_fp4 = total // 128
    residual = 0
    has_bf16[row] = 0
else:
    fail_closed()

for p in range(n_fp4):
    entry = page_table[slot, p]
    assert tag(entry) == FP4
    fp4_page_table[row, p] = payload(entry)

seqused_fp4[row] = n_fp4 * 128
seqused_residual[row] = residual
```

它替换：

```text
views.fp4_subpages.index_select
views.fp4_count.index_select
views.bf16_count.index_select
views.bf16_block_ids.index_select
seqused_fp4 multiply
seqused_bf16 subtract
seqused_residual clamp
safe-id / where kernels
```

Metadata 每 step 构建一次并跨 `L=32` layers 复用，不能把 tag decode 下沉到
每层 attention mainloop。

Production 的 `fail_closed()` 必须是 device assert/trap，或一个在 attention
读取 scratch 前生效的 on-device gate；不能只写一个无人同步检查的
`tag_error`。Debug/test 可额外输出 error word 帮助定位。

#### Target `decode_unified_v2` interface

Tag-aware metadata preparation 完成后，per-layer decode 的逻辑输入应当是：

```python
def decode_unified_v2(
    *,
    query,                   # [N, H_q, D] BF16
    query_row_indices,       # [M] int32

    fp4_k_pool,
    fp4_v_pool,
    fp4_k_scales,
    fp4_v_scales,
    fp4_page_ids,            # [M, P_max] int32
    seqused_fp4,             # [M] int32

    bf16_k_cache,            # [num_blocks, 128, H_kv, D] BF16
    bf16_v_cache,
    bf16_block_ids,          # [M] int32
    seqused_residual,        # [M] int32
    has_bf16,                # [M] bool

    softmax_scale,
    out,                     # [N, H_q, D]
    out_indices,             # [M] int32
):
    ...
```

这里：

- `fp4_page_ids`、`seqused_fp4`、`bf16_block_ids`、
  `seqused_residual` 和 `has_bf16` 都由 once-per-step tag-aware metadata
  kernel 生成；
- `query_row_indices` 让 Q-quant kernel 从 full query 的 `N` 行中读取 `M`
  个 decode rows；
- `out_indices` 让 attention epilogue 把 `M` 个结果直接 scatter 回 full
  output；
- `fp4_page_ids` 已经去掉 dtype tag，只包含 FP4 subpage payload，因此
  per-layer attention mainloop 不需要解析 tag；
- `bf16_block_ids` 只定位每行最多一个 BF16 residual block；
- `has_bf16=0` 必须触发真正的 residual skip，不能使用 block-0 sentinel。

实现上仍可把 FP4 pools/scales 封装在 `cache` 对象中，也可把上述 row-space
metadata 封装成 `TaggedDecodeMetadata`。关键合同是 decode 不再接收
`PreGroupedViews`、`fp4_count` 或 `bf16_count`。

Split-K partitions、persistent Q/O scratch 和 fused Q-quant flags 属于执行优化
参数，可以作为附加参数保留；它们不改变上面的 tag-derived 数据依赖。

### 4.2 Persistent scratch

只写 `[0, n_fp4)` 时，scratch 后部可能残留前一个 request 的 page ids。
可以选择两种合同：

1. **推荐：不清理 unused tail。**
   - attention/split-K 由 `seqused_fp4` 保证不读取 unused columns；
   - dual-read 只比较 consumed ranges；
   - poisoned-tail test 证明 stale ids 不可观察。
2. **只有存在会读取 unused ids 的 consumer 时才清理。**
   - 维护 `prev_n_fp4[row]`；
   - 只清除 shrinking range `[n_fp4, prev_n_fp4)`。

Hot kernel 只检查 consumed prefix 和 active entry。“后续 entries 全 INVALID”
由 debug/GC oracle 检查，不能为了该 assertion 每 step 扫描 `max_pages`。

### 4.3 Split-K

第一版保留现有 split-K resolution/partition。

原因：

- `num_splits_fp4` 是 host integer；
- auto mode 使用 `seqused_fp4.max().item()` 和 heuristic；
- partition width 依赖最终 split count。

后续若融合 partition，必须显式传入已解析的 `num_splits_fp4`，并保持：

- full-width column partition；
- contiguous `page_table_k1/k2`；
- forced `K=3/4/8`；
- auto threshold；
- unsupported `K=2` fallback；
- split/non-split parity。

### 4.4 Prefill transaction

当前 layer-0 可能在所有 layers qpack 完成前 stamp FP4 tag。tag 成为唯一
source of truth 后必须改为：

```text
entry 保持 INVALID
→ pending ledger 保存 new FP4 subpage id
→ 所有 L layers qpack data + scales
→ commit FP4 tag
→ release source ownership
```

任何 attention 可见的 FP4 tag 都必须表示所有 layers 已完整写入。

### 4.5 Delayed promotion 与 roll

不能在 layer 0 的 `seqused % 128 == 0` 时 qpack 所有 layer caches。此时后续
transformer layers 尚未写入 boundary token，会量化 stale K/V。

推荐 next-step delayed promotion：

```python
if seqused % 128 == 1:
    new_page_idx = (seqused - 1) // 128

    if new_page_idx > 0:  # seqused > 128
        old_page_idx = new_page_idx - 1
        old_entry = page_table[slot, old_page_idx]
        if tag(old_entry) == BF16:
            promote(old_page_idx)
        elif tag(old_entry) != FP4:
            fail_closed()

    page_table[slot, new_page_idx] = pack(BF16, new_block_id)
```

顺序：

```text
上一 page 的所有 layers 已完成
→ allocate FP4 subpage
→ qpack all layers
→ FP4 data/scales happens-before tag flip
→ BF16 tag 改为 FP4 tag
→ old BF16 block 进入 release/retry protocol
→ 新 page 写 BF16 tag
→ 构建本 step metadata
```

`seqused=1` 也满足 `%128==1`，但没有 previous page；必须避免
`old_page_idx=-1`。

Exact-boundary prefill 可能已经把 old page eager-qpack 为 FP4。此时 token
129/257 只需验证 old tag 为 FP4 并跳过 promotion，再 roll 新 BF16 tail；不能
把所有 previous full pages 都假设为 BF16。

CPU allocator 版本通过 `tail_owner_by_slot` 获取 old block id，只上传
boundary-only compact worklist。GPU 必须验证 worklist old id 与 tagged payload
一致。

若不维护 ownership ledger，就必须做 boundary-only compact DtoH；该 event
必须计入最终 profile。

### 4.6 GC 与失败语义

GC 顺序：

```text
stop future access
→ wait/event after last GPU use
→ snapshot committed tags + pending ownership
→ invalidate page-table row
→ establish invalidation visibility
→ return custom-owned FP4/pending allocations
→ clear ownership ledgers
→ slot reuse
```

仍由 vLLM 拥有的 BF16 blocks 由正常 request teardown 释放。Custom GC 不能仅
因 entry 带 BF16 tag 就再次 free，否则可能 double-free。

Pending transaction 至少包含：

```text
(slot, logical_page)
old_bf16_block
new_fp4_subpage
layers_completed
state = ALLOCATED / QPACKED / TAG_COMMITTED / RELEASE_PENDING
```

规则：

- qpack 完成前不能 flip tag；
- host-side allocation/launch 前失败可回收 pending FP4 subpage；
- tag commit 后旧 BF16 block 只 release 一次；
- release 失败需要幂等重试；
- reserved/illegal tags 必须 fail closed；
- 历史 BF16 blocks 已释放后不能静默 fallback 到 BF16；
- asynchronous CUDA device fault 采用 fail-stop，不承诺进程内回滚继续服务。

## 5. Overhead 如何归并

### 5.1 由 tag-first 直接删除或融合

#### A. INT metadata index-select 与 sequence arithmetic

测量：

```text
INT index-select: 2.151698 ms / 512 events
integer add/sub:  0.296326 ms / 158 events
```

来源：

- `decode_unified_v2.py:99-137`
  - 四次 `PreGroupedViews.index_select`
  - FP4/residual sequence-length 算术
- `vllm_hook.py:1927-1945`
  - layer-0 `bf16_count` gather
- `vllm_hook.py:1684-1729`
  - promotion count/page-table gathers

512 次 INT index-select：

```text
4T decode metadata
+ T layer-0 bf16_count
+ 2T promotion counts
+ T promotion page-table rows
= 8T = 512
```

Tag-first 后：

- 四次 decode gather 由每 step 一个 metadata kernel 替代；
- promotion 直接定位 old logical tail；
- 不再读取 `fp4_count/bf16_count`；
- FP4/residual 算术融入 metadata kernel。

Phase 1 理论变化：

```text
256 decode gathers → 64 metadata launches
maximum net reduction = 192 launches
```

完整 tag migration 的理论上界：

```text
512 old INT gathers → 64 metadata launches
maximum net reduction = 448 launches
```

这是上界。fail-closed、split resolution、worklist 和 GC 可能新增 event。

#### B. 重复状态引起的 DtoH/HtoD/DtoD/scalar sync

Tag 直接删除的部分：

- `vllm_hook.py:1700-1729`
  - promotion counts 与整行 page-table DtoH
- `vllm_hook.py:1927-1955`
  - `bf16_count` roll staging
- `pregrouped_views.py:45-83`
  - count/page-id scalar writes 与 `.item()` assertions
- `vllm_hook.py:734-767`、`1918-1937`
  - 仅为上述 host read 服务的部分 staging DtoD

删除 `PreGroupedViews` 后不再执行：

```text
fp4_count[slot] = ...
bf16_count[slot] = ...
fp4_subpages[slot, page] = ...
bf16_block_ids[slot, 0] = ...
```

仍然保留的 transfer 不能归功于 tag：

- mixed-varlen overlay 的 qlens/qsl/seq-len metadata；
- prefill hook 的 `.cpu().tolist()`；
- prefill `slot_mapping[...].item()` 取得 BF16 tail/source block id；
- CPU allocator 的 boundary-only FP4 ids/worklist；
- qpack subpage-id fallback；
- 必要的 tagged-entry update。

所以 `494 DtoH`、`363 HtoD`、`+380 DtoD` 和 `+180 Pinned DtoH` 都只能
部分下降，不能提前承诺全部归零。

#### C. Tagged `index_put` 不应单独消除

测量：

```text
0.040257 ms / 11 events
= 2 prefill stamps + 5 promotion updates + 4 roll-only updates
```

来源：

- prefill stamp：`vllm_hook.py:1502-1509,1613-1623`
- promotion flip：`vllm_hook.py:1805-1822`
- roll append：`vllm_hook.py:1957-1987`

Tag-first 后这些 writes 是唯一 page-state transition，不再是重复写。

可以把它们融合进 prefill/promotion/roll transaction，但不应为了让 symbol
消失而跳过状态更新。该项只有 11 events / 0.040 ms，优先级最低。

### 5.2 Tag 无法删除：K/V payload materialization

#### A. Prefill CatArray + BF16 direct-copy

测量：

```text
CatArray:        1.426139 ms / 64 events
BF16 direct-copy 0.214558 ms / 64 events
```

来源：

- `vllm_hook.py:1497-1572`
- `vllm_hook.py:1625-1632`

```python
pages_k_bf16 = torch.cat(k_page_batches, dim=0).contiguous()
pages_v_bf16 = torch.cat(v_page_batches, dim=0).contiguous()
```

两种 symbol 是同一类业务步骤的不同 dispatch：把 chunked/strided K/V
materialize 成 qpack 接受的 contiguous page batch。

最终方案是让 prefill qpack 接受 chunk descriptors：

```text
source K/V base pointers
chunk starts / lengths
full-page mapping
destination FP4 subpage ids
```

qpack 直接读取原始 K/V 并写 FP4 pool，从而同时删除：

- 64 CatArray；
- 64 BF16 direct-copy；
- 中间 contiguous BF16 page tensor。

预分配 workspace 只能删除 allocation/CatArray，不能删除 payload copy，不是
最终方案。

#### B. Promotion BF16 KV-page index-select

测量：

```text
0.859586 ms / 320 events
320 = K/V × L × N_prom
```

来源：

- candidate ids：`vllm_hook.py:1731-1768`
- per-layer gathers：`vllm_hook.py:1769-1803`

```python
pages_k = vllm_k_caches[layer_idx].index_select(0, block_ids)
pages_v = vllm_v_caches[layer_idx].index_select(0, block_ids)
```

Tag 只提供 BF16 block id，不能消除 payload gather。最终需要 indirect promotion
qpack：

```text
source_cache[num_blocks, 128, H, D]
block_ids[N_pages]
destination_subpage_ids[N_pages]
```

qpack kernel 内按 block id 计算源地址，删除 320 次 index-select 和中间 page
tensor。qpack 与 block release 必须按第 4.5/4.6 节排序。

### 5.3 与 tag 正交的 control-plane overhead

#### A. Prefill/overlay DtoH 与 qlens 算术

来源：

- overlay：`vllm_hook.py:734-800`
- prefill：
  `_local/nvfp4_repro/vllm/vllm/v1/attention/backends/flash_attn.py:1145-1183`

主要包括：

```text
block_table[:, 0].cpu().tolist()
qlens.cpu().tolist()
qsl.cpu().tolist()
(_qlens > 1).any().item()
qsl[1:] - qsl[:-1]
slot_mapping[...].item()
```

三处 bare `.cpu().tolist()` 每 layer、每 prefill execution：

```text
3 × L × P = 192 events
```

它们不是 `PreGroupedViews` 产生的。最终方案：

- scheduler/model runner 直接传递同 step 的 CPU qlens/qsl/chunk metadata；
- scheduler 直接提供 prefill tail/source physical block ids，或在 GPU 上批量
  生成 ownership worklist，删除 `vllm_hook.py:1580,1609` 的逐 scalar
  `slot_mapping[...].item()`；
- 或在 GPU 上生成最终 compact metadata，不回 Python；
- step/generation identity 必须防止 stale CPU shadow。

把 non-contiguous pinned slice 改成 compact pinned destination 只能降低 copy
成本，不能删除同步，因此只作为临时诊断优化。

#### B. `index_kernel_impl<OpaqueType<4>>`

测量：

```text
delta = +0.176667 ms / +70 events
70 = 64 sequence-length gathers + 6 block-table cache misses
```

来源：

- block ids：`vllm_hook.py:860-884`
- sequence lengths：`vllm_hook.py:885-887`

```python
new_token_block_ids = block_table[_bt_rows, _bt_cols]
seqused_k_total = seq_lens.to(torch.int32)[_bt_rows]
```

Tag 不包含当前 vLLM query-row mapping，因此无法直接删除它们。

建议：

- 让 scheduler 提供同 step compact device metadata；
- 或把 row selection 融入 tag-aware metadata preparation；
- block-id cache key 必须包含 request/generation identity；
- request membership、finish、GC、slot reuse 和 page roll 时 invalidate。

不建议依赖“先 DtoH、再 packed HtoD”来删除该 kernel，因为最终方向本身要删除
这次 round trip。

#### C. Qpack id scratch 与 overlay upload

来源：

- qpack fallback：`vllm_hook.py:1355-1365`
- overlay Python tensor upload：`vllm_hook.py:825-858`

最终应：

- 复用已有 device indices；
- 对 CPU allocator 只上传新分配的 compact FP4 ids；
- 使用 persistent pinned upload buffer 仅作为过渡；
- 避免 `.tolist() → torch.tensor(device=cuda)` 往返。

## 6. 实施顺序

### Phase 0：先修 correctness contract

1. 统一 FP4/BF16 payload 语义；
2. 修复旧 `sp_id // 4` oracle；
3. FP16/reserved tags 明确 unsupported/fail closed；
4. 修复或约束 unaligned chunked prefill；
5. 增加真正的 `has_bf16=0` residual skip；
6. 禁止 layer-0 exact-boundary promotion；
7. 建立 pending/release ownership ledger。

此阶段不宣称性能收益。

### Phase 1：实现 tag-aware metadata kernel

1. 预分配 output scratch；
2. 生成 FP4 compact table、BF16 block id、has_bf16 和 sequence splits；
3. 旧 views 与新 tag path 同时运行，仅在测试中比较；
4. consumed ranges、BF16 id、lengths 必须一致；
5. unused scratch 使用 poison test；
6. 第一版保留当前 split-K partition。

### Phase 2：production 改读 tag

1. `decode_unified_v2` 使用 tag-derived metadata；
2. 四类 decode `views.*.index_select` 变成 0；
3. metadata kernel 每 step 一次并跨 layers 复用；
4. `PreGroupedViews` 暂时仅 shadow-write，便于 oracle/回滚。

理论上：

```text
256 decode gathers → 64 metadata launches
net reduction upper bound = 192
```

### Phase 3：迁移 state transitions 并删除 views

1. prefill 改为 all-layers qpack 后 commit tag；
2. new-page step 先 delayed promotion，再 roll 新 BF16 tail；
3. promotion 不再读取 counts 或整行 page table；
4. GC 使用 committed tags + pending ownership；
5. 验证完成后停止所有 views writes；
6. 删除 runtime `PreGroupedViews` object。

完成后，旧 512 INT gathers 相对一个 `T=64` metadata kernel 的理论净下降上界
为 448。必须把新增 fail-check/worklist/GC events 计入净值。

### Phase 4：删除 K/V materialization

1. promotion qpack 直接读取 vLLM paged K/V；
2. prefill qpack 直接读取 chunked/strided K/V；
3. 删除 320 BF16 gathers；
4. 删除 64 CatArray + 64 BF16 direct-copy；
5. 删除中间 BF16 page buffers。

### Phase 5：清理剩余 control plane

1. scheduler 直传 qlens/qsl/chunk metadata；
2. GPU 生成 compact row/block metadata；
3. allocator/worklist 逐步 GPU-resident；
4. 删除 steady-state `.cpu().tolist()` / `.item()`；
5. 最后评估是否值得融合 11 次 tagged-entry writes。

## 7. 验收

### 7.1 Correctness

必须覆盖：

- tag encode/decode、signed int32、INVALID/reserved tags；
- consumed tag metadata 与旧 views oracle 一致；
- scratch shrinking/poisoned tail；
- `<128`、128、129、255、256、257 tokens；
- exact boundary 保持 128-token BF16 tail；
- `seqused % 128 == 1` 时先 promote previous page，再 roll；
- cross-layer sentinel：所有 layers 写完 boundary token 才能 flip tag；
- FP4-only row 完全跳过 residual；
- unaligned prefill：`64+64`、`100+100`、`127+2`；
- mixed prefill/decode、pure decode、连续 promotion；
- request finish、GC、slot reuse；
- pending allocation rollback 与 release retry；
- forced split-K `3/4/8`、auto threshold、`K=2` fallback；
- `K=1`、`K=8`、`K>256`；
- full/non-contiguous Q/K/V；
- asynchronous device fault fail-stop。

### 7.2 Profile

```bash
PROFILE_ARTIFACTS_ROOT=_local/nvfp4_repro/profiles_bookkeeping_next \
CUDA_VISIBLE_DEVICES=0 \
bash scripts/run_nvfp4_profile_manual.sh profile nvfp4

PROFILE_ARTIFACTS_ROOT=_local/nvfp4_repro/profiles_bookkeeping_next \
CUDA_VISIBLE_DEVICES=0 \
bash scripts/run_nvfp4_profile_manual.sh reduce nvfp4
```

Phase gates：

- Phase 2：
  - 四类 decode views index-select 为 0；
  - tagged metadata kernel 为 once-per-step，不是 per-layer；
  - 256 gathers → 64 metadata launches，理论净下降 192；
- Phase 3：
  - promotion count/page-row DtoH 为 0；
  - production 不再出现 views scalar writes/readbacks；
  - runtime 不再分配 `PreGroupedViews`；
- Phase 4：
  - 320 BF16 KV index-select 为 0；
  - CatArray 与 BF16 direct-copy 都为 0；
  - 不允许只是换成另一类 payload-copy symbol。

所有阶段都检查：

- total `B_bookkeeping` events 与 Self-CUDA；
- raw kernel family；
- DtoH/HtoD payload；
- total CUDA 与 wall latency；
- FP4 attention/Q-quant launch count不得下降；
- fallback warning 为 0。

以下不算优化完成：

- 只修改 classifier；
- 四次 views gather 合成一次、但继续维护 views；
- Pageable 变 Pinned、但同步仍存在；
- CatArray 变成多个 DtoD/direct-copy；
- tag decode 变成 `O(L·T)` per-layer work；
- qpack 完成前 flip tag；
- 跳过 promotion/release/page-table update；
- bucket 下降但 total/wall 没改善。

## 8. 最终优先级

1. **统一 tag payload 与 state-machine correctness。**
2. **实现 once-per-step tagged metadata kernel。**
3. **Production 改读 tag，删除 `PreGroupedViews` reads。**
4. **迁移 prefill/promotion/roll/GC，再删除 views writes/object。**
5. **实现 indirect promotion qpack。**
6. **实现 chunk-descriptor prefill qpack。**
7. **最后清理 scheduler/allocator control-plane 往返。**

核心区别：

- dtype tag 负责 **删除重复索引**；
- tagged metadata kernel 负责 **一次构建、跨层复用**；
- indirect qpack 负责 **删除 K/V payload materialization**；
- GPU-resident control plane 负责 **删除剩余 DtoH/HtoD**。
