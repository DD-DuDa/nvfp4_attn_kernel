# 2. NVFP4 Decode Kernel：性能、架构与优化现状

本文是一份**状态文档**，回答四个问题：现在跑多快、代码长什么样、相对 BF16
FA4 做了哪些改动、下一步还能往哪走。历史过程见
`docs/tasks/2.fp4_decode_speedup.md`，单项实验见 `docs/reports/`。

测量日期 2026-08-04，代码状态 `6a77037`。

---

## 1. 结论

三句话：

1. **在 Llama-3.1-8B 这类 group 4 的配置上，我们与 trtllm-gen 打平**（80 个点的
   几何平均 1.01），大 batch 长上下文上领先（b16/s128k 为 0.85），实测 KV 带宽
   5.59 TB/s，是本机 FA4 BF16 实测上限 6.70 TB/s 的 83%。
2. **性能的解释变量是 GQA group size（每个 KV head 摊到几个 query head），不是
   batch，也不是 seqlen。** 相对 trtllm-gen：group 4 打平，group 8 慢 22%，
   group 16 慢 51%。trtllm-gen 自己在同样的变化下几乎不动。
3. 这部分差距不在访存也不在 Tensor Core：固定 `heads_kv` 只改 `heads_q`，DRAM
   流量和 MMA 指令数完全不变，而我们的延迟接近翻倍。多出来的时间全部落在「每多
   一行真实 query 就要多做一遍」的 softmax、P 量化和 epilogue 上。

对照组：

- **trtllm-gen**：同为 NVFP4 的直接竞品，是唯一同口径的对手。
- **FA4 BF16**：不是竞品，是这台机器在这种访存模式下的实测天花板。它每元素读

### 2.3 解释变量是 group size

前三行固定 `heads_kv = 8`，只改 `heads_q`。这意味着：

- KV cache 都是 **2.25 GiB**，DRAM 流量完全相同；
- query tile 无论如何都补齐到 128 行，**Tensor Core 指令条数也完全相同**。

在这两个都不变的前提下，我们从 432 µs 涨到 854 µs（+97%），而 trtllm-gen 是
507 → 484 → 527 µs（±5% 以内）。多出来的时间里没有多读一个字节，也没有多发一条
MMA，全部是**每多一行真实 query 就要多做一遍**的 softmax、P 量化和 epilogue。

把 kernel 的实际配置打出来（走真实编译路径读 `FP4DecodeKernel` 属性）：

| group | 活跃 query 行 | softmax 组数 | 每线程行数 | CTA 线程 | softmax 寄存器 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1（MHA 8:8） | 1 | 1 | 1 | 512 | 216 |
| 4（32:8） | 4 | 2 | 2 | 512 | 216 |
| 8（64:8） | 8 | 4 | 2 | 768 | 96 |
| 16（128:8、64:4） | 16 | 4 | 4 | 768 | 96 |
| 32（MQA 32:1） | 32 | 4 | 8 | 768 | 96 |

对照上面的延迟，退化分成**两段互不相同的台阶**：

- **group 4 → 8：+28%，每线程行数没变（都是 2）。** 变的是 CTA 从 512 线程展宽到
  768（多两个 softmax warpgroup），每线程寄存器从 216 掉到 96，同时 softmax 的
  *总*工作量翻倍（指数个数、写进 SMEM 的 P 字节、归约暂存的往返都 ×2）。这一段
  说明瓶颈不只是串行链长，还有 softmax 的总吞吐。
- **group 8 → 16：+54%，CTA 宽度没变。** 变的是每线程行数从 2 到 4。这一段是纯
  粹的串行链加长。

组数封顶在 `MAX_SOFTMAX_ROW_GROUPS = 4`，因为四个 softmax warpgroup 已经让 CTA
到 24 个 warp / 768 线程，launch 时每线程只剩 80 个寄存器（65536 / 768 向下取整
到 8 的倍数）；第五组会掉到 72，第八组直接越过 1024 线程的 CTA 上限。

### 2.4 转置不是问题所在

既然转置把并行度钉死在 128 个 KV 位置上，一个自然的怀疑是 group 16 上应该退回
未转置布局。实测否定了这个想法（`tests/kernel_profile/probe_transpose_crossover.py`，
同一份输入上交替强制两种布局，b16 / s131072）：

| 配置 | 转置 | 未转置 | 转置领先 |
| --- | ---: | ---: | ---: |
| 32:8（group 4） | 493.8 µs | 1901.7 µs | 3.85x |
| 64:8（group 8） | 637.7 µs | 1902.5 µs | 2.98x |
| 128:8（group 16） | 983.8 µs | 1901.6 µs | 1.93x |

未转置在三个配置上是**恒定的 1902 µs**，因为它不管有几行是活的，都对补齐后的
全部 128 行做 softmax。转置只碰活的行，所以即使在 group 16 上仍然快 1.93 倍。
（该表在锁频 1605 MHz 下测得，与 §2.2 不同口径，只用于同表内比较。）

原始数据 `docs/reports/data/transpose-crossover.json`。

### 2.5 一个硬约束：group 必须整除 128

PackGQA 要求 `m_block_size % qhead_per_kvhead == 0`，而 `m_block_size = 128`，
所以 group 只能取 128 的约数 `{1,2,4,8,16,32,64,128}`——**恰好就是 2 的幂**。
不满足的形状不是静默回落，而是直接抛错：

```text
gqa7_b1_s1024_hq28_hkv4   SKIPPED ValueError: 128 must be divisible by the
                          query-heads-per-KV-head ratio
```

因此 Qwen2.5-7B（28:4，group 7）当前**完全跑不了**。也因此
`fp4_decode_kernel.py` 里 `transpose_s` 判定中的 `qhead_per_kvhead` 是 2 的幂那
一项，在能构造出来的形状上恒为真，是冗余条件。这一点修正了
`docs/reports/3.original_vs_transpose.md` 结尾「24/8 = 3 的模型会悄悄走未转置
路径」的说法——它会报错，不会静默。

## 3. 代码架构

### 3.1 调用链

```text
fp4_decode (interface.py)
  └─ fp4_decode_impl (_kernel.py)
       ├─ [BF16 Q] quantize_query (_quantize.py)
       │            └─ quantize_decode_q_to_padded_fp4 (quantize_q_kernel.py)
       ├─ [可选] split_k_heuristic → decode_fp4_split → flash_attn_combine
       └─ decode_fp4 (_decode.py)
            ├─ 形状/dtype 校验
            ├─ _compile_decode → cute.compile(FP4DecodeKernel(...))
            └─ compiled(...) → FP4DecodeKernel.__call__ → .kernel(...).launch(...)
```

| 文件 | 职责 | 行数 |
| --- | --- | ---: |
| `interface.py` | 稳定公开 API，检查 K/V 参数齐备，惰性导入实现 | 134 |
| `_kernel.py` | 组合 Q 路径（BF16 量化 vs 预量化直通）、residual 补齐、split-K 分派 | 218 |
| `_quantize.py` | host 侧门面：分配 FP4 Q 与 E4M3 scale 布局，启动 Q 量化器 | — |
| `quantize_q_kernel.py` | CuTeDSL Q 量化 kernel | 505 |
| `quantize_kv_kernel.py` | CuTeDSL 页量化 kernel（供 serving 用，不在 decode 路径上） | 822 |
| `_decode.py` | 校验、布局适配（scale stride、page pitch）、编译缓存、启动 | 1173 |
| `fp4_decode_kernel.py` | SM100 主 kernel：warp 角色、SMEM/TMEM、TMA/MMA/softmax/correction/epilogue | 6224 |
| `split_k_combine.py` | split-K 的 LSE 加权归约 kernel | 768 |

**编译缓存**在 `_decode.py`，两份字典：

- 非 split：`(device.index, heads_q, heads_kv, has_residual, out_indices is not None)`
- split：`(device.index, heads_q, heads_kv, num_splits, has_residual)`

page stride 在编译期是动态的（`Int32(0)`），所以同一个二进制既能跑 dense page，
也能跑从更宽 cache page 里切出来的子区域。注意 **cache key 里不含
`transpose_s`**，做布局对照实验时必须同时关掉 CuTeDSL 的磁盘缓存。

### 3.2 `_fa4/` 私有包

18 个模块，decode 路径实际用到的：`blackwell_helpers`（tcgen05 PTX 发射）、
`block_scaled_layout`（SFA/SFB 布局）、`block_info`、`copy_utils`、`fast_math`、
`mask`、`mma_sm100_desc`、`pack_gqa`、`paged_kv`、`pipeline`、`seqlen_info`、
`softmax`、`tile_scheduler`、`utils`。

`block_sparsity` / `block_sparse_utils` 被 import 但 host 永远传
`blocksparse_tensors=None`，编译期即死代码；`combine_utils` 只服务
`split_k_combine.py`。

### 3.3 warp 专业化与寄存器预算

每个 softmax 组是连续 4 个 warp，起始于 128 线程边界——这正是
`thread_idx % 128` 能直接当作 KV 位置用的前提。N 个 softmax 组时：

| 角色 | warp id | 数量 |
| --- | --- | ---: |
| softmax 组 `0..N-1` | `0 .. 4N-1` | 4N |
| correction | `4N .. 4N+3` | 4 |
| MMA | `4N+4` | 1 |
| epilogue | `4N+5` | 1 |
| load | `4N+6` | 1 |
| empty | `4N+7` | 1 |

| softmax 组数 | warp | CTA 线程 | launch 每线程寄存器 | softmax 实得 |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 16 | 512 | 128 | 216 |
| 4 | 24 | 768 | 80 | 96 |

correction 48 / 其他 24 / empty 24。softmax 拿的是「CTA 寄存器池减去其他角色」
之后按组数均分的结果，所以展宽 CTA 是要付寄存器的。

### 3.4 主循环流水线

| 角色 | 工作 |
| --- | --- |
| load warp | TMA 搬 Q(+SFQ)，然后每块搬 K+SFK、V+SFV 进 staged SMEM |
| MMA warp | S2T 搬 scale 进 TMEM；tcgen05 QK MMA → S；tcgen05 PV MMA → O |
| softmax 组 | 等 S → 行最大值归约 → exp2 → 量化打包 P 进 SMEM → 通知 MMA |
| correction | 按 softmax 给的 max 增量重缩放 O，最后交给 epilogue |

KV 流水线是 `PipelineTmaUmma`，深度由 SMEM 预算推出后再封顶：非 split 最多 10
级、split-K 最多 8 级，断言 ≥ 2。Q 只有 1 级（decode 单 tile）。

一个 KV block 的稳态顺序（转置路径）：

1. **load**：TMA `K_i`+`SFK_i`，`V_i`+`SFV_i` 进环形缓冲。
2. **MMA**：等 K → S2T 搬 SFQ/SFK → **QK MMA** → `tcgen05.commit(mbar_S_full)`。
3. **softmax**：等 `mbar_S_full` → TMEM→寄存器读 S → 通知 `mbar_sfqk_load`（S 已
   抽干）→ 跨线程行最大值（具名 barrier）→ exp2 → 量化打包 P/SFP 写 SMEM →
   通知 `mbar_P_full_O_rescaled`。
4. **MMA**：**先发下一块的 QK**，再等 P → S2T 搬 SFP/SFV → **PV MMA** 累加进 O。
5. **correction**：读 `sScale` 重缩放 O；最后一块经 `mbar_corr_epi_*` 交给 epilogue。
6. **release**：MMA 释放用完的 K/V 级，load 得以续填。

第 4 步「先发 QK 再等 P」是转置带来的，未转置路径必须 PV 在前，因为那时 P 与 S
共用 TMEM 列（详见 §4.4）。

### 3.5 内存布局

tile 参数：`m_block_size = n_block_size = head_dim = head_dim_v = 128`，
`mma_tiler_qk = mma_tiler_pv = (128,128,128)`，`sf_vec_size = 16`，
`cluster_shape = (1,1)`，不用 2-CTA MMA。

SMEM（编译期打印的实测值，两个变体）：

| 字段 | 非 split（b16/b64） | split-K（b1/b4） |
| --- | ---: | ---: |
| 合计 | 154 KB | 159–160 KB |
| `sO` | 32 KB | 0 KB |
| `sQ` | 8 KB | 8 KB |
| `sK`（与 sV 别名，全部 stage） | 80 KB | 64 KB |
| `sSFK` / `sSFV` | 10 KB / 10 KB | 8 KB / 8 KB |
| `sSFQ` / `sSFP` | 1 KB / 1 KB | 1 KB / 1 KB |

每级 K 或 V 是 `128×128×0.5 = 8 KB`，SFK/SFV 各 `128×128/16 = 1 KB`，所以
`sK = 80 KB` 对应 10 级、64 KB 对应 8 级。预算上限 227 KB。

TMEM（共 512 列）：

| 区间 | 列 | 内容 |
| --- | --- | --- |
| S stage 0 | `[0,128)` | QK 累加器 |
| S stage 1 槽位 | `[128,256)` | `q_stage=1` 时闲置 |
| O | `[256,384)` | PV 累加器 |
| P（未转置） | 别名到 S + 64 | softmax 输出留在 TMEM |
| SFP/SFV（转置） | `384+` | 挪出 S 的别名区，见 §4.4 |

### 3.6 API 边界

| 张量 | 形状 | 说明 |

## 4. 相对 BF16 FA4 做了什么

这个 kernel 是从 FA4 BF16 移植过来的。以下是所有实质性改动。

### 4.1 block-scaled FP4 MMA

QK 与 PV 都走 `make_blockscaled_trivial_tiled_mma`，发射的指令是

```text
tcgen05.mma.cta_group::1.kind::mxf4nvf4.block_scale.scale_vec::4X
```

数据是 E2M1，每 16 个元素配一个 E4M3 scale（`sf_vec_size = 16`）。因为 FP4 是
半字节，每个 MMA 的 K 原子仍是 256 bit，于是 `mma_inst_tile_k = head_dim / 16`。

scale 有自己的一整套布局：`BlockScaledBasicChunk` 给出 K-major 原子
`((32,4),(16,4))`，SFA 按 `(M,K)` 铺、SFB 按 `(round_up(N,128),K)` 铺。TMA 把
SFK/SFV 搬进 SMEM，MMA warp 再用 `tcgen05.cp`（`Cp4x32x128bOp`）做 S2T 搬进
TMEM，然后才能喂给 MMA。BF16 路径这些全都不存在。

转置会把 QK 的两个操作数角色对调，所以 SFQ 用 SFB 布局、SFK 用 SFA 布局。

另一个 FP4 特有的约束：**V 必须是物理 K-major**（seqlen 连续），而 BF16 FA4 要的
是 MN-major。kernel 不做运行时转置，这个布局由 serving 侧的量化器负责产出。

### 4.2 转置 softmax

把 S 存成 `(kv 位置, query 行)` 而不是 `(query 行, kv 位置)`。线程 `tidx` 持有
kv 位置 `tidx`，只跑 `qhead_per_kvhead` 次 exp2，而不是一整行 key。

动机是 decode 的 tile 极度稀疏：`m_block_size = 128` 而活跃 query 行只有 group
个。未转置时 softmax 要对整块 128×128 做指数和量化，group 4 时 **32 倍的功白费**。

选中条件是 13 项合取（`fp4_decode_kernel.py:707`），关键几项：预量化 FP4 输入、
PackGQA、`seqlen_q_static_one`、非 causal/local、无 score mod、无 block sparsity、
group 整除 128。这里有个 DSL 的坑：这 13 项必须写成 `all([...])` 而不是 `and`
链——DSL 预处理会把每个短路算符改写成携带后续代码副本的嵌套条件，16 项 `and`
链让这个函数的 AST 从 1.4 万节点涨到 400 万以上，预处理从 0.01 秒变成十分钟。

转置还带来两个连锁改动：P 从 TMEM 挪到 SMEM（`OperandSource.SMEM`），以及
`softmax_row_groups` 把活跃行拆给多个 softmax warpgroup（见 §2.3 的表）。

代价是行最大值换了轴：转置后 S 的一行沿线程轴展开，行归约从线程内的局部操作变
成 5 步 warp 蝶形 + 四个 warp 经 SMEM 的交换 + 一次具名 barrier。这是今天最大的
单项开销，也是 §5 的头号目标。

### 4.3 P 的在寄存器量化：除以 6

exp2 之后 P 要就地量化成 E2M1 + E4M3 再写 SMEM 给 PV 用。关键技巧是
**scale 存的是 `max/6` 而不是 `max`**：E2M1 的最大有限值是 6，归一化到 `[0,6]`
能用满 8 个正数档位；如果归一化到 `[0,1]`，就只会用到 `{0, 0.5, 1.0}` 三档。

转置路径下这一步特别便宜，因为一个 scale 组的 16 个 kv 位置恰好是同一个 warp 的
16 个相邻 lane：组最大值可以直接从行最大值蝶形的前 4 步中间结果里取出（exp2 单
调，组内最大的指数就是最大分数的指数），不用第二次归约；归一化用
`rcp_approx` 近似倒数而不是精确除法——P 只有三位尾数，除数还是被除数取不到的上
界，精度绰绰有余；两个相邻 lane 的 E2M1 通过 `shuffle_sync_bfly` 打包进同一个
字节。

### 4.4 SFP/SFV 迁出 S 的 TMEM 列

未转置时 P 和它的 scale 复用 S 读出的那块 TMEM，于是**下一块的 QK 必须排在这一块
的 PV 之后**，而 PV 又要等 softmax，形成一条长依赖链。

decode 只有一个 Q tile，O 之上还有 128 列 TMEM 闲置。把 SFP/SFV 挪过去
（`tmem_sfpv_offset = tmem_total`）之后，下一块 QK 只需要等 softmax 把 S 抽干，
而这个信号在 softmax 读完 TMEM 时就发出（`mbar_sfqk_load`），不必等整步结束。
这一项当时把纯 FP4 四档从 0.464–0.479 推到 0.342–0.381（相对 FA4）。

### 4.5 分页 + TMA

page size 固定 128，与 `n_block_size` 相等，所以一块就是一页。`mPageTable[batch,
n_block]` 给出物理页号，TMA 直接按页号取（`tXgX[None, 0, page_idx]`），scale 用
同一个页号。page pitch 可以大于 dense 尺寸，这样一页可以是更宽 cache page 里的
子区域。

非 TMA 的 `cp.async` 回退路径（`PagedKVManager`）还在，但 host 永远走 TMA。

### 4.6 融合 BF16 residual

FP4 页是整页量化的，尾部不满一页的部分以 BF16 保留。这一块被融合进同一次 decode
launch：在 FP4 主循环之前先做一次 BF16 的 QK + softmax + PV，用独立的单级 SMEM
tile 和独立的 mbarrier，softmax 在线状态由它播种，后续 FP4 块以
`is_first=False` 并入。

约束：**融合 residual 时 `softmax_row_groups` 被强制为 1**（residual 会清一块所有
组都要写的 P tile，而每组的归约 barrier 无法给不同组的清零和写入定序），并且会
关掉 persistent scheduler。`seqused_residual = 0` 的行必须贡献恰好为零，这是
API 合同的一部分，`tests/kernel` 有专门用例。

### 4.7 split-K

host 侧 `split_k_heuristic` 按 makespan 比较 `{2,4,8,16,32}` 与不拆的代价，要求
每个 split 至少 2 页。拆开后各 split 写 FP32 部分结果 + LSE，再由独立的
`flash_attn_combine` 做 LSE 加权归约成 BF16；空 split 的 LSE 是 `-inf`，权重为
零。带 residual 时每个 split 都跑 residual 块，非归属者拿长度 0。

**现状是这条路径基本不赚钱**：实测 split-K 一致带来 13–23% 的开销，b1/b4 上试图
用它填占用率的尝试是负收益。它今天仍会在低 batch 被启发式选中，值得复查。

### 4.8 decode 专用的编译期裁剪

host 编译时固定：`is_causal=False`、`is_local=False`、`pack_gqa=True`、
`score_mod=None`、`is_varlen_q=False`、`seqlen_q_static_one=True`、
`blocksparse_tensors=None`。

`seqlen_q_static_one` 连带把 `q_stage` 钉成 1、关掉 TMA store O（改走 PackGQA 的
gmem 散写，从而支持 `out_indices` 散射）。causal/local 的掩码循环在未转置
`softmax_loop` 里还在，但对公开 decode 入口是编译期死代码。

### 4.9 correction / epilogue 上的零碎改动

- **`RESCALE_THRESHOLD = 8.0`**：在线 softmax 的 O 重缩放，如果这一步的
  `acc_scale` 与 1 的差距在 2⁻⁸ 以内就整段跳过。decode 的分数分布通常很快收敛，
  这个跳过命中率不低。
- **Kahan 补偿求和**：只在未转置的 residual 路径上开（`kahan=
  fused_residual_first_block`），因为 BF16 尾块与 FP4 块混合累加时误差更敏感。
- **LSE**：split-K 必须写（combine 要用），非 split 通常直接传 `mLSE=None` 省掉。
- **输出走 PackGQA 散写而非 TMA store**：`seqlen_q_static_one` 关掉了
  `use_tma_O`，改走 gmem 散写路径，代价是少了一次 TMA，好处是天然支持
  `out_indices` 散射。
- **IKET 埋点常驻树内**：`iket.range_push/pop` 密集包住 load / mma / softmax /
  correction / epilogue（`sm_exp`、`sm_pquant`、`mma_wait_p` 等），正常构建会被
  剥掉。这是 CLAUDE.md 里唯一允许常驻的诊断设施，必须有 `tests/kernel` 覆盖。

### 4.10 总览

| 方面 | 原版 BF16 FA4 | 本 kernel |
| --- | --- | --- |
| MMA | BF16 tcgen05 | `mxf4nvf4` + E4M3 块缩放，vec=16 |
| V 布局 | MN-major | K-major（由 serving 产出） |
| softmax 布局 | S 行主序，整块做功 | 转置成 (kv, query 行)，只碰活跃行 |
| softmax 并行 | 一组 | 按活跃行拆 1–4 组，各自具名 barrier |
| P 去向 | BF16 留在 TMEM | E2M1+E4M3 写 SMEM |
| P 量化 | 无 | 除以 6 + 近似倒数 + 蝶形中间级取组最大 |
| TMEM 别名 | P 别名 S | SFP/SFV 迁出，QK 可提前发射 |
| KV 来源 | 连续或分页 | 分页 + TMA，page = block = 128 |
| 尾部 | 无 | 融合 BF16 residual 块 |
| Q 长度 | 通用 | 静态为 1，PackGQA |

## 5. 未来的优化方向

按证据强度排序。

### 5.1 group ≥ 8 的 softmax 吞吐（最大的一项）

覆盖 70B/405B/235B 这一整类模型，是当前唯一让我们输给 trtllm-gen 超过 20% 的原
因。§2.3 已经把它拆成两段，两段的修法不同：

- **串行链（group 8 → 16 那 54%）**：让每线程少走几行。组数已经封顶在 4，再加要
  付寄存器和 CTA 上限，所以出路不在加组，而在把跨线程行最大值本身变便宜或变少：
  - **降低同步频率**：维持线程内 running max，每 N 块才做一次全局同步并 rescale。
    链长不变但 barrier 和 SMEM 往返降 N 倍。风险是 rescale 的数值行为要重新验证。
  - **更便宜的归约**：现在是 5 步蝶形 + 4 warp 过 SMEM。`redux.sync` 或 Blackwell
    的 DSMEM 也许能减少步数。
  - **挪出关键路径**：让第 i 块的归约与第 i+1 块的 QK 重叠。这条要先用 IKET 量清
    楚现在到底阻住了多少，否则可能只是把等待换个地方。
- **总吞吐（group 4 → 8 那 28%）**：这一段每线程工作量没变，怀疑是 768 线程下
  softmax 只剩 96 寄存器造成的溢出，以及多出来的 warp 争抢 SMEM 带宽。第一步应该
  是用 ncu 看 group 8 上有没有 local memory 流量——如果有，寄存器预算的分配方式
  （固定 216 vs 按组数均分）就值得重新设计。

### 5.2 低 batch

b1/b4 上四个配置全线落后 7–60%，与 group size 那条正交。已知的两个成因：

- **split-K 目前是亏的**（13–23% 开销），但启发式仍会在低 batch 选它。至少应该
  重新校准阈值，或者直接关掉再测一遍。
- **头部约 952 ns/CTA 的指针追逐**：`seqused_k` → 页表行 → 首个 K 的 TMA，三跳
  串行。前两跳可以与描述符预取重叠，第三跳是冷 DRAM 读。只对短序列和低 batch
  有意义。

已经排除的路：2 CTA/SM 占用率（split-K 填不动，反而更慢）、query 维窄化（padding
MMA 几乎免费，Tensor Core 有大量余量，收益极小）。

### 5.3 支持 group 不整除 128 的形状

Qwen2.5-7B（28:4）今天直接报错。要么让 PackGQA 支持非约数 group，要么至少提供一
条明确的回退路径，而不是让调用方在运行时撞 `ValueError`。这一项不是性能，是覆盖
面。

### 5.4 融合 residual 与 FP4-Q 的组合

`fused_residual_first_block` 会把 `softmax_row_groups` 强制为 1，也就是说带
residual 的形状拿不到 §2.3 里的任何行拆分收益。如果 serving 常态带 residual，这
条的实际权重会比现在看起来大。另外 FP4-Q + BF16 residual 的组合按设计文档是留到
性能达标之后才实现的，需要确认当前状态。

### 5.5 死代码清理

- `bf16_q_input` 分支：`_decode.py` 硬编码 `bf16_q_input=False`，kernel 内的
  BF16→FP4 量化是死代码。它在一次数值问题排查中造成过误诊，应当删掉。
- `q_replicate`：挂在 `_enable_q_replicate` 上，该属性在仓库里从未被设置，恒为 1。
- `transpose_s` 判定里的 2 的幂检查：给定 PackGQA 的整除断言，恒为真（§2.5）。
- `compute_sp1`：softmax 里另一条把 FP8 与 FP4 的 scale 融合起来算的路径，默认
  关闭，且与转置互斥，等于永远走不到。
- `q_replicate` 相关的 `_enable_q_replicate` 开关，以及未转置 `softmax_loop` 里
  的 causal/local 掩码分支——对公开 decode 入口都是编译期死代码。
