01结论

达到设计目标的 同样的显存预算下 FP4 cache 装 4,221,696 个 token，BF16 装 1,186,432，比值 3.5583，正好是页大小比 16/4.5 = 3.5556 该给的。 把这个比值花在 65,536 的上下文上，就是 61.3 条并发对 17.3 条：一批 32 路请求 在我们这里跑得满，在 BF16 上必须排队。
没有付出的代价 自定义路径在 steady-state 里 不多做一次 DtoH/HtoD（同 backend 下与 BF16 引擎逐次相等：23 步 48/52 对 48/52）。200 个请求连续跑完，同一批题 两遍逐 token 相同，slot 表的 sticky error_code 为 0。
付出的代价 准确率掉 3.0 个点（0.7400 vs 0.7700，N=200）——这是四个 bit 本身的代价，同一张表上 vLLM 自带的 nvfp4 掉 8.5 个点。tail buffer 按 32 slot 上限收 512 MiB，占 cache 的 0.34%。
真正的 blocker，且它不在 GPU 上 每步 decode 慢 9,447 µs。配对 profile 显示 GPU 侧只多做了 239 µs（4,522 vs 4,283），剩下 9,208 µs 是 host gap。同一份 trace 里 attention kernel 自己比 BF16 快 208 µs， 而 Python/CuTeDSL 前端把它赚回来的时间花掉了 30 倍。
必须一起读的第二个数 这 9,447 只是「四个 bit」那一笔。同一组测量里「不能用 CUDA graph」另收 9,888 µs/step。两笔几乎一样大，而后者与量化无关，做完 graph capture 就能拿回来。拿 NVFP4 eager 直接比 BF16+graph 是 6.1×，那个数会同时把两笔 算在四个 bit 头上。

03内存：同样的预算装得下多少

这是整个项目的目的。两个引擎拿到的 KV 预算相差 0.08%（144.83 对 144.94 GiB），所以比的是页大小，不是谁抢到更多显存。

臂页/层blockstokensKV 预算
BF16524,288 B9,2691,186,432144.83 GiB
NVFP4147,456 B32,9824,221,696144.94 GiB
比值3.55563.55833.55831.0008

3.5556 就是 16 / 4.5：一个 BF16 值 16 bit，一个 NVFP4 值 4 bit 外加每 16 个值共享一个 E4M3 scale，合 4.5 bit。实测的 token 容量比 3.5583 略高于它，差在两个 backend 别处预留量的零头上。

tail buffer：这套 layout 独有的租金

V 沿 token 轴整页打包，半页无法量化，所以每层每 slot 要在 cache 之外留一个 BF16 页。这块内存不在 vLLM 的 KV 记账里，报毛比值等于不报它。

毛（不计 tail）——3.5583
实测 8 slot128 MiB0.09%3.5525
32 slot 上限512 MiB0.34%3.5433
断言建在上限那一栏 每 slot 16.0 MiB，线性于 slot 数。测量时引擎只开了 8 slot，按实测报会 把成本少算四倍，所以门槛按 MAX_SUPPORTED_SLOTS = 32 的最坏情况 收。旧仓库正是在这里翻车过——FP4 池做成净增量，总量反而更大。

04并发：把比值花在长上下文上

3.5583 是关于 block 的数。在 65,536 的上下文上，它变成关于请求的数。

臂cache tokens65,536 下装几条batch 32 能不能跑满
BF161,136,51217.3不能，必须排队
NVFP44,018,17661.3能，32 条全部返回完整输出

写成容量而不是「实测抢占了几次」，是因为抢占是调度器的决定、它腾地方的办法 不止一种；cache 能装多少才是这个项目改变的性质。

顺带越过的一道坎 这一跑是这条路径第一次真的走到 block table 五百列宽、FP4 页偏移越过 231。那个 wrap 是 quantizer 寻址里的真 bug（175761c 修的），此前只有 kernel 测试用手搭的两 GiB 张量摸到过；这次是按用户会走的 路走到的。
为什么不是「相同显存下的最大上下文」 原本的验收口径是这个，但这台机器上 BF16 的 cache 已经装得下模型 rope 上限 （131,072）的 9 倍，两条臂都会停在架构上限而不是内存上限，测出来是同一个数。 换成固定长上下文比并发，才是这台机器上唯一能分出胜负的口径。

05准确率：四个 bit 该掉多少

同一批 GSM8K 题、5-shot、greedy、256 新 token。前两条臂算术完全相同， 用来证明测量本身没问题；后两条是这台机器上仅有的两个 4-bit KV cache。

臂KV cacheN=32N=200读法
FLASH_ATTNBF160.75000.7700基线
CUSTOMBF160.75000.7700与上一行 token 完全相同
CUSTOMNVFP4（本仓库）0.71880.7400−0.0300
FLASHINFERNVFP4（vLLM 自带）0.65620.6850−0.0850

第二条臂存在的唯一理由是证伪：它和第一条走完全相同的算术，如果 token 不是 逐个相同，那说明 backend 接线本身就改变了结果，后面两条臂的对比也就不成立。 实测 32/32 完全一致。

与另一个 4-bit cache 的对比 我们比 vLLM 自带的 nvfp4 高 5.5 个点（N=200 多答对 11 题）。 这条对比回答了 BF16 对比回答不了的问题：多少损失是四个 bit 本身的（两边都付）， 多少是布局的（只有一边付）。
这条对比不完全公平 FlashInfer 那条臂还把 Q 和输出一起 FP8 量化了，所以它的 8.5 个点里有一部分 不是 KV cache 的错。不能据此声称我们的 KV 布局强 5.5 个点。

06状态卫生：跨请求、跨步骤有没有漏东西

这套东西在请求之间不重置任何状态：tail slot 留着上一位租客的 token，slot 表留着它的 key 和时钟，回收的 block 留着前一个占用者的字节。这是故意的—— 急着回收正是丢 tail 的原因——但它意味着每个请求都跑在前面请求留下的状态上。

200 / 200 连续 200 个请求。同一批 100 题作为第 1–100 与第 101–200 个请求两次通过同一引擎，逐 token 完全相同。
error_code 0 slot 表的 sticky 错误字全程为 0。它是 sticky 的，所以结束时读一次覆盖全部 200 个请求。
每 slot 多次换手 在设备上用影子副本比对 key 变化来数，不读回主机，所以计数本身不扰动被计数的东西。
0 次同步 set_sync_debug_mode 只在本包代码在栈上时布防，23 个 decode step 一次没响。vLLM 自己在 sampler 里每步都同步，那不是我们的。

07速度账：三条臂，两笔账

一条被服务的 NVFP4 引擎每步比 BF16 慢，而这个差里折着两笔完全不同的成本。 NVFP4 路径拒绝 CUDA graph capture（promotion 在 capture 下未验证，护栏只收 CUDAGraphMode.NONE），而生产上的 BF16 部署是开 graph 的。

但两笔支出把它吃掉了 query 量化 201.5 µs 和 临时缓冲清零 196.2 µs，合计 397.7 µs，正好抹平 attention 省下的 208 还倒欠。第二笔是纯浪费：quantize_query 每次调用都 torch.zeros 出两个新张量，一层一次、一步 32 层，于是每步多出 128 次 fill launch——占了全部 165 次额外 launch 的四分之三。

全部 47 个配置———0.476 几何平均

FA4 那一列几乎是水平的，它把这台机器的 DRAM 天花板标在 6.33–6.61 TB/s， 与 head 配置无关。这给了一把绝对的尺子：NVFP4 每 token-head 搬 144 字节、 BF16 搬 512 字节，所以一个跑满带宽的 FP4 kernel 相对 FA4 的时间比应该是 0.281。

本文最值得记住的一处反差 隔离测：我们的 kernel 是 FA4 BF16 的 0.380 倍时间（快 2.6 倍）。
引擎内：同一个 kernel 是 BF16 attention 的 0.647 倍（快 1.5 倍）。
端到端：整步是 BF16 eager 的 1.69 倍（慢 69%）。
每往外走一层，优势就被上一层的开销吃掉一截，最后翻成劣势。慢从来不在 kernel 里。

隔离的 0.380 与引擎内的 0.647 之间的差距不是矛盾，是口径不同：引擎内这一栏 含 split-K combine（74.2 µs），而且这里的序列只有约 1,000–1,288 token，远短于 对拍网格的 4,096–65,536。序列越短，kernel 越是被 setup 而不是被带宽支配。

12边界与下一步

本报告确立了什么

  • 内存目标达成，且扣掉 tail buffer 之后仍然达成（3.5433 净，按 32 slot 上限）。
  • 把比值花在长上下文上是真的：65,536 下 61.3 条对 17.3 条，32 路全部返回。
  • 四个 bit 的准确率代价是 3.0 个点，比同机唯一的另一个 4-bit cache 好 5.5 个点。
  • 没有跨请求污染，没有自定义的 host 同步与拷贝增量。
  • 每步慢的 9,447 µs 里，GPU 只占 239 µs（2.5%），attention kernel 自身反而快 208 µs。
  • 按上一代审计的同一 workload 重采，GPU 侧相对 BF16 的开销从 +18.90% 降到 +3.79%，且 BF16 对照组两边只差 0.7%。

没解决的，按性价比排序

下一个受控实验 先做第 2 项，因为它便宜且可证伪：改成 persistent scratch 之后， 每步 launch 应当从 638 掉到约 510，GPU 从 4,522 掉到约 4,326， wall 应当掉多于 196 µs（因为还省了主机侧的分配）。如果 wall 不动， 说明 host gap 不是按 launch 数线性的，第 1 项的归因就要重做。

这份报告不能说明什么

  • 只测了一个模型（Llama-3.1-8B，GQA 32:8）。group size 变了 kernel 那一侧的结论就会变。
  • 延迟只在 batch 8 / prompt 1,000 上测过。host gap 按步长固定，batch 越大它被摊得越薄，所以大 batch 下劣势应当收窄——没有测。
  • 准确率 N=200 的差分标准差约 0.03，所以 3.0 个点这个数本身就在一倍标准差上，只能说「小」，不能说「精确等于 3.0」。
  • CPU 归因那张表是在 profiler 下采的，只当排序读。
