# 3. 未转置 vs 转置：softmax 布局值多少钱

Llama-3.1-8B GQA（`heads_q=32`, `heads_kv=8`, `head_dim=128`），batch=16，
seqlen 1k→128k，纯 FP4 paged decode。

## 结论

转置 softmax 在 batch=16 上把注意力内核加速 **2.2×（1k）到 3.8×（64k）**，
倍数随上下文增长而增长。

未转置路径的实测带宽从 seqlen 8192 起就钉死在 **1.4 TB/s** 不再上升。这不是
DRAM 的限制——同一台机器同一批 page，FA4 能跑到 6.6 TB/s。1.4 TB/s 是 softmax
的吞吐上限：每个 KV block 的 softmax 代价是固定的，于是延迟随 token 数线性增长，
带宽收敛到一个常数。转置把这个常数抬到 5.5 TB/s。

IKET 把钱花在哪里量清楚了：未转置时 `sm_exp` + `sm_pquant` 吃掉一个 KV block
的 66%，因为 S tile 是 128×128 而只有 4 行带 query，指数和量化对整块做，**32 倍
的功白费**；同时第二组 softmax warp 从头到尾没启动过。转置后这两项塌缩到 27%，
第二组 warp 也上岗了。代价是行归约换了轴，`sm_rowmax` 从 103 ns 涨到 218 ns，
成为今天最大的单项——**当前挡路的 rowmax，正是转置为了那笔大账付出的价钱。**

## 测量口径

先说清楚这组数字怎么来的，以及哪些地方不能过度解读。

**未转置是开关翻转，不是 git 回滚。** `_decode.py` 的模块级常量
`_TRANSPOSE_S` 是 `fp4_decode_kernel.py:613` 那 13 个条件合取里的第一项，置
`False` 即强制走未转置路径。测量用 `/tmp` 里的一次性 wrapper 在首次 compile 前
改写该模块属性，仓库源码未改动；wrapper 同时包住 `FP4DecodeKernel.__init__`
断言每一次 decode 构造都确实带着 `transpose_s=False`，避免拿到贴错标签的数字。
另配 `CUTE_DSL_CACHE_ENABLED=0`，因为编译缓存的 key（`_decode.py:235`）里不含
`transpose_s`，磁盘缓存有可能把转置版内核喂回来。

选开关而不是回滚，是因为转置之前的那棵树同时还带着流竞态（`c6e4032` 才修）和
tail 放大器。回滚测出来的差值里会混着这两个 bug 的代价，无法归因给布局本身。

**三列同一 session 测出。** 参数逐字对齐：
`--head-configs 32:8 --batches 16 --iters 20 --warmup 30 --repeats 5 --with-fa4`，
CUDA graph replay 计时。FA4 不受 `_TRANSPOSE_S` 影响，被独立测了三轮作为对照：
七个点彼此相差 1% 以内，s=65536 上早先 sweep 的 755.1 µs 与本轮两次的 655 µs
相差 15%，判为旧值的一次瞬时抖动。表中 FA4 取三轮中位数。

**TB/s 的分母各不相同，不能横向比大小。** 每一列都是「该内核真实搬运的字节 ÷
它花的时间」。NVFP4 每元素 0.5625 字节（4 bit 数据 + 每 16 元素一个 E4M3
scale），BF16 每元素 2 字节，相差 3.56 倍。所以 FA4 的 6.6 TB/s 高于转置版的
5.5 TB/s，并不意味着 FA4 更快——同一 workload 下转置版的延迟只有它的 1/2.9。
FA4 这一列的作用是标出这台机器在这种访存模式下的实测天花板。

**本轮未做正确性验证。** 未转置路径的正确性依据是 `262e1a6` 记录的 soak 4/4
通过 + kernel 套件 60 项全过；本报告只测性能，没有重跑校验。

softmax warp 的耗时：

| range | 未转置 | 转置 | |

| `sm_pquant` | 545 ns | 128 ns | 转置后省 4.3× |
| **计算合计** | **1372 ns** | **403 ns** | **省 3.4×** |

其余角色：

| | 未转置 | 转置 |
| --- | --- | --- |
| block 周期（插桩） | 1920 ns | 704 ns |
| block 周期（无桩推算） | 1635 ns | 441 ns |
| `mma_wait_p` | 1371 ns | 331 ns |
| softmax0 计算占周期 | 73% | 59% |

因为一个周期里的 range 数量一样。但它占未转置周期的 15%、占转置周期的 40%，
所以任何绝对时间对比都必须用无桩测量，图上的空白也不能直接读成空闲。

## 转置到底改了什么

四处改动，三处赚钱一处亏钱。

**1. query 从行变成列，softmax 不再对整块做无效功。** `m_block_size = 128`，
而 GQA 组大小只有 4。未转置时 S 是（128 query 行 × 128 kv），PackGQA 只填满 4
行，其余由 TMA 补零——但 softmax 仍要对整个 tile 做指数和量化。补救手段
`q_replicate`（把 query 行重复填满 tile，让每个 softmax 线程只需负责一小段列）挂在
`_enable_q_replicate` 上，而这个属性在代码库里从未被设置过，所以
`q_replicate` 恒为 1，补救从未生效。转置后 S 变成（128 kv × 128 query 槽），
其中 `transposed_query_rows = qhead_per_kvhead = 4` 是活的，softmax 只碰这 4 列。
这是 `sm_exp` 从 724 ns 掉到 57 ns 的原因。

**2. 第二组 softmax warp 上岗。** decode 只有一个 q stage，未转置时 softmax1
那一组没有 stage 可认领，直接退出——trace 里它的生命周期和 `empty` warp 一样
是 1.5 µs。转置后 `softmax_row_groups = 2`（条件：`q_stage == 1`、
`transposed_query_rows` 为偶、且没有融合 residual），四个活列一组分两个，
butterfly、指数和打包的每线程工作量再减半。

**3. P 改走共享内存，解开了下一个 QK 的依赖。** 未转置时 P 和它的 scale factor
复用 S 读出的那块 tensor memory，所以下一个 block 的 QK 必须排在本 block 的 PV
之后。转置后 P 住在 shared memory，只剩 scale factor 仍有别名，而 decode 在 O
之上留有 128 列空闲 tmem 可以把它们挪过去。挪开之后下一个 QK 只需等 softmax
把 S 抽干，而这个信号在 load 完成时就发出，不必等到整步结束。体现在
`mma_wait_p` 从 1371 ns 降到 331 ns。

**4. 代价：行归约换了轴。** 转置后 S 的一行沿线程轴展开，行归约从线程内的局部
操作变成了 warp 蝶形 + 四个 softmax warp 之间经共享内存的交换
（`fp4_decode_kernel.py:3609` 的注释）。`sm_rowmax` 因此从 103 ns 涨到 218 ns，
在转置版里成了最大的单项，占 softmax 计算的 54%。

## 与既有记录的对账

`docs/tasks/1.vllm_v1_design.md` 记的是「注意力内核快约 1.8 倍」，与本表的
2.2–3.8× 不矛盾：那组数字取自 vLLM 实跑，rows=1 和 rows=8，注意力设备时间
5.8/10.6 µs 与 6.3/11.6 µs——上下文极短，内核时间由 prologue 和启动开销主导，
主循环占比小，于是布局差异被稀释。本表也复现了这个趋势：加速比从 s=1024 的
2.22× 单调爬到 s=65536 的 3.80×。倍数随 KV block 数增长，因为差在每个 block。

由此该文档里的那条提醒需要按更大的数值重述：`_TRANSPOSE_S = True` 只是「请求」，
13 个条件里任何一条不满足都静默回落，其中 `qhead_per_kvhead` 必须是 2 的幂是
模型相关的。Llama-3.1-8B 的 32/8 = 4 满足，但例如 24/8 = 3 的模型会悄悄走未转置
路径，`guards.py` 没有任何检查拦它。**静默损失不是 1.8 倍，长上下文下是 3–4
倍。**

## 后续

`sm_rowmax` 现在是转置版 softmax 里最大的单项（218 ns，占 softmax 计算的
54%，占一个 block 周期的 32%）。转置版当前 5.5 TB/s 对 FA4 实测天花板 6.6 TB/s
仍有约 19% 的差距，能不能靠压 rowmax 拿回来，是下一轮要回答的问题。
