# 为 NVFP4 vLLM 路径开启 CUDA graph：改动、性能，以及 RL 接入

任务计划见 `docs/tasks/3.vllm_cudagraph.md`。本文记录实际落地的结果。

## 结论

**图开起来了，而且代价为零。** 捕获后的 NVFP4 每步 **3,798 µs**，捕获后的 BF16 是
**3,809 µs**，比值 **1.00**——这个比值在开工前是 **6.1**。验收线原本定在 ≤1.25，
实际落在 1.00。

三句话概括这轮做了什么：

1. 拆掉 `guards.py` 里那条禁止 CUDA graph 的拦截，让后端向 vLLM 声明
   `UNIFORM_SINGLE_TOKEN_DECODE`，由 vLLM 自己解析出 `FULL_AND_PIECEWISE`。
2. 把每步重新分配并清零的量化 scratch 改成常驻缓冲——这些清零会被录进图，每次
   replay 重跑。
3. 把 split-K 从派发路径上摘掉，生产恒为单块。

**关于 RL：此前所有 NVFP4 臂跑的都不是我们的后端。** `kv_cache_dtype=nvfp4` 是
vLLM 自己的 KV cache dtype，由 FlashInfer 服务；我们的后端只有
`--attention-backend CUSTOM` 才够得着。详见 §5。

## 1. 性能

### 1.1 四条臂

`tests/e2e/test_speed_account.py`，Llama-3.1-8B、SM100、batch 8、prompt 1000，
两点差分（32 token 与 288 token 各生成一遍，斜率即每步代价，prefill 落在截距里抵消）。

| 臂 | µs/step | 是什么 |
| --- | ---: | --- |
| BF16 + CUDA graph | 3,809 | BF16 部署实际跑的配置 |
| BF16 eager | 13,695 | 同样的算术，去掉 graph |
| NVFP4 eager | 23,142 | 本轮开工前我们的状态 |
| **NVFP4 + CUDA graph** | **3,798** | **本轮的产出** |

**NVFP4+graph / BF16+graph = 1.00。**

前三行取自 `docs/reports/2.bf16-comparison.html`。第四臂这次测量里
eager→captured 是 **4.9×**（该次运行的 eager 臂读数低于历史基线的 23,142；两条
eager 臂在多次运行间漂移可达 5.6%，两条捕获臂则稳定在 0.5% 以内）。**方差本身就是
结论**——它住在图消掉的那些 Python 里。

### 1.2 这笔钱原本是怎么丢的

开工前 23,142 对 3,807 的 6.1× 可以拆成两笔独立的账：**四个 bit 收 +9,447 µs**，
**不能用 CUDA graph 另收 +9,888 µs**。后者与量化无关，是本轮的全部标的。

而 9,447 那一笔里 GPU 只占 239 µs（4,522 对 4,283），attention kernel 本身反而比
BF16 **快 208 µs**。也就是说 NVFP4 的 GPU 侧早就合格了，剩下的几乎全是主机没跟上
设备。图把这部分抹平之后，两条捕获臂自然收敛到同一个数。

### 1.3 split-K：测了，不采纳

在真实 vLLM 引擎、图打开的条件下扫过 `num_splits`（`tests/kernel_profile/sweep_split_served.py`，
提交 `379ab9d`）。结论与 `docs/infos/2.decode_kernel_state.md` §4.7 记录的
「一致 13–23% 开销」**相反**——那条结论是 eager 下测的，而本轮恰好拆掉了它的前提：

| batch（prompt 16384） | 1 路 | 最优 | 收益 |
|---|---:|---|---|
| 1 | 6,563 | 16 路 4,655 | −29.1% |
| 4 | 6,606 | 4 路 5,169 | −21.8% |
| 16 | 6,778 | 1 路 | — |
| 32 | 9,343 | 1 路 | — |

低 batch 上确实是大幅正收益。**仍然不采纳**，理由是这一轮的优先级是正确性而非性能：

- split 路径**从未跑过 padding 行**。`tests/kernel` 里所有 split-K 用例都是满行，
  而图重放下「一批里混着零长度行和满行」是每一步的常态。
- 按行数选 split 的规则会要求从没运行过的档位（MQA 单行在 148 SM 上算出 128 路，
  GQA 算出 16 路），而测试只覆盖到 2、4、8。combine 的 shared memory 按
  `log_max_splits` 开，高档位是没走过的代码。

既然单块路径已经与 BF16 持平，用一条正确性更薄的路径去换 20–29% 是反向交易。
测量结果留在 `docs/tasks/3.vllm_cudagraph.md` §7.2，需要时可以再启一轮。

### 值得单独一提的两处

**scratch 常驻的契约不对称。** 原以为「量化 kernel 反正覆盖整块内存，清零多余」。
对 `query_fp4` 成立，对 scales **不成立**：量化 kernel 每个 KV head 只写
`heads_q // heads_kv` 个 slot，其余永远没人写。用 `0xA5` 预填 `torch.empty` 做对照，
packed query 仍与全新分配逐字节相等，scales 则发散。所以 **scales 必须在分配时清零
一次、此后永不再清**——这是常驻化之后唯一无法靠形状检查兜住的契约，写进了
`fp4_decode` 的 docstring。

**capture 后清 slot 表的标志位被提前消费过。** `build_for_cudagraph_capture` 默认
转调 `self.build`，所以先置标志位会被同一次调用消费掉，导致每次捕获都清一遍、而
捕获结束那一刻反而不清。改成在 `super()` 返回之后于 `finally` 里置位，并加
`capturing` 标志把捕获自身的 build 排除掉。测试断言收紧为「最后一次捕获之后恰好
清一次」。

## 3. 正确性

### 3.1 已有覆盖

- `tests/kernel`：新增 12 个用例覆盖 scratch 参数的持久性、校验与等价性，含一个

- `tests/e2e/test_cudagraph.py`：新增 596 行。捕获发生过、每个 decode step 都重放了
  图、`error_code` 全程为零、含 padding 的批与不含 padding 的同一批结果一致、
  捕获期没有编译也没有同步。
- 全套 `tests/e2e` 在**图开/图关两种配置下各跑一遍**均绿（120 passed / 1 skipped）。

**额外做了一趟「不变量全程 armed」的重跑。** 控制面的错误字在生产路径上没人读
（读一次要一次 host 同步），所以平时它写了也白写。用 `NVFP4_DEBUG=1` 把每步的检查
打开重跑整套 e2e：**119 passed / 3 failed / 1 skipped，而三个失败全部是
`test_steady_state.py` 那三条「decode 步不许问设备问题」的闸门抓到了我故意打开的
那次同步**——23 次违规全部指向 `control.py:433`，即 `raise_for_errors` 内部。

也就是说：**在换手、页提升、尾巴复位、图捕获与重放的全部 e2e 场景里，没有任何一条
控制面不变量被破坏**，而闸门本身也证明了它抓得住多余的同步。

### 3.2 本轮发现并补上的缺口

**仓库里唯一一个检验「模型还答得对吗」的测试跑的是 `enforce_eager=True`。**
`tests/e2e/test_vllm_integration.py` 的四条 GSM8K 臂全部禁用图，而我们要上线的
恰恰是开图的配置。为图写的那 120 个 e2e 测试全是结构性的——图有没有捕获、padding
行有没有被中和、slot 表有没有复位——**没有一个问过开图之后准确率还在不在**。

补法是加第五臂（`CUSTOM` + `nvfp4` + 图），闸门用 BF16 那条现成的准确率下限，
并额外比较 eager 与捕获两条 NVFP4 臂的 token 分歧。分歧不能用严格相等来卡：
图重放下 vLLM 会把 decode 批 padding 到捕获宽度，线性层因此跑在 eager 从未见过的
token 数上，cuBLAS 可能换 tile 形状，reduction 顺序一变 logits 末位就变，贪心
argmax 偶尔落到别处——这在 BF16 开图时同样成立。有用的信号是**分歧的形状**：数值
噪声表现为「晚且少」，真缺陷（slot 表坏了、尾巴陈旧、padding 行污染活行）表现为
「早且普遍」。

### 3.3 追查过的两个疑点

**睡眠/唤醒会不会让新请求读到上一轮的尾巴。** 不会，而且有代码依据而非类比。
slot key 是首个 KV 页的**物理 block id**，会被回收复用；新请求捡到回收的 block 时
必然是 prefill、`computed == 0`，而 `control.py:226-234` 的 `ERR_STALE_SLOT_HISTORY`
判断与 `(computed > 0)` 相与，因此不触发——**接管旧 slot 是设计内的正确行为**。它随后
把自己的尾巴写进去，`seqused_residual` 只圈到自己的长度，页内残留落在被 mask 的
位置且是有限 BF16 而非 NaN（`runtime.py:51-52` 那次 `zeros` 的注释正为此）。睡眠/
唤醒不过是「带间隔的普通换手」，走同一条路径。

**常驻缓冲在训练期占多少。** Qwen3-8B（36 层、8 KV 头、head_dim 128、页 128、
32 slot）下 `tail_key` + `tail_value` = **576 MiB**，query 那三个约 3 MiB。它们在
`CuMemAllocator` 之外，睡眠时不释放。相对整卡是 0.3% 量级，不构成问题。

### 3.4 已知且不修

`test_prequantized_query_matches_bf16_query_exactly[32-1]`：MQA（`heads_q=32`,
`heads_kv=1`）纯 FP4 路径下 decode 不可复现。**不是测试顺序问题**，加残差后同一
几何稳定，`(8,8)`、`(32,8)`、`(16,1)` 十六次重复均稳定。这个几何和预量化 Q 路径都
不在 vLLM 集成里用到（Qwen3-8B 是 32:8 GQA、BF16-Q 路径）。已记入 `CLAUDE.md`。

## 5. 如何启用 RL training with custom NVFP4

### 5.0 先纠正一个认知

**`kv_cache_dtype=nvfp4` 选的不是我们的后端。** 它是 vLLM 自己的 KV cache dtype
（`config/cache.py` 的 `CacheDType`），由 `v1/attention/backends/flashinfer.py`
服务。我们的后端是 `AttentionBackendEnum.CUSTOM`，其 enum value 为 `None`，
从不出现在 `_get_backend_priorities` 里，**只能通过 `--attention-backend CUSTOM`
显式选中**。

所以 `train_dapo_math.sh` 此前所有 NVFP4 臂（`N0`、`nvfp4_icepop`、`nvfp4_tis`、
`nvfp4_kpop`、`nvfp4_ais`）跑的都是 FlashInfer 上的原生 NVFP4。证据：8 月 3 日那次
`nvfp4_ais one_step`（status 0）以 `block_size=16`、`max_num_seqs=128`、
`enable_chunked_prefill` 启动——这三样每一样都会被我们的 `guards.py` 拒绝，而
`NVFP4Backend.supports_block_size(16)` 返回 `False`。若我们的后端在场，引擎会在启动
时就死掉。它没死，所以它不在场。

推论有二：那条路上 **CUDA graph 一直是开着的**（`enforce_eager=False`，同一份日志
显示 `Capturing CUDA graphs (decode, FULL): 7/7`）；以及**只改那四个设置什么也得
不到**，只会让现有的 FlashInfer 路径变慢。选后端才是承重的那一步。

### 5.1 前置：把包装进训练环境（必需，否则启动即失败）

Ray 和 vLLM server 实际运行在 `_local/envs/golongrl-train`，而不是
`_local/envs/vllm-nvfp4`。前者此前没有 `nvfp4_attn_kernel`，`--attention-backend CUSTOM`
会抛 *"Backend CUSTOM must be registered before use"*。

```bash
/opt/conda/envs/torch-base/bin/uv pip install \
  --python /apdcephfs_wzc1/share_303098609/hunyuan/juliandeng/dev/dayou/BitKV_nvfp4/_local/envs/golongrl-train/bin/python \
  --no-deps -e /apdcephfs_wzc1/share_303098609/hunyuan/juliandeng/dev/dayou/nvfp4_attn_kernel
```

**已执行并验证**：entry point `nvfp4_vllm -> nvfp4_vllm:register` 注册成功，
`AttentionBackendEnum.CUSTOM.get_class()` 解析到 `nvfp4_vllm.backend.NVFP4Backend`，
`supports_block_size(128)` 为 `True`、`(16)` 为 `False`。`--no-deps` 足够，两个环境
的 torch 2.11.0+cu130 与 nvidia-cutlass-dsl 4.6.0 一致。撤销方式：
`uv pip uninstall --python <同一个> nvfp4-attn-kernel`。

这不会影响其他臂：vLLM 用 `try/except` 包住插件加载，注册 `CUSTOM` 在不选中它时
不改变任何行为。

### 5.2 脚本改动

`BitKV_nvfp4/scripts/train_dapo_math.sh`，**目前未提交**。加一个显式开关，默认
`native` 保持所有既有臂的行为不变：

```bash
NVFP4_BACKEND="${BITKV_NVFP4_BACKEND:-native}"
case "${NVFP4_BACKEND}" in
    native|kernel) ;;
    *) echo "BITKV_NVFP4_BACKEND must be native or kernel" >&2; exit 2 ;;
esac
```

然后由这一个选择**派生出全部五项要求**，调用者不需要手写任何一项：

```bash
NVFP4_KERNEL_MAX_SLOTS=32   # nvfp4_vllm control.MAX_SUPPORTED_SLOTS
ENABLE_CHUNKED_PREFILL=True
ROLLOUT_BLOCK_SIZE=16
NVFP4_BACKEND_ARGS=()
if [[ "${NVFP4_BACKEND}" == kernel ]]; then
    if [[ "${NATIVE_NVFP4_KV}" != True ]]; then
        echo "BITKV_NVFP4_BACKEND=kernel is accepted only by an NVFP4 arm" >&2
        exit 2
    fi
    # 不开 chunked prefill，vLLM 就不会拆 prompt，每步 token 预算必须装得下最长的
    # 那个，否则引擎拒绝启动。
    if (( MAX_NUM_BATCHED_TOKENS < ROLLOUT_MAX_MODEL_LEN )); then
        echo "NVFP4 kernel backend needs max_num_batched_tokens >= max_model_len" >&2
        exit 3
    fi
    ENABLE_CHUNKED_PREFILL=False
    ROLLOUT_BLOCK_SIZE=128
    if (( MAX_NUM_SEQS > NVFP4_KERNEL_MAX_SLOTS )); then
        MAX_NUM_SEQS="${NVFP4_KERNEL_MAX_SLOTS}"
    fi
    # verl 会把 false 布尔直接丢掉而不是发 vLLM 的 --no-<flag>，所以这两个必须关掉
    # 的设置用取反后的 flag 传。
    NVFP4_BACKEND_ARGS=(
        +actor_rollout_ref.rollout.engine_kwargs.vllm.attention_backend=CUSTOM
        +actor_rollout_ref.rollout.engine_kwargs.vllm.no_enable_chunked_prefill=True
        +actor_rollout_ref.rollout.engine_kwargs.vllm.no_enable_prefix_caching=True
    )
    EXPERIMENT_BASE="${EXPERIMENT_BASE}_kernel"
fi
```

配套地把三处硬编码字面量换成变量（`enable_chunked_prefill`、
`engine_kwargs.vllm.block_size`、`max_num_seqs`），并把 `NVFP4_BACKEND_ARGS` 加进
`TRAIN_ARGS`。这三处在其他任何路径上都保持原值——已用 A/B dry run 验证 `bf16` 臂
解析出的配置逐字节相同。

**这段必须放在 knob 文件 source 之后**，因为 source 会覆盖 `MAX_NUM_SEQS`。

#### 为什么不复用 `NATIVE_NVFP4_KV` 而要加新开关

`NATIVE_NVFP4_KV` 当前的语义是「vLLM 原生 NVFP4」，有五条完成了 200 步的臂由它
定义。劫持它会让 `nvfp4_ais full200` 静默换成另一套 attention 实现、并发降到四分
之一，而运行名与原生那次相同。四个设置仍然是全派生的，没人需要手写。

#### 不需要改的

`cudagraph_capture_sizes=[1,2,4,8,16,32,64]` 里的 64 **不用动**。vLLM 的 decode
dispatcher 按 `max_num_seqs` 过滤捕获宽度（`v1/cudagraph_dispatcher.py:211-222`），
64 会被静默剔出 FULL decode 图，只留一个 64-token 的 piecewise 图；而 dummy batch
的行数在 `_dummy_run` 里本来就被夹在 `max_num_seqs` 以内，
`ControlPlane.prepare` 的 `num_reqs > num_slots` 够不着。且 64 对其他臂
（`MAX_NUM_SEQS=128`）是有用的捕获宽度，改成条件式反而更复杂。

### 5.3 启动

```bash
cd BitKV_nvfp4
BITKV_NVFP4_BACKEND=kernel bash scripts/train_dapo_math.sh nvfp4_ais one_step
```

运行根目录为 `_local/runs/qwen3_8b_dapo_aime_nvfp4_ais_seed42_kernel_one_step`。

**首跑建议加安全网：**

```bash
BITKV_NVFP4_BACKEND=kernel NVFP4_DEBUG=1 bash scripts/train_dapo_math.sh nvfp4_ais one_step
```

`NVFP4_DEBUG=1` 让每步都读那个平时没人读的控制面错误字并具名抛出（平时不读是因为
一次 host 同步）。代价是每步一次同步，但 `one_step` 本来就不测吞吐；它换来的是
「跨越捕获、重放、请求换手、睡眠/唤醒这一整套，有没有哪条不变量被破坏」的确定答案。
**已验证它与图捕获兼容**（`test_cudagraph.py` 在 `NVFP4_DEBUG=1` 下 11 passed /
1 skipped，与不开时一致）。

### 5.4 预期性能，以及怎么比才有意义

**`max_num_seqs` 从 128 降到 32 会显著变慢，这与 kernel 无关。**
`GEN_BATCH_SIZE=192 × rollout.n=16 = 3072` 个序列摊到 8 个 TP=1 副本，每副本排队
384 个——128 时引擎已经 3 倍超订，32 时是 12 倍，两者都饱和，所以墙钟直接跟着
并发走。带宽下界只恶化 2.1×（NVFP4 KV 在 ~5.5k 上下文约 0.23 GB/序列，
45 GB/step → 23 GB/step），但实测比下界高约 3 倍，那部分若是按步计就是完整的 4×。
**预计 `timing_s/gen` 从 ~460 s 涨到 950–1850 s。**

**所以不要拿它和 8 月 3 日那次原生跑直接比。** 唯一能隔离出 kernel 贡献的比较是
**同为 `max_num_seqs=32` 的 native 与 kernel 对照**，不需要再改脚本：

```bash
sed 's/^MAX_NUM_SEQS=.*/MAX_NUM_SEQS=32/' _local/dapo_aime_qwen3_8b_frozen_knobs.env > /tmp/knobs_seqs32.env
DAPO_FROZEN_KNOBS=/tmp/knobs_seqs32.env DAPO_RUN_ATTEMPT=seqs32 \
  bash scripts/train_dapo_math.sh nvfp4_ais one_step
```

`CALIBRATED_*` 键会带过去，校验仍然通过。

看这几个指标（verl 已经全部记进 console / TensorBoard / SwanLab）：

| 指标 | 8/3 原生基线 | 含义 |
|---|---:|---|
| `timing_s/gen` | 462.87 | rollout 墙钟，主对照量 |

后两个要先确认，动态过滤可能悄悄让生成量翻倍。

另外注意：rollout 的每步约 23 ms，而 §1.1 测的 attention 侧是 3.8 ms 量级，**attention
在 rollout 的一步里是少数派**，并发上限的影响多半会盖过 kernel 的贡献。

### 5.5 剩余风险

- **睡眠/唤醒**是最大的未测项。§3.3 从代码上论证了它安全，但 e2e 套件不覆盖它。
  一步跑通即等于验证通过。
- **`no_enable_*` 这条传参路径是新的。** flag 能正确解析、vLLM 也确实应用了，但
  经 verl `engine_kwargs` 的这条具体路线从未运行过。
- 顺带发现（未改）：verl 的 `build_cli_args_from_config` 丢弃 `False` 布尔而不发
  `--no-<flag>`，而 `enable_prefix_caching` 在 vLLM 侧默认 `True`——**意味着此前
  所有臂（含 BF16）实际上都开着 prefix caching**。修它会改变既有 BF16 臂的行为，
  故留待你定夺。kernel 臂通过上面的取反 flag 绕开了。
